# brush as a Cognia shell backend

Assessment date: 2026-11-11 (Asia/Shanghai). This is a source and documentation assessment, not a runtime acceptance test.

Architecture review status: **conditional candidate for a profile-only experiment on an already-authorized terminal surface**. An embedded persistent Agent worker is not yet an architecture-ready design; the adversarial review below records the missing contracts.

Scope clarification from the user: the goal is an **optional shell backend**, and the architectural question is whether the existing implementation provides an adequate extension seam. The earlier review establishes safety/adoption constraints; it does not establish that today's extension interface is complete. The focused extension review below confirms reusable process owners, fragmented shell resolution/assembly, and an existing optimistic integration-capability declaration.

## What can be embedded

`brush-core` provides a persistent `Shell` with execution, variables, functions, working directory, jobs, and configurable I/O. `run_string` executes shell source and returns an `ExecutionResult`; `invoke_function` calls a stored function. `brush-parser` can be used independently for a Bash/POSIX AST, including optional serde serialization. These are actual library APIs, rather than a requirement to drive an interactive CLI. [Execution API](https://github.com/reubeno/brush/blob/0b6a4acc3bf68f41ddab686c6cb809871e01b508/brush-core/src/shell/execution.rs), [function example](https://github.com/reubeno/brush/blob/0b6a4acc3bf68f41ddab686c6cb809871e01b508/brush-core/examples/call-func.rs), [parser manifest](https://github.com/reubeno/brush/blob/0b6a4acc3bf68f41ddab686c6cb809871e01b508/brush-parser/Cargo.toml).

The bare core builder starts with an empty builtin registry. A full shell embedding must explicitly add the standard `brush-builtins` set, or register a deliberately selected set; core alone does not supply `cd`, `export`, etc. `brush-builtins::ShellBuilderExt::default_builtins` is the supplied convenience adapter. [Core builder](https://github.com/reubeno/brush/blob/0b6a4acc3bf68f41ddab686c6cb809871e01b508/brush-core/src/shell/builder.rs#L137), [registry default](https://github.com/reubeno/brush/blob/0b6a4acc3bf68f41ddab686c6cb809871e01b508/brush-core/src/builtins/registry.rs#L16), [builtin adapter](https://github.com/reubeno/brush/blob/0b6a4acc3bf68f41ddab686c6cb809871e01b508/brush-builtins/src/builder.rs).

I/O can be redirected through `ExecutionParameters::set_fd` and `OpenFile` values, including OS files/pipes and custom streams. This provides the building blocks for separate output capture, but Cognia would still own streaming, backpressure, output limits, lifecycle events, and terminal transport. No Cognia-level protocol is supplied. [Open files](https://github.com/reubeno/brush/blob/0b6a4acc3bf68f41ddab686c6cb809871e01b508/brush-core/src/openfiles.rs), [execution parameters](https://github.com/reubeno/brush/blob/0b6a4acc3bf68f41ddab686c6cb809871e01b508/brush-core/src/interp.rs), [I/O example](https://github.com/reubeno/brush/blob/0b6a4acc3bf68f41ddab686c6cb809871e01b508/brush-core/examples/call-func.rs).

## External execution hooks: main versus release

Main exposes `ShellExtensions::ProcessLauncher` and `TaskSpawner`. A custom launcher receives the resolved executable, argv, complete environment, cwd, descriptors, process-group policy, and kill-on-drop preference in a `LaunchRequest`. This is a useful interception point for external-program policy or alternative execution. It also exposes a separate `exec` operation. [Extension contracts](https://github.com/reubeno/brush/blob/0b6a4acc3bf68f41ddab686c6cb809871e01b508/brush-core/src/extensions.rs#L65), [launch request](https://github.com/reubeno/brush/blob/0b6a4acc3bf68f41ddab686c6cb809871e01b508/brush-core/src/processes.rs#L142).

**The published release tag does not have these hooks.** Its `ShellExtensions` contains only `ErrorFormatter`. Adopting the main hooks therefore requires a pinned source revision or a later release containing them, rather than assuming the published `brush-core 0.5.0` API includes them. [Release extension contract](https://github.com/reubeno/brush/blob/brush-shell-v0.4.0/brush-core/src/extensions.rs).

The launcher is not a complete sandbox boundary. Builtins and functions do not pass through it, and redirections open files directly through `std::fs::OpenOptions`. A command such as `printf x > /some/path` can write from the interpreter without launching an external program. The whole interpreter must run inside the appropriate OS/container isolation, or its filesystem and builtin behavior must be separately constrained. [Launch scope](https://github.com/reubeno/brush/blob/0b6a4acc3bf68f41ddab686c6cb809871e01b508/brush-core/src/processes.rs#L142), [direct file opens](https://github.com/reubeno/brush/blob/0b6a4acc3bf68f41ddab686c6cb809871e01b508/brush-core/src/shell/fs.rs#L235).

## Embedding and lifecycle caveats

1. **Do not embed the unrestricted default shell in the desktop Host process.** With the standard `exec` builtin and default Unix launcher, `exec` reaches `CommandExt::exec`, replacing the hosting process. Standard `umask` changes the hosting process's mask, and `ulimit` changes process resource limits. A worker process contains these effects; alternatively, an in-process design needs a carefully restricted builtin set and custom launcher. [exec builtin](https://github.com/reubeno/brush/blob/0b6a4acc3bf68f41ddab686c6cb809871e01b508/brush-builtins/src/exec.rs#L89), [native exec](https://github.com/reubeno/brush/blob/0b6a4acc3bf68f41ddab686c6cb809871e01b508/brush-core/src/sys/unix/commands.rs#L14), [umask](https://github.com/reubeno/brush/blob/0b6a4acc3bf68f41ddab686c6cb809871e01b508/brush-builtins/src/umask.rs#L105), [ulimit](https://github.com/reubeno/brush/blob/0b6a4acc3bf68f41ddab686c6cb809871e01b508/brush-builtins/src/ulimit.rs#L78).
2. **`cd` itself is per-shell state.** The implementation updates its own `PathBuf`, `PWD`, and `OLDPWD`, and supplies cwd when spawning children. It does not call process-global `chdir`; do not attribute the other process-global hazards to `cd`. [Working directory](https://github.com/reubeno/brush/blob/0b6a4acc3bf68f41ddab686c6cb809871e01b508/brush-core/src/shell/fs.rs#L21), [child setup](https://github.com/reubeno/brush/blob/0b6a4acc3bf68f41ddab686c6cb809871e01b508/brush-core/src/sys/tokio_process.rs).
3. **Cancellation needs explicit ownership.** Main defaults `kill_external_commands_on_drop` to false. Dropping a `TaskHandle` explicitly does not stop its task. Cancelling only `run_string` is therefore not evidence that background tasks or descendants were terminated; validate worker/process-tree teardown. [Builder option](https://github.com/reubeno/brush/blob/0b6a4acc3bf68f41ddab686c6cb809871e01b508/brush-core/src/shell/builder.rs#L196), [task handle](https://github.com/reubeno/brush/blob/0b6a4acc3bf68f41ddab686c6cb809871e01b508/brush-core/src/tasks.rs#L13).
4. **A custom future-backed child loses native job control.** Only default-launched native children have the private PID/process-group linkage. `ChildProcess::from_future` children have no PID, cannot receive `kill`/stop/continue through brush, and require their own cancellation strategy. The extension documentation explicitly records these limitations. [Launcher limitations](https://github.com/reubeno/brush/blob/0b6a4acc3bf68f41ddab686c6cb809871e01b508/brush-core/src/extensions.rs#L72), [child implementation](https://github.com/reubeno/brush/blob/0b6a4acc3bf68f41ddab686c6cb809871e01b508/brush-core/src/processes.rs#L31).
5. **Signals are not per-shell subscriptions.** Native waiting uses Tokio Unix signal listeners for SIGTSTP/SIGCHLD and Ctrl-C; job-control helpers can alter SIGTTOU handling. This is another reason to prefer a worker process over unrestricted embedding in a multipurpose Host. [Wait implementation](https://github.com/reubeno/brush/blob/0b6a4acc3bf68f41ddab686c6cb809871e01b508/brush-core/src/processes.rs#L72), [signal implementation](https://github.com/reubeno/brush/blob/0b6a4acc3bf68f41ddab686c6cb809871e01b508/brush-core/src/sys/unix/signal.rs#L108).

## Terminal integration protocol evidence

Brush's terminal integration is experimental, off by default, and does not by itself establish compatibility with a consumer using OSC 633. Its current wire shapes are:

```text
633;A
633;B
633;C
633;D;<exit-code>
633;P;Cwd=<escaped-path>
633;E;<escaped-command>[;<session-nonce>]
```

The nonce is optional and appears only on `E`, rather than on every event. A Cognia adapter must compare and preserve the actual authentication and event contract, not merely match the numeric OSC identifier. [Exact emitted sequences](https://github.com/reubeno/brush/blob/0b6a4acc3bf68f41ddab686c6cb809871e01b508/brush-interactive/src/term_integration.rs#L103), [opt-in feature](https://github.com/reubeno/brush/blob/0b6a4acc3bf68f41ddab686c6cb809871e01b508/docs/reference/experimental.md#terminal-shell-integration).

## Upstream assessment

Source evidence supports a trial as an optional Bash-like shell executable, an isolated persistent shell engine, or an independently adopted shell parser. It does not support treating brush as a replacement for PTY/ConPTY transport, a security sandbox, a source of all system utilities, or a compatibility-equivalent replacement for every platform's native shell.

### Existing terminal automation needs an adapter

Both Rust and TypeScript classify brush as `Unknown`/`unknown`; Rust then skips shell integration. A direct read-only check of `detectShellKind` returned `unknown` for both `/opt/homebrew/bin/brush` and `C:\Tools\brush.exe`. [Rust recognition](../../crates/cognia-terminal/src/integration.rs#L52), [unknown-shell setup](../../crates/cognia-terminal/src/integration.rs#L170), [TypeScript recognition](../../packages/plugin-contract/src/lib/terminal/shell-detect.ts#L39).

Cognia requires the per-spawn nonce on every consumed event:

```text
633;A;<nonce>
633;B;<nonce>
633;C;<nonce>
633;D;<nonce>;<exit-code>
633;P;<nonce>;Cwd=<path>
```

These differ from brush's native sequences above. In particular, merely enabling brush's built-in terminal integration will not establish Cognia command-end or cwd events. The existing `run-in-dock` flow explicitly depends on command-end events and times out for shells without integration. Headless command capture also consumes these events. A full integration must add a recognized shell kind and an adapter or compatible hook script, and validate nonce preservation, output boundaries, cwd, and exit codes. Reusing Cognia's Bash integration script is a candidate to test, not an established compatibility result. [Cognia event contract](../../crates/cognia-terminal/src/osc633.rs#L25), [Bash integration script](../../src-tauri/resources/terminal/shell-integration.bash), [dock execution](../../lib/terminal/run-in-dock.ts#L10), [headless capture](../../crates/cognia-terminal/src/headless.rs#L15).

### Keep confinement around the interpreter

Cognia's interactive spawner can already wrap the entire shell executable in its OS sandbox launcher. This shape also confines brush's own builtin and redirection effects. By contrast, attaching only main's `ProcessLauncher` to `SandboxedExec` would constrain external programs while leaving interpreter-side effects outside that boundary. Preserve existing Host approval and policy checks; an AST or launch hook can assist them but cannot replace confinement. [PTY sandbox prefix](../../crates/cognia-terminal/src/session.rs#L687), [OS enforcement contract](../../crates/cognia-exec-sandbox/src/traits.rs#L49).

## Recommendation and remaining acceptance work

**Proceed only with a bounded profile experiment on existing, authorized macOS/Linux terminal surfaces.** Keep the selected execution Host, trusted profile resolution, PTY ownership, sandbox policy, replay and transport. This recommendation does not enable a disabled multi-tenant terminal surface or change any Agent shell tier. Do not replace the full terminal stack or set brush as the global cross-platform default on this evidence.

If the actual goal is persistent shell state or Rust-defined builtins for agents, first compare the existing persistent headless terminal and private Agent REPL. An isolated `brush-core` worker remains a candidate only after its placement, execution identity, per-command job, approval, output, cancellation, drain and recovery contracts have been designed. Process separation alone establishes neither confinement nor that integration. The review below supersedes the earlier suggestion to proceed directly to a second worker experiment.

Before promoting an implementation beyond an experiment:

1. Pin the intended released version or source revision and build it on each supported target. If `ProcessLauncher` is required, verify its presence in that exact source rather than relying on the crate version string.
2. Run representative Cognia commands: quoting and Unicode paths, pipelines, heredocs, command/process substitutions, environment changes, working-directory persistence, `set -e`, `pipefail`, git, pnpm, and cargo. Check actual stdout, stderr, exit code, and filesystem effects.
3. Verify PTY programs, resize, Ctrl-C/Ctrl-Z, foreground/background jobs, timeout and explicit cancellation, full descendant cleanup, concurrent sessions, and Host restart behavior. For any later embedded worker, first satisfy the review's worker contract, then verify safe `exec`, `umask`, and `ulimit` behavior.
4. Drive Cognia's real interactive and headless flows with the nonce-compatible adapter: prompt readiness, command boundaries, cwd updates, nonzero exit, run-in-dock, disconnect, and reattach.
5. Exercise confinement against both external commands and interpreter-side writes such as builtin redirection. Confirm the same approval, output limits, and lifecycle policy as the current backend; test Windows separately before offering parity.

Verification in this assessment: upstream official documentation and source review, local owning-source and ADR review, and the read-only shell-family detection check described above. ## Adversarial architecture review — 2026-11-11

### Scope, claim and evidence standard

Claim under test: brush can be introduced as an optional interpreter within Cognia's existing execution owners, without adding a parallel execution authority. This matters because a shell can retain credentials, create descendants, and act after the caller has disconnected or lost authority.

Two independent, fresh-context, read-only reviewers examined Host authority/placement and terminal/job lifecycle. The primary reviewer reconciled their findings against the artifact and owning source, and additionally checked startup modes and module/crate ownership. The user explicitly chose to skip the optional cross-model review. Findings below concern omissions in the adoption proposal, not deployed brush vulnerabilities: there is no brush implementation in this change.

The review distinguishes ADR status from implementation. ADR-0196 and the Rust layer gate govern crate boundaries; ADR-0249 is Accepted and owns completion delivery. ADR-0253 is Accepted and records implementation of member standing, partitions and revocation, while its real two-person/model/browser rig remains unrun. ADR-0243, ADR-0244, ADR-0245 and ADR-0250 still carry Proposed headers; they contain implemented slices and future obligations, so their entire target state is not assumed present. A worker can be a supervised implementation detail, but it cannot invent a second process/session/admission authority. [Brush execution policy](https://github.com/reubeno/brush/blob/0b6a4acc3bf68f41ddab686c6cb809871e01b508/brush-core/src/shell/execution.rs#L12), [group application](https://github.com/reubeno/brush/blob/0b6a4acc3bf68f41ddab686c6cb809871e01b508/brush-core/src/commands.rs#L715).

### Release gates derived from the findings

- **Profile trial:** brush exists on the actual Host, existing profile sync and authority remain in place, unsupported/missing binaries refuse without switching execution Host or shell semantics, and integration capability is shown as degraded until nonce-compatible command/cwd events work. ## Optional backend extensibility — corrected review scope

The user's clarification changes the question from whether an application may safely run brush to whether a new optional shell backend can be added coherently. The `claim-verify-first` and `codebase-design` review separates the existing process/session owners from the shell-specific resolution and assembly that callers currently repeat.

**Verdict: partially extensible today, with concrete gaps in the shell-specific layer.** The existing PTY accepts an arbitrary executable, profiles carry shell/argv/cwd/env, the job supervisor accepts program/argv, and `createBashTool` already accepts an injected `ShellDescriptor`. These are useful seams to extend. They refute a blanket claim that the execution infrastructure cannot support another backend. They do not amount to a shared, selectable backend contract across the intended surfaces. [PTY executable](../../crates/cognia-terminal/src/session.rs#L692), [profile launch fields](../../lib/terminal/profiles.ts#L29), [job request](../../crates/cognia-jobs/src/types.rs#L109), [descriptor injection](../../sidecar/src/tools/builtin/core-files/bash.ts#L359).

### Smallest complete extension direction

Introduce a Host-resolved shell adapter seam inside the existing owners, rather than a new execution service. Its narrow job is to resolve a selection and startup mode into a launch plan plus truthful capabilities:

```text
resolveShell(selection, startupMode, admittedExecutionContext)
  -> backend identity + dialect + launch plan + effective capabilities
```

This is a proposed interface contract, not implemented code. The descriptor separates which backend is selected (`system` or `brush`), which syntax it accepts, where its executable/runtime comes from, and which startup modes it supports. The launch plan contains executable/argv and the relevant environment/startup integration changes; the existing execution owner still authorizes and launches it. An explicit unsupported mode or unavailable selected backend returns a named failure rather than silently running another interpreter.

The system adapter must preserve existing per-surface behavior: interactive profiles, chat login-command argv, deterministic unattended startup, and scheduled/bridge defaults are not interchangeable. Brush is the second adapter at this seam. Starting with its executable avoids introducing persistent interpreter semantics just to make it optional. If embedding `brush-core` is later required, its implementation must fit the separately specified worker/session contract; the initial extension must not claim that returning an external launch plan already implements an embedded engine.

The shared contract must have one authoritative descriptor/schema source and behavior fixtures across languages; it must not become another independent copy of `ShellKind`. Use the existing module/crate ownership rules for assembly, without adding a new plugin platform, supervisor, approval chain or transport. A selected backend starts only when requested; making brush available must not make it a mandatory dependency or start a permanent worker at boot.

Verification for this scope was a current owning-source and reachable-call-path review. The earlier 35 passing contract tests remain baseline evidence; they do not test the proposed seam or fix EXT-03. A future implementation needs a failing capability-regression test first, then adapter contract tests for system/brush selection, startup modes, discovery/degradation, unavailable selections, and preservation of existing process/admission/job contracts. The action in this turn is to correct the assessment and identify the minimal extension work; production source was not changed.
