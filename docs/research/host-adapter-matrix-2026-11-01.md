## 0. What this answers

ADR-0250 §2 says a brain runtime cannot be reused on the desktop by swapping the bridge, because the event publisher, the connector server lifecycle and the plugin adapters differ per host. This matrix lists, for every registered `HeadlessRuntime` and for every provider effect that owns runtime behaviour without a registry entry, how it is assembled on each host:

- **desktop**: the Tauri WebView, where React providers and initializers start the same `lib/` code;
- **brain**: `cognia-agent serve` (`cli/src/serve/serve-command.ts`), which boots the registry through `bootstrapHeadlessRuntimes`;
- **person brain**: one member's data partition on a multi-tenant Host (`COGNIA_BRAIN_PROFILE=person`, roster pinned by `PERSON_BRAIN_RUNTIMES` in `lib/headless/runtimes/index.ts`).

### 2.1 Connector server lifecycle

|                       | Desktop                                                                                                                                      | Brain                                                                                                                                                               |
| --------------------- | -------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Single owner          | Web Lock `CONNECTOR_RUNTIME_LOCK`, then a Rust runtime lease with `ownerClass: "desktop"`, `onUnavailable: "proceed"` (fails open)           | Lease with `ownerClass: "brain"`, `onUnavailable: "block"` (refuses to boot without it)                                                                             |
| HTTP ingress          | `connectorsStartServer` starts a loopback axum server only when a webhook or reverse-WS adapter is enabled; public reach through cloudflared | `connectors_start_server` returns `"companion:/connectors"`; the ingress is nested in the companion router, mounted only with headless services in single-user mode |
| Commands              | Tauri `connectors_*` (local-only per dispositions)                                                                                           | `headlessConnectorInvoker` remaps `connectors_register_adapter` → `connectors_register` etc.; others pass to `transport.call`                                       |
| OAuth callbacks       | desktop native flows                                                                                                                         | Lark and connector OAuth handlers installed after the lease is acquired                                                                                             |
| Remote-host interplay | `ConnectorBusProvider` tears down while a remote Host is driven, retries after lease loss                                                    | —                                                                                                                                                                   |

Both hosts compete for the same Rust lease slot. Under 2a this collapses to one owner (the local brain); under 2b the fail-open/fail-closed asymmetry must be resolved.

### 2.2 Desktop-only extras hidden inside registered rows

The exclusion gate records initializer symbols only, so these provider-level extras are recorded nowhere:

- `PluginToolDispatchProvider`: plugin hook exec and protocol-adapter exec/cancel.
- `GatewayProvider`: routing snapshot push and gateway decide answers.
- `DesktopMessageSourceProvider`: CLI and WASM renderer request sources.
- `WorkflowRuntimeProvider`: `installApprovalNotificationActions`.
- `routing-runtime`, `provider-cost-mirror`, `template-trust-reconciliation`, `background-task`, `file-share-host-sync`, `scheduler`: the reduced brain variants listed in the table.

Two symbols also read as live by accident: `startAutomationAuditMirror` matches a doc comment in `lib/automation/audit.ts`, and `ensurePlanStepRecovery` is called from `components/agent/plan/plan-halt-dock.tsx`, which sits in the brain's import graph.

## 4. What only the Tauri process can provide

Under 2a these stay in the Tauri process, and a local brain reaches them through the bridge or not at all:

Two different things are easy to conflate here. Some capabilities already have a brain implementation (a Node adapter or a `service/internal` command the companion RPC dispatches). Others exist only as Tauri commands marked `client` / `internal` in `protocol/companion-commands.json`; the companion RPC has no dispatch arm for them and rejects names outside `KNOWN_COMMANDS` (`crates/cognia-companion-rpc/src/rpc.rs`). Mounting the headless services on the desktop's companion server does not provide the second kind: each needs a new authenticated adapter from the brain into the Tauri process, or a move into a crate the brain can call.

## 5. Findings to hand on

These are defects or questions surfaced while building the matrix. They are recorded here and in the 0a ledger; fixing them is outside A5.
