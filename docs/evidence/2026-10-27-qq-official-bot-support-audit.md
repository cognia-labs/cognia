## Audit baseline before repair

Cognia has a working implementation structure for QQ official bots: credential-based token resolution, Webhook and gateway ingress, four conversation scenes, text and selected media sends, recalls and scene-limited typing/reactions. It does **not** implement the current platform's full messaging surface. Several omissions follow obsolete assumptions, and a few affect the correctness of already-supported paths.

“Implemented” below means reachable in checked-out source, with the stated local checks. It does not mean the current QQ application has permission or that production delivery was exercised.

### Support matrix

| Area                                    | Current implementation                                                                                     | Assessment                                                                                              |
| --------------------------------------- | ---------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------- |
| AppID/AppSecret and QQBot authorization | Keyring credentials, token cache, refresh-before-expiry, one HTTP 401/403 retry. REST uses api.bot.qq.com. | Implemented; token URL and business-error decoding need alignment.                                      |
| Webhook                                 | Form defaults to Webhook; URL card; native Ed25519 verification, op 13 response, op 12 ACK; TS subscriber. | Implemented in source; real console validation unverified.                                              |
| WebSocket                               | HELLO/IDENTIFY, heartbeat ACK detection, RESUME and backoff; GET /gateway.                                 | Compatibility path implemented; not a guarantee of present platform access.                             |

### Confirmed correctness and contract-alignment gaps

**F01 — P1: REST business errors and asynchronous outcomes are not decoded correctly.**

`index.ts:137` models `code`, not `err_code` or body `trace_id`; `index.ts:286` rejects only non-2xx HTTP responses. The native HTTP wrapper returns the original status/body without interpreting QQ errors (`crates/cognia-net/src/http_client.rs:239`), so no lower layer repairs this. The current [API guide](https://bot.q.qq.com/wiki/develop/api-v2/dev-prepare/api-call-guide.html) specifies `err_code` and body/header trace identifiers, and distinguishes 201/202 asynchronous outcomes. A synthetic HTTP-200 `{err_code:40034005,...}` response makes the real `send()` return `{ok:true}` with no message ID. A 400 response loses the documented business code and body trace. The exact real HTTP status for each business error was not measured. Fix the response contract, definitive-success criteria and async audit handling before expanding sends.

**F02 — P1: C2C uses the group five-reply budget.**

`serialize.ts:65` defines a shared limit of 5; both single and multipart reservation use it. Current [C2C send documentation](https://bot.q.qq.com/wiki/develop/api-v2/autogen/api/v2_users_user_openid_messages.post.html) and [overview](https://bot.q.qq.com/wiki/develop/api-v2/server-inter/message/overview.html) specify four C2C replies, while groups retain five. The fifth distinct C2C serializer call is accepted locally. `index.ts:134` also derives typing-slot reservation from the shared limit, risking loss of the final-answer slot under the existing conservative typing accounting. Whether typing itself counts remains unverified. Use scene-specific limits; include typing, multipart output and retry accounting in regression cases.

**F03 — P1: Full-message modes are dropped before the bus.**

The official [GROUP_MESSAGE_CREATE event](https://bot.q.qq.com/wiki/develop/api-v2/autogen/event/group_message_create.html) covers non-mention messages when enabled. `parse.ts:64` omits it; the gateway's `QQ_MESSAGE_EVENTS` allowlist also drops it (`gateway-client.ts:244`). Webhook accepts the envelope but reaches the same rejecting parser. Private-guild `MESSAGE_CREATE` is likewise omitted, and its intent is not configurable through the adapter factory. Both parser probes return null. Merely adding event names is insufficient: `parse.ts:241` currently sets selfMentioned=true for every accepted message, and runtime capabilities declare unmentionedDelivery=false. Preserve actual mention semantics and conversation admission when adding coverage. The [channel event contract](https://bot.q.qq.com/wiki/develop/api-v2/server-inter/channel/message/event.html) restricts the private-guild family by permission.

**F04 — P2: Token acquisition still uses the old domain.**

`auth.ts:15` sends credentials to bots.qq.com; the current [access-token page](https://bot.q.qq.com/wiki/develop/api-v2/dev-prepare/access-token.html) specifies api.bot.qq.com/app/getAppAccessToken. The [2026-08-10 changelog](https://bot.q.qq.com/wiki/develop/api-v2/changelog.html) unifies API domains. The probe confirms the old URL is used. This is a documented-domain mismatch; no evidence here proves the old hostname is currently unavailable. Token failure handling does reject missing access_token, so this is not the same false-success defect as F01.

### Missing current messaging capabilities

These are implementation gaps relative to QQ's platform, not a claim that every connector must implement every optional API.

**F05 — P2: Custom Markdown is disabled for an obsolete reason.**

`capability.ts:7` and both setup guides justify text fallback with per-template approval. The current [Markdown page](https://bot.q.qq.com/wiki/develop/api-v2/server-inter/message/type/markdown.html) explicitly opens custom Markdown to all group/C2C bots from 2026-04-23; channel use still requires invitation. `serialize.ts:135` flattens Markdown, producing msg_type=0 in the probe. Add scene-aware msg_type=2 with markdown.content, and keep channel restrictions separate. This also removes a false limitation in the onboarding documentation.

**F06 — P2: Visible quote references and structured inbound messages are missing.**

Current [C2C events](https://bot.q.qq.com/wiki/develop/api-v2/autogen/event/c2c_message_create.html) and group events carry message_scene.ext indexes, msg_elements and ark_data. The parser and A2UI mapper read only content, attachments and legacy message_reference. A nested-only quote normalizes to no text/reply context and no A2UI block; raw still retains the payload. Current send endpoints distinguish passive msg_id from visible message_reference indexes; responses provide ext_info.ref_idx. The adapter discards the latter and never emits native group/C2C message_reference. Add separate source-message/reply-index mapping, bounded nested/card projection, and preserve provenance; never use raw auth_token as visible content or model context.

**F07 — P2: File sends and local/binary/chunk uploads are absent.**

`serialize.ts:222` rejects every file segment with “QQ public API does not support file uploads”; its upload object only supports public URLs and types 1-3. Current [group](https://bot.q.qq.com/wiki/develop/api-v2/autogen/api/v2_groups_group_openid_files.post.html) and [C2C upload](https://bot.q.qq.com/wiki/develop/api-v2/autogen/api/v2_users_user_openid_files.post.html) contracts include file_type=4, binary data and upload_id merge flows. The file probe is rejected before HTTP. The [rich-media guide](https://bot.q.qq.com/wiki/develop/api-v2/server-inter/message/rich-media.html) recommends chunked local uploads. Extend the existing serializer/send pipeline rather than requiring users to host local files publicly; obey scene isolation and current upload limits.

**F08 — P2: Audio support is narrower than documented, and voice helpers are unused.**

`serialize.ts:240` accepts only SILK. The current group upload field table also permits MP3/WAV; the group-WAV probe is rejected locally. `parse.ts:34` omits voice_wav_url and asr_refer_text; probes show neither converted WAV nor supplied ASR reaches normalized segments/text. Add those inbound fallbacks. Do not generalize group formats to C2C without validation: its endpoint table still lists SILK and conflicts with the broader rich-media overview.

**F09 — P2: Native C2C streaming is absent.**

The official [streaming endpoint](https://bot.q.qq.com/wiki/develop/api-v2/autogen/api/v2_users_user_openid_stream_messages.post.html) uses stream_msg_id, ordered index and generation/final states. The adapter exposes only normal send, and the shared runtime matrix leaves textStreaming=false. A complete addition needs the runtime stream sink as well as REST serialization, lifecycle, ordered updates and finalization. Do not promise group streaming: its current endpoint explicitly excludes it.

**F10 — P2: Proactive, wakeup and event-based replies are blocked.**

`serialize.ts:178` says proactive push was withdrawn; line 254 requires msg_id for all scenes. Current send docs expose proactive sends, C2C is_wakeup and event_id replies; a no-msg_id probe fails locally. `QQDispatch` also lacks the outer event id, the gateway reconstructs envelopes without it, and non-message events are not normalized. Support must be deliberate: distinguish msg_id/event_id/is_wakeup, permission/consent state, per-app/per-recipient quotas and existing outbound authorization. Retaining failure on an expired passive reply is correct; never silently turn it into a proactive send.

**F11 — P2 at initial audit: native keyboards and interaction lifecycle absent; implemented in G6.**

Current group/C2C send contracts support keyboard content and callback actions. The QQ native A2UI matrix is empty, serializers flatten interactive output, default gateway intents omit INTERACTION, and parsing has no interaction callback path. A real implementation needs send projection, signed inbound normalization, callback acknowledgement and ConnectorBus callback routing. This is broader than adding a keyboard JSON field; channel permissions remain separate.

**F12 — P2: The 2026-10-21 material APIs have no integration.**

The official [material-management API](https://bot.q.qq.com/wiki/develop/api-v2/server-inter/message/material-management.html) adds prepare → binary PUT → complete, reusable qqbot-media references, list and delete. No such path exists in the QQ adapter. This can remove the public-CDN prerequisite for Markdown images. It is a separate lifecycle from message file_info uploads; preserve ownership, reference expiry and quota semantics rather than treating references as general remote URLs.

**F13 — P3: The 2026-10-26 group @all addition has no structured mapping.**

The changelog adds a native group-all token with administrator and daily-use restrictions. `buildQQContent()` turns mention segments into display text; there is no QQ role/quota-aware serializer for it. A manually supplied text literal may already pass through unchanged, so “the adapter cannot send the token at all” would overstate the gap. The missing piece is first-class segment mapping and discoverable, permission-aware behavior.
