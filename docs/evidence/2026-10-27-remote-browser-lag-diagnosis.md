## Problem frame

Diagnose O1 along the local Docker desktop path. G1 is met by identifying concrete bottleneck mechanisms and distinguishing them from unmeasured incident attribution. Inspect viewer selection, cadence, input queue, screenshot validation and guest configuration; test the frontend behavior. The initial phase excluded product changes. The user subsequently authorized the stream detection, auxiliary capture isolation and Selkies recovery repairs recorded below. Daemon/container changes and deployment were not performed. Real incident attribution remains open until Q1 and live timing evidence are available.

G3 extends discovery to the local Chromium/user-Chrome/embedded paths. Distinguish stream publication freezes, excess producer work, display-density cost and polling backlog. Follow C3; proposals must preserve R2/R5 safety constraints. Produce a prioritized source-backed report and targeted reproductions, without representing the new diagnosis as deployed optimization or native acceptance.

G4 subsequently authorizes the six repairs and real comparison under C4. The declared comparison exercises actual Chromium service, frame bytes, project decoder/painter/input queue and real canvas clicks; it replaces Tauri IPC with a browser binding and therefore does not establish WKWebView/native latency or the original Docker incident's cause. Native shell and Docker acceptance remain separate obligations.

G5 reopens discovery for remaining candidates. Prioritize unbounded runtime retention, then auxiliary screenshot budgets, layout invalidation, duplicate page instrumentation and measured native copy/decode costs. Actual diagnostic counts are separate from a proposed fix's accepted performance gain; do not disable required adaptation or input validation to claim a win.

## Diagnostic interpretation

The native automatic-refresh period is approximately `1000 ms + frame RPC/capture/validation/render scheduling cost`, so automatic animations refresh at less than 1 FPS when capture takes nonzero time. Manual and post-input refresh can happen sooner; 1 FPS is not a universal cap on every refresh.

For native human input the critical path includes any in-flight capture wait, a backend preflight screenshot, action delivery, and the frontend's post-action screenshot. Both captures include full-image validation. Several events tied to the same displayed proof do not form a smooth input queue: only one mutation can consume that proof. The existing test explicitly expects the second queued keystroke to return false.

A healthy Selkies iframe uses its own video/input transport; the native per-action proof path is not its video path. In that case inspect actual encoder mode, effective FPS, CPU, virtual-machine resource limits, architecture/emulation and transport timing instead of attributing lag to the native poll interval. The checked configuration alone does not prove CPU starvation or architecture emulation.

If the experience used to be smooth, a transition from Selkies to screenshot fallback is a useful hypothesis, not a proven regression. Before the authorized repair, the frontend opened once per enabled mount without timed retry after stream-open failure, and exposed screenshot cadence without the stream-open error. The repair below supersedes those historical observations; they do not describe the current stream hook.

## Repair implementation and final evidence

The authorized implementation supersedes the pre-repair failure descriptions above; those observations remain as historical evidence. The current production paths are:

- **Guest-to-viewer liveness.** The new image copies Selkies' stock Web root, verifies the exact entry and runtime-core hashes and import path, and instruments the asset the UI actually loads. The small child bridge observes socket, decoder/display-path and server-KILL signals. Only bounded versioned health is sent after a parent handshake. Parent validation requires the actual iframe source, exact grant origin, per-mount nonce, version and field schema. First-frame and missing-heartbeat timeouts recover view-only. No-frame idle periods remain healthy; hidden suspension resets pending decode timing.
- **Control remains authoritative.** Recovery invokes release/settlement before closing/retrying the grant. It never acquires a controller lease automatically. Explicit screenshot-mode control pauses stream retries until release. Auxiliary frame RPC failure clears the native frame/proof and reports a warning while an existing stream lease renews normally. Invalid returned proofs, expiry (including a hung renewal), renewal refusal, blur and session invalidation still release through existing paths. The release button remains usable without an auxiliary screenshot. Native frame TTL, single-use semantics, input-preflight capture, atomic drag and shared control guard were not weakened.
- **Guest recovery.** Selkies retries crashes and transient spawn errors indefinitely with capped interruptible backoff; stability resets backoff. Shutdown uses its own delay after stop is set, avoiding busy-spin, and never starts another child after stop.
- **Compatibility and rollout.** Health support is read from the image label and serialized as optional healthVersion. Legacy/custom images without protocol 1 keep their stream, show an upgrade notice, and are exempt from unsupported heartbeat deadlines. New built-in Selkies creation uses image revision 2; old saved built-in tags resolve to the repaired recipe on recreation. Existing containers and their data are never replaced automatically. The image README documents this upgrade path.
