## Original request

> 帮我分析一下现在的源代码管理的缺口，看看差什么功能，存在什么问题

## Problem frame

范围按 Cognia 产品的 `/source-control`、会话工作台、Agent 变更集及其 Git／Host 调用链理解。检查用户能否选对仓库、理解变更、正确暂存和提交、处理冲突、同步及恢复。以当前源码的可达入口和临时 Git 仓库为依据。没有用户提供的故障样本或功能优先级，本轮按改错文件、丢失修改、覆盖远端提交、流程中断的影响排序。

审计基于本机 `dev`。开始时 HEAD 为 `5ff8b5b52b`，复核时为 `e4eaf4bf96`。两者之间的提交未改本轮审计的 SCM 路径。桌面面板与 Git crate 的受审路径无未提交变更。探针以 macOS arm64、Git 2.54.0 和当前 Rust 命令实现运行，所有 Git 写入发生在临时仓库及本地 bare remote。

## 修复顺序与验收条件

1. **锁定操作对象。** 写侧用字面路径，保留原始文件名，作为同一变更处理重命名两端。Stash 使用对象 ID 验证当前序号。验收检查未选中文件的字节、暂存区及相邻 stash 均未改变。
2. **锁定远端和提交。** 发布预览目标 remote/ref，优先落实用户已有推送配置。强推绑定确认瞬间看到的远端 OID 和单一 ref，后续 Fetch 不更新这次确认。同步分别报告 Pull 与 Push，失败也回读已发生的状态变化。
3. **完整处理冲突。** 在协议表达文本、二进制及缺失的 stage，提供删除、选边和可编辑的文本合并结果。以 index 和最终文件字节为验收依据。
4. **补齐仓库选择和恢复。** 紧凑版能切换两个已授权的仓库，配对客户端用 Host 仓库标识获取正确 Agent 变更集，快速提交失败保留草稿。恢复从危险动作的预览、stash 内容和回收／reflog 入口着手。跨仓交付、行级暂存、子模块和 LFS 再按实际使用频率排期。

### 优先修复的实现边界

1. **Host 输入必须与命令语义一致。** 普通 Git 操作复用带修订号的 Fetch 对命名 remote 和参数分隔的已有约束。配对端还应校验 remote 的实际传输目标，以及 Git 实际使用的 common dir。审批命令范围保持与允许的作用范围一致。逐文件丢弃拒绝 Git 元数据，跟踪状态读取错误立即失败。
2. **把确认和快照带到执行点。** 强推确认保存 Host、仓库、目的 ref 和预期远端 OID。根或分支变化使旧确认失效。删除 worktree 时校验它当前关联的分支及预期 tip。
3. **让多个副作用的执行结果可核对。** Stack Push 用原子推送保证批量引用的一致性。跨步骤 worktree 删除需报告每一步的结果并回读当前状态。配对协议保留已脱敏的 Git 错误种类，使客户端继续提供对应恢复操作。
