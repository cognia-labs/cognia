## Confirmed defects

Severity ranks impact in the stated scenario, not observed frequency in production. Characterization probes intentionally assert the current bad outcome: their passing does not mean the defect is fixed.

### F1 — P1: external update preserves trusted procedural authority

- Trigger: a permitted plugin/MCP/Companion writer updates the text of an existing, namespace-authorized verified procedural row.
- `updateExternalMemory` checks namespace, update permission and PII but neither refuses procedural text changes nor downgrades their review/provenance. Its patch keeps `provenance: explicit`, `reviewStatus: verified`, `contaminationState: clean`.
- The procedural eligibility check and assembler continue accepting that text as verified guidance. Blocking creation of external procedural rows does not protect existing ones.
- Sources: `lib/memory/api/mutate-memory.ts:81-155`; contrast `lib/memory/api/store-memory.ts:126-131`; `packages/memory/src/retrieve/retriever.ts:400-405`; `packages/memory/src/runtime/apply-memory-context.ts:209-217`.
- Evidence: boundary probe B1 returned `ok:true, version:2` and retained every trusted flag. Policy and namespace scope are required; this is not unauthenticated access.
- Repair direction: apply procedural trust rules on every text-changing path; refuse or require explicit review of externally authored replacement text.

### F2 — P1: create-only permission reaches consolidation UPDATE / DELETE

- Trigger: an agent permits create but denies update and forget; a deliberate store matches an existing row in its authorized namespace, and the consolidation judge chooses UPDATE or DELETE.
- `storeMemoryCore` authorizes only `canCreate` / create scope, then delegates to a consolidator whose mutation callbacks can update or invalidate existing rows. Operation ceilings are not passed through or checked per chosen action.
- Sources: `lib/memory/agent-policy.ts:35-79` (independent hard ceilings); `lib/memory/api/store-memory.ts:177-180,224-240`; `packages/memory/src/consolidate/consolidator.ts:428-446`.
- Evidence: B2-UPDATE and B2-DELETE used the real policy resolver, store core and consolidator, fixed model replies and synthetic persistence. Both mutations occurred with `canUpdate:false, canForget:false`. The probe supplies the similarity result. On the current Host, the production builder additionally withholds personal candidates in this background context. The finding requires a visible, similar same-namespace row, such as a fact sourced from an unmarked message. The original fixture does not establish reachability for owner-only facts.
- Repair direction: enforce the permission for the selected operation at the mutation boundary, including automatic consolidation paths. DELETE here means soft invalidation, not physical deletion.

### F3 — P2: transient extraction failure becomes terminal no-output

- Trigger: a utility provider throws, returns malformed extraction output, or downstream consolidation throws while processing a turn-extraction job.
- Extractor catch returns `[]`; the orchestration catch also returns an empty result. The durable worker sees no applied operations and settles `no_output/nothing_durable`, bypassing retry/backoff. Completed-job dedup then reuses the terminal result.
- Sources: `packages/memory/src/extract/extractor.ts:105-106`; `lib/memory/write/run-memory-extraction.ts:183-184`; `lib/memory/lifecycle/job-worker.ts:385-392`; `lib/memory/lifecycle/enqueue-turn-memory.ts`.
- Evidence: L1 injects provider `503`, comparing it to a successful empty extraction: both yield identical terminal outcomes in the real worker. Current extraction tests explicitly expect swallowed errors.
- Repair direction: distinguish actual no-output from retryable failure without blocking the foreground chat. Project mining already propagates its errors; do not generalize this finding to every job kind.

### F4 — P2: a failed text-update upsert leaves an existing vector stale

- Trigger: an already indexed memory is revised, Dexie commits its new text, then the vector upsert fails once (or vector writing is unavailable during the change).
- Existing-vector UPDATE in extraction ignores the failure. Reconciliation tests only whether the document ID exists, so an old embedding under that ID is reported `already_consistent`; the new text stays lexical-only or semantically mismatched.
- Sources: `lib/memory/write/run-memory-extraction.ts:275-282`; `lib/memory/write/run-project-mining.ts:605-625`; `lib/memory/lifecycle/job-worker.ts:735-740`.
- Evidence: L2 supplies current text NEW and existing vector ID m1 representing OLD. It reports zero upserts and `already_consistent`. Removing the backend ID makes the control heal for a row with a visible source. Current reconciliation intentionally withholds private or unproven rows from background re-embedding, so the missing-ID control does not generalize to those rows.
- Repair direction: persist an indexing generation/content hash or durable dirty state, and reconcile content/version drift in addition to missing IDs and orphans.

### F5 — P2: queued lifecycle compaction runs in temporary mode

- Trigger: a lifecycle sweep is queued while enabled, then temporary mode is entered before it executes; cold compaction is enabled and an eligible episode exists.
- Worker re-reads settings and checks `enabled` but omits `temporary`. Vector builders refusing work do not stop the sweep from reading and revising canonical text.
- Sources: `lib/memory/lifecycle/job-worker.ts:758-786`; `lib/memory/lifecycle/lifecycle-sweep.ts:112-127`; temporary contract `packages/memory/src/types/memory.ts:370-371`.
- Evidence: L3 runs real retention, compaction, sweep and worker: `temporary:true` still produces one text write; master-disabled control skips.
- Repair direction: recheck the hard gates at execution for every job kind, retaining necessary deletion/privacy cleanup behavior deliberately.

### F6 — P2: query expansion loses synonym-only lexical matches

- Trigger: keyword-only fallback, expansion enabled; query `delete file`, saved memory `Remove document`.
- Expansion correctly builds `delete file remove document` and BM25 finds the memory, but the later meaningful-term gate requires overlap with the original query. The synonym-only hit is discarded.
- Sources: `packages/memory/src/retrieve/retriever.ts:576-595`; `packages/rag/src/keyword-expansion.ts`.
- Evidence: R1 returns one hit for direct `remove document` and zero for expanded `delete file`, over the identical corpus. Expansion can still affect ranking of rows that already overlap the original; it is not wholly inert.
- Repair direction: gate against meaningful expanded terms while keeping the stopword-only false-positive protection.

### F7 — P2: excluded scoped override suppresses valid global fallback

- Trigger: active global and workspace rows share key `package-manager`; workspace row is expired or quarantined but still has status active.
- Candidate loader applies stable-key precedence before retriever eligibility. It removes the global fallback, then retrieval excludes the sole surviving workspace row and returns nothing.
- Sources: `lib/db/memories.ts:675-686`; `packages/memory/src/retrieve/retriever.ts:391-405,542-544`.
- Evidence: R2 uses real Dexie queries and transactions: both expiry and quarantine return zero; deleting only the ineligible override yields the global hit with the same query.
- Repair direction: compose eligibility and per-caller scope/type filtering before choosing stable-key winners, or retain fallback layers until eligibility is resolved.

### F8 — P2: failed Companion receipt strands the operation key

- Trigger: `memory_mutate` reserves a pending receipt, the canonical command succeeds, then receipt persistence fails or the host exits in that window.
- The reservation and canonical command/receipt are separate commits. While the pending marker exists, the TypeScript command waits up to five seconds and rejects the same key with `memory_mutate: operation still in flight`. The normal retention sweep deletes markers older than 30 days. That cleanup frees the key without determining the original command result.
- Sources: `lib/memory/api/manage-for-caller.ts:121-170`, `lib/db/memory-operations.ts:263-287,316-335`, `lib/db/memory-governance.ts:759-771`, `lib/storage/retention.ts:156-161`.
- Evidence: B3 injects receipt failure and observes one canonical write, two rejected retries and a pending receipt. The poll budget is shortened to 0 ms. The existing retention test in `lib/db/memory-governance.test.ts:566` independently verifies that stale pending markers are eventually pruned.
- Repair direction: make canonical result and receipt atomic where possible, or recover a pending operation by durable outcome/fencing. Simply releasing the key after an ambiguous successful create risks duplication.

### F9 — P2: OpenCode / Pi global files cannot be saved from their editor

- Trigger: edit `~/.config/opencode/AGENTS.md`, `~/.pi/agent/SYSTEM.md` or `APPEND_SYSTEM.md` in the external memory tab, outside the current workspace.
- Providers mark them editable. The actual hook constructs allowedRoots from workspace roots plus only `~/.claude` and `~/.codex`; the editor forwards this allowlist to the save guard, which necessarily refuses these global files.
- Sources: `hooks/memory/use-external-memory.ts:123-129`; `components/memory/external/external-memory-tab.tsx:149`; `components/memory/external/external-memory-editor.tsx:100`; `lib/memory/external/providers/opencode.ts`, `lib/memory/external/providers/pi.ts`, `lib/memory/external/edit.ts:79-80`.
- Evidence: R3 uses real discovery and save guard with the hook's exact root construction: three editable files, three `Refusing to write outside the allowed roots` errors. The hook/editor wiring is source-verified, not a real UI click.
- Repair direction: share resolved vendor roots between discovery and the guarded editor, preserving path bounds and backup behavior.

## Gaps and deliberately limited support

1. **Memory embedding remains coupled to Twin.** No independent memory embedding/backend configuration was found. `tryBuildMemoryDeps` reuses Twin dependencies and exposes safe keyword fallback plus a reason. This is a supported degradation, not an assertion that recall is absent.
2. **External-file discovery is incomplete for relocated/new layouts.** Providers accept vendorRoots but `useExternalMemory` never supplies resolved roots. Codex provider enumerates only one level of `<codexHome>/memories`; it does not discover `memories_v2` or nested rollout contents. This statement is about current code coverage, not an external vendor compatibility guarantee. No real home-directory memory files were read by this audit.
3. **Real acceptance remains pending.** `lib/memory/module.ts:14` explicitly sets `acceptance: { realSmoke: "pending" }`. Searches under `tests/e2e` and `tests/real-e2e` found route/wallpaper inclusion but no dedicated memory learning-to-recall-to-delete browser journey. TUI smoke has limited list/delete checks. Phone/offline replay, host restart and real provider quality need acceptance runs.
4. **Evaluation measures deterministic plumbing, not semantic model quality.** Current golden eval uses character-trigram hash embeddings and an in-memory loader; it bypasses real embedding configuration, DB scope precedence, transport and device boundaries. The local run reports BM25 hit@1 78.6%, hit@5 92.9%, paraphrase hit@5 50%. Hybrid hash-fixture numbers are NOT evidence that real semantic embeddings improve or worsen production recall.
5. **ADR drift:** ADR-0202 still says Companion `asOf` is deferred; current dispatcher AND generated request schema support it. This is a documentation defect, not a missing feature.
