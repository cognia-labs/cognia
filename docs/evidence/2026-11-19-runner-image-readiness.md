## Problem frame

Runner 的价值是把指定 Agent 按照部署选择送进正确的容器并完成真实任务。评估沿 `runtime catalog → Dockerfile → 发布 → registry → 部署路由 → 握手、执行、清理` 展开（G1、C1）。本轮沿用先前 [Runner 按需选择](2026-10-21-runner-agent-selection.md) 和 [镜像拼装审计](2026-11-02-image-assembly-audit.md) 的背景，以当前源码、CI 和 registry 重核关键结论。现有镜像拼装审计有共享工作树改动，本次 Runner 专项在独立账本落证据。

## 现有能力

- `cognia-runner` 随容器启动单个外部 Agent，通过 stdio 对接，工作区由宿主挂载。`selected` 支持指定 runtime、`all` 与 `none`，并从锁中裁剪 npm 依赖。`full` 为兼容默认，安装更广的 Agent 集合。自定义 `RUNTIME_IMAGE` 的文档入口面向 Debian/glibc，Selected 带固定版本 Node，覆盖原镜像用户和入口点。 [Runner README](../../deploy/runner/README.md)
- `cognia-agent-bundle` 对应 sandbox pool。它把 Agent 与项目工具链镜像分开，支持按 digest 固定镜像、探测 libc 与可用命令，并注入 supervisor。GitHub Runner 的工作流引导属于独立交付路径。 [ADR-0183](../content/docs/en/adr/0183-the-agent-is-brought-to-the-image.md) · [GitHub Runner](../../deploy/github-runner/README.md)
- 已有可复用的做法包括 Selected 的完整性锁、Kiro/Droid 固定校验和、离线 CLI 冒烟、以及 Runner 在按 digest 测试后推广标签。 [Runner Dockerfile](../../deploy/runner/Dockerfile#L18) · [Images workflow](../../.github/workflows/images.yml#L258)

1. **恢复交付。** 补齐 18 个分类并复跑 Runner 和 bundle 的预检、构建与冒烟。用可访问、带 digest 的发布引用替代 T2 缺省值，验收冷机启动和上一个 digest 的回滚。
