## Problem frame

Audit the current checkout, treating terminal support as the integrated interactive terminal plus SSH/serial, paired-host access, agent/workflow execution and extension entry points (G1). Trace entry points through transports and native handlers, then run focused existing tests. Distinguish implementation, deterministic verification and real-environment acceptance. Do not infer deployment or device behavior from documentation or mocks (O2, O3). Preserve concurrent work (O1, C1).

## Initial findings and follow-up order

1. **Interactive result semantics need attention.** `runInDockTab` and Dock wait_for_exit return `output: last?.cmd`, and the interactive workflow forwards that field. For a command producing `hello`, this source path supplies the command line instead of its stdout. The separate `command-output.ts` helper reads xterm buffer rows for UI output actions; it is not used by these return paths. Headless execution has a different implementation returning backend output. Before changing anything, define whether the interactive API promises stdout, terminal output, or command metadata, then add a discriminating behavioral test. Also account for shells without integration, which cannot signal command_end normally.
2. **The local terminal test baseline is red, with concrete stale assumptions.** `run-in-dock.test.ts:46-49` directly seeds `agent:<chat>:<tab>:terminal:write`, while `consent-broker.ts:265-266` now appends a serialized scope (`:null` when absent); the supposed pre-grant is ignored and the tests wait for a consent request they never answer. `terminal-instance.test.tsx:534-536` mocks window.confirm; the chip now awaits useConfirmDialog, so clicking takeover alone does not call takeControl. The chip's own dialog-confirmation tests passed. This explains the fixture mismatch; it does not prove a real runtime consent/takeover failure.
3. **Docs are stale in decision-relevant ways.** `integrated-terminal.mdx` still describes WebRTC as planned, all browsers as unsupported and desktop PTYs as in-process; all conflict with traced code. It also contains old static module/command counts. ADR-0031 includes both a shipped WebRTC heading and older deferred-path wording. Use current source for support decisions until these docs are reconciled.
4. **Recording is built but not surfaced.** Unit-tested recorder/player utilities are not enough to claim a recording feature. Product scope and entry point still need an explicit decision.
5. **Run real acceptance after fixing the fixtures and restoring build headroom.** Prioritize desktop spawn/input/resize/search/split → reload/detach/reattach/kill; paired WS and WAN fallback → controller takeover and permission revoke; SSH auth/jump/host-key/SFTP/forwarding; serial hardware; PowerShell/cmd and Linux native runs. Include long-running output/replay truncation and old-host capability negotiation. The module itself still records realSmoke pending.

## 2026-11-18 内置终端与外部 Shell 审计

> 帮我分析一下，看看现有的内置终端和对外部shell环境的支持，差什么功能，或者存在什么问题，并且对照业内的优秀实践

Cognia 已经具备可持续运行的 PTY、命令感知终端和多种外部连接。最紧迫的差距是执行位置的一致性。打开、重启、释放端口和补全各自解析运行位置，用户在终端看到的上下文可能与动作实际使用的 Host、目录或环境不同。其次是登录 Shell 的兼容性。当前集成能产生结构化事件，但部分启动配置会在注入过程中改变。

审计取样为 2026-11-18 的共享工作区，基线为 `f6b7354c51ac80d256653ce2e62b2eb4dc3d73e2`。核心终端实现与基线一致，Companion 通用 Shell RPC 和终端文档含共享改动。本轮聚焦可交互终端、关联 Agent/Workflow 执行、SSH 和已接入的外部运行环境。只更新证据账本及本地验证产物。复杂度主要来自终端流、通用 RPC、项目绑定分别维护状态，以及真实双 Host 和跨平台环境才会出现的差异。

在 `f6b7354c51` 基线上，把 Profile、动作路由、兼容性分别交给三组独立的只读复核。采纳了可由生产调用链重复验证的结论。主表 T01–T12 已逐项替换并追加 T13–T16。

### 改判依据

- **T13 上调为首要问题。** `terminal_host_sync_profiles` 与 `terminal_kill_port` 都声明 `approval: interactive`。常规配对 HTTP 和 WebRTC 转发调用参数，统一进入 `authorize_approval`。参数缺少 `adminLease` 时，且前置的设备和能力检查已通过，返回 `428 interactive_approval_required`。启动流另走终端 ticket、配对授权和 Spawn 帧，因此同步拒绝后仍可能开出 Host 的默认 Shell。正常界面没有在这些调用处取得批准。见 `protocol/companion-commands.json:27291,27325`、`lib/tauri/transport-companion.ts:1196,1237`、`crates/cognia-companion/src/api.rs:1184`、`crates/cognia-companion/src/signaling/dispatch.rs:766`、`crates/cognia-companion/src/remote_execution.rs:1030` 和 `crates/cognia-companion-security/src/admin_lease.rs:101`。
- **T01/T02 保留条件性 P1。** 旧探针以单个 JS Map 模拟 Profile 同步。本轮使用生产 WS adapter 和帧编解码，Host 替身按设备整表替换。接受同步的对照中，普通命名项使用保存字段，两个并行 ad hoc 会互相覆盖，同一 Host 的另一设备作为隔离对照。普通 ad hoc 还可覆盖等待 Spawn 的 Agent 临时项。修复 T13 时需同时验证这些竞态，以免恢复同步后暴露。
- **T03 分成两个等级。** 本机 IPC 可以命中与原标签不同的 TCP 监听，保留 P1。以 SSH 标签为例，需要命令集成能识别失败、用户点击修复、本机具有同端口监听和终止权限。配对 RPC 常规路径被审批门拒绝，保留 P2 的静默失败。原生 RPC 成功返回空数组时照样尝试重跑。以实际客户端替身捕获动作发往本机，重跑发往旧远端 A 或原 SSH 句柄。由 Rust 源码确认本机执行空间及强制信号行为。
- **T04 保留 P1。** 对旧会话的停止请求送回原连接。可以成功结束、被拒绝，或连接失败。非严格停止处理随后移除标签与句柄，替代会话通过当前路由打开。实验分别验证 A 成功停止后 B 启动、停止被拒绝后旧会话仍在替身 Host 以及原会话已退出后新建被插件否决。原生同机请求也缺少原 argv/env、cwd 快照和 sandbox/编码字段，Rust 有自己的默认值。扩展伪终端菜单仍显示无法完成的 Restart，分屏菜单操作组主标签，替代项会另开普通标签。后两个属于界面一致性问题，未另立 P1。见 `components/terminal/terminal-tab-context-menu.tsx:130,202`、`components/terminal/terminal-dock.tsx:947`、`stores/terminal/terminal-store.ts:684`。
- **T14/T15 是两个独立失败窗口。** T14 在将 A 的同步结果交还客户端前切到 B，收到实际编码的 Spawn 帧的是 B。T15 让模拟 Host 在构造会话后关闭 WS，而后真实编排切到 WebRTC 发送第二次请求。同一目标也可能重复启动，因此只固定 Host 仍需处理丢确认。
- **T05–T12 保留分级，调整范围。** T06 的配置刷新与协议功能刷新是两件事。T07 新增 Zsh 非登录复验。T09 将解析阶段的「无端口」更正为导入计划的「22 端口」，第二个密钥无预览提示。T10 的远端一次性合同属于主动拒绝，现有缺口主要是运行位置提示及环境接入。T11 已有降级与重连通知，待补的是准确说明新 Shell 和重协商结果。T12 保留可选扩展。Profile 启动命令只有类型与帮助函数，改列 T16。
