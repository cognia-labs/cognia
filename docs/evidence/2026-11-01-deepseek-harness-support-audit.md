## Problem frame

Audit Cognia's managed DeepSeek Harness integration end to end: release identity, installer/doctor, profile authority, SDK/ACP lifecycle and events, tool/model bridges, UI reachability, and shell/platform limitations (G1). The first follow-up authorized F1/F2/F8-F11 repairs and review (G2,C3); G3 additionally authorizes the remaining F12/F13 ownership and profile-code repairs under the user-selected C4 recovery policy. Preserve concurrent work and user data; the RC upgrade, optional native features and separate dsh-superagent-prototype remain outside these six repairs. Distinguish upstream, composed, adapter and actually exercised capability throughout.

## Audit: findings and priorities

### F1 — P1: reinstall removes native DSH history and attachments

Both production finalizers rename the current runtime to `.previous`, activate the staged tree, then recursively delete `.previous`: `cli/src/runtime/external/dsh-installer.ts:440-460` and `crates/cognia-external-agent/src/dsh_runtime.rs:398-421`. Staging only copies runtime assets/dependencies and creates an empty `dsh-home`; it never carries old state forward. Session JSONL is explicitly rooted at `<runtimeHome>/sessions`, while attachments are rooted under `<runtimeHome>/dsh-home`. Therefore a successful reinstall removes those native records. Cognia's separately stored chat transcript is not the same data and is not claimed to be deleted here.

The reachable UI calls stage/finalize on Reinstall (`hooks/agent/use-dsh-runtime.ts:147`, `deepseek-harness-card.tsx:289`). The separate CLI one-phase installer has the same replacement/deletion pattern (`dsh-installer.ts:110-164`). Existing replacement tests check that old markers disappear; they do not assert native-state preservation. Prioritize separating durable state from runtime binaries or explicitly carrying it forward with rollback. Do not use reinstall as a repair path for valuable native DSH sessions until this is addressed.

Probe: `.cache/deepseek-harness-audit-20261101-reinstall-repro.mjs` bundles and imports the actual production Node installer module and invokes its exported finalizer against temporary session/attachment fixtures. It reports both fixtures missing and fails the preservation assertion. It does not start the host or touch a user runtime. The matching Rust path has been inspected in source, not dynamically executed by this probe.

### F2 — P1: maintenance lacks an authoritative host lifecycle guard

Install/finalize do not check live processes. Removal only trusts a supplied session count: CLI `backend remove` omits it (`cli/src/cli/backend-command.ts:132`), Node IPC defaults it to zero (`node-backend.ts:694-700`), and Tauri forwards the renderer value (`commands.rs:597`). Even the UI count reads manager session-map entries (`lifecycle/service.ts:670`), while session creation registers the entry only after `await adapter.createSession()` (`manager.ts:4145`). Starting/handshaking processes and sessions in another CLI process are not authoritative inputs to that count.

The install button is gated only by hook-local busy/report. Runtime files and persistence can consequently be replaced/deleted while still owned. This establishes unsafe maintenance admission, not proof that every running process immediately crashes. No real user session was disrupted. The guard must be owned by the host and cover active/starting processes and concurrent maintenance, not merely a renderer session count.

### F3 — maintenance item: the supported release trails the current RC line

The registry snapshot resolves `latest`/`next` to `0.2.1-rc.5` and `alpha` to `0.2.2-alpha.2`. The managed manifest, launcher and channel all pin `0.2.1-rc.2`. The official rc.4 release fixes diagnostics entering ACP stdout; rc.5's listed change concerns thinking presentation. Version lag alone does not establish a P2 product defect. Cognia's actual ACP receive path uses `JsonRpcPeer`, which skips non-JSON noise (`packages/agent-runtime-kit/src/json-rpc-peer.ts:259`); its focused noise test passed. That does not guarantee tolerance of every possible stdout corruption, but no such failure was reproduced here. The original P2 priority is withdrawn in favor of a release-maintenance item.

Downloaded rc.2 and rc.5 SDK protocol `types.ts` compare byte-for-byte equal (`diff -u`, exit 0). This narrows one upgrade risk; it does not establish equality of runtime behavior, session events, dependencies or ACP implementation. Upgrade the RC line only with refreshed closure, profiles and conformance evidence; do not edit the version string alone.

### F4 — explicit capability gap: SDK persistence is not connected to resume

The pinned SDK already defines `session/resume`; Cognia's transport exposes prompt/wait/close only and its manifest declares resume unsupported. Normal multi-turn works while the owned process survives; stop closes that process and the adapter cannot reconnect to the same persisted native session. ACP is the existing resumable channel. A complete SDK implementation needs stable stored identity, owned-process restoration, missing/incompatible history handling, interrupted-turn repair and cancellation/reconnect tests, rather than merely turning on the capability bit.

### F5 — capability exclusions: native subagents, skills and plugins remain absent

All managed profiles certify `dsh-sdk-minimal`; the launcher rejects extra bundles/profile dependencies. Native subagent service/spawn/fork/control plugins, skill discovery, plugin management, goals and PTC are explicitly `not-composed`. SDK lineage decoding and `session/wait` are present, but do not enable native delegation. Cognia teammate dispatch, MCP tools and instruction summaries are independent paths and must not be advertised as native DSH feature parity. Enabling those native features would be a deliberate profile/authority expansion with its own validation obligations.

### F6 — future alpha support requires a new SDK host-request path

The separate `0.2.2-alpha.2` protocol adds opt-in `approvalRequests`, `capabilities.userQuestions`, `approval/request`, `user-question/ask` and `user-question.cancelled`. Current Cognia does not negotiate or handle them. The current SDK limitation on native mid-turn approval is true for the pinned RC, not a timeless upstream limitation. Existing Cognia MCP `ask_user` is a different bridge. Adopting alpha also requires reviewing the minimum Node 24.9 change and runtime composition/API migrations; Cognia's current >=26 floor already exceeds that minimum.

### F7 — maintenance and verification debt

- ADR-0120 records the original hand-written host plane, session format 0 and limited ACP behavior. Current code uses the official launcher, format 4 and richer ACP; a superseding/amending record should point readers to the current contract. Some installer comments still point to removed `lib/.../runtimes/dsh/` paths.
- The doctor still treats a C compiler as the native-subprocess readiness signal and comments that Linux node-pty has no prebuild. The inspected installed closure contains `node-pty@1.2.0-beta.15` with `prebuilds/linux-{x64,arm64}/pty.node`, and the provider uses lazy loading. Therefore the old explanation is stale; compiler presence is not evidence that the actual binding/sandbox can start. Linux behavior itself was not run, so this is a probe-design gap, not a claimed Linux failure.
- The original runtime smokes exercise ACP new/prompt/permission rejection without persisted resume/list/close/cancel. The adversarial follow-up below now passes those lifecycle operations on the actual pinned DSH wire, including history and same-process continuation. The Cognia ACP adapter/manager path and packaged shell still need their own lifecycle acceptance.

### F8 — P1: concurrent installs can activate another unfinished staging tree

Both hosts use one shared `.staging` path. Every stage deletes/recreates it (`dsh-installer.ts:413`, `dsh_runtime.rs:340`); finalize checks only its existence, without operation identity, readiness or digest validation (`dsh-installer.ts:440`). A controlled interleaving reproduced: A completes stage; B deletes/recreates staging and pauses in dependency installation; A finalizes B's incomplete tree. The activated runtime has no lockfile, the original session is lost, and B subsequently fails ENOENT while its error still claims the previous runtime was left in place.

This is reachable without assuming multiple desktop windows: `external-agent-settings.tsx:710` conditionally mounts the runtime card; leaving that view unmounts its hook, while the pending install action continues. Returning creates a fresh hook-local `actionBusy` state and permits another installation after doctor completes. Independent CLI processes are another route. The Node counterexample runs the actual exported stage/finalize functions with real temporary filesystem operations and a controlled fake dependency installer; the matching Rust algorithm was inspected, not dynamically run. Per-operation staging identity and host-owned serialization are required; a local React busy flag is insufficient.

### F9 — P1: the default Node host rejects its own managed launcher in a normal project

Runtime facts/install use `defaultDataRoot()` (`~/.cognia`) at `node-backend.ts:665-679`, but `isDshLauncherInvocation()` derives its permitted runtime from `dirname(workspacesRoot)` (`node-backend.ts:376`). The CLI constructs a default backend (`host-branch.ts:36`) whose workspaces root defaults to the project CWD (`node-backend.ts:549`). These roots differ for an ordinary project.

An isolated current-source backend probe reads its own facts, then invokes `spawn_external_agent` using that exact Node path and runtime launcher. It is rejected before process launch: `command must be a bare allowlisted binary name, got a path: .../node`. The same launcher is admitted when the workspace root is artificially placed at `<home>/.cognia/workspaces`. The earlier adapter smoke explicitly constructs a sibling `runtime`/`workspaces` layout (`scripts/smoke/deepseek-harness-adapter-smoke.ts:209-227`) and therefore missed the default-path defect. The positive smoke results stand for that fixture layout, not ordinary CLI startup.

### F10 — P2: one-phase CLI activation failure has no rollback

`installDshRuntime()` renames the live tree to `.previous`, then performs the staging-to-live rename without a rollback catch (`dsh-installer.ts:156-160`). Fault injection at the second rename leaves no live runtime, with the old session only under `.previous`. A retry unconditionally deletes that sole backup before activation; the old session is not recovered. This differs from the two-phase finalizer, which has a rollback catch. The injected failure and retry were run against the actual one-phase installer with a temporary filesystem and controlled fake npm.

### F11 — P2: effective SDK capability profiles incorrectly certify live streaming

`manifest.ts:91` declares SDK `streaming: native`; the SDK preset refinements do not override it. The adapter contributes only `mcpTools: true` (`sdk-client.ts:737`), so the production manager's negotiation path (`manager.ts:5715`) retains that declaration. A pure negotiated-profile counterexample returns `native` for both SDK profiles, versus `unsupported / committedRepliesOnly` for ACP.

This is a contract mismatch, not an inference from the word streaming: `channel.ts:65` explicitly defines the boolean as live token deltas, `DSH_SDK_CAPABILITIES.streamingDeltas` is false, and `install.ts:358` maps generic `streaming` to that boolean. That helper has no production caller. The codec synthesizes `message_delta` only from committed `assistant/message`, which cannot supply live tokens. The settings card's direct snapshot is accurate while the effective profile is not; passing generated-catalog consistency gates did not check that truthfulness property.
