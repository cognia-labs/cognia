## Problem frame

用户应当能回答今天/本月消耗了多少、这笔钱对应哪个项目或 run、多少钱已确认、多少钱仅是估算、哪些调用受预算约束。当前主要问题是同一用量在采集、成本结算和使用端可能变成不同数字（O1–O3）。阶段验收应从相同样本跨接口对齐开始，随后验证真实账单、真实 Host 和移动端（Q1）。

## 结论

Cognia 的消费可见性已有较完整的产品形态。此时最该投入的是**让同一笔用量从调用到报表都可追溯**。报表里显示的钱可能是 SDK 估值、本地价格推算、Router + Fusion 保守入账，也可能混入其他工具折算出的价格。每种金额都能回答有价值的问题，但需要标清来源、到哪一步已确认，以及哪些数据尚未覆盖。当前有低报和高报两种方向，无法用一个全局修正系数解决。

## 建议实施顺序

1. **先让数字可用。** 优先修 F01–F05、F12–F15，并验证 F20 的两条入账路径。统一零值、未知、部分估算、SDK 报告、厂商确认；修 token 子集、外部扫描覆盖、多端更正游标和归属。补上镜像和日期边界（F06–F07）。验收用同一组合成调用覆盖重复、跨 provider 更正、迟到、外部读失败与删除后投影守恒。金额用最小精确单位累加，复用 Fusion 的账本和定价能力。历史行只有在量、身份和当时费率可证时才可更正，其余保留可解释的未知状态。
2. **给预算明确的保护范围。** 一般日/月预算作为已计金额门禁，显示未知用量、未入账和覆盖范围。需要硬限额时复用 Host 侧已有预留/结算机制，做并发、不同 provider fallback、取消、崩溃与重启回收故障注入。保护对象按账号、project 和 run 分开配置。已产生的费用在删除聊天后仍保有明确处理政策。
3. **用小范围真实账单建立对账。** 先选 OpenAI 与 Anthropic 的一个隔离 workspace/项目，验证管理凭据、分页、账单 line item、时区、数据延迟和非 token 费用。OpenRouter 按活动窗口接入并标注覆盖。把本地估算、厂商已报告、订阅配额、外部 API 标价折算各自显示，保留差额和未知归因。组织计费、凭据授权、历史修复与个人离线能力可独立交付。
4. **扩展可操作的分析。** 用同一个查询与口径覆盖 Web/desktop/mobile、CLI、CSV/JSON。加自选账期、account/project/provider/model/agent/workflow/attempt drill-down、价格与来源详情、数据新鲜度和缺失告警。已有月末预测、优化检测和工作单元归因可直接放在这一层。更长历史可用去标识日/月聚合支撑，同时保留项目删除、隐私与同步的明确规则。
