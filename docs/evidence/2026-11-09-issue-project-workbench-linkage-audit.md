## Problem frame

The acceptance path starts with an issue in its owning project and workspace. A user can find its current work in the workbench, launch or inspect the right run, trace its session, branch, PR and deliverable, then handle review or CI feedback and confirm delivery on the original issue. Feedback must stay within the workspace and must survive a temporary refusal. An explicit stop needs an observable authority boundary. Existing project, issue and execution records are the units of inspection. The audit uses current checkout source and isolated fixtures on macOS arm64.

### Status semantics

| Surface                  | Implemented state model                                             | Customisation and flow                                                                                                                                         |
| ------------------------ | ------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Local Issue              | Backlog, Todo, In Progress, In Review, Done, Canceled               | Fixed columns. View grouping, collapse and external status-value mapping exist. Triage and numeric Stage are separate attributes.                              |
| IssueProject             | Backlog, Planned, In Progress, Paused, Completed, Canceled          | Fixed descriptive values. Changing these values does not stop its issues or wakeups.                                                                           |
| IssueRun                 | Queued, Running, Succeeded, Failed, Cancelled                       | Claims, engine acceptance and one-shot settlement. Success and failure both advance the issue to In Review. Cancellation hands it back to its recorded status. |
| Coordinator Thread       | Waiting, Working, Staged, Ready for Review, Landing, Idle, Resolved | Read-time projection of chat, child lifecycle and PR facts. The resolved marker wins before pending approval checks.                                           |
| AgentTask and Squad task | Runtime-owned execution plus explicit human review transitions      | Their review verdict is independent of the linked Issue status. A dependent AgentTask requires its dependencies to be Completed.                               |

The issue move guard is intentionally permissive outside an active In Progress lock. Moving a card to Done does not require a delivery acceptance or a prior review decision. Sync and federated status projection are also lossy. A local failed IssueRun parks its issue In Review, while a federated failed AgentTask maps to Canceled. The run history preserves the engine outcome, so column counts alone do not express failure or human waiting.
