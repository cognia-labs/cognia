Compare public Codex product guarantees and exposed API behavior, keeping capability parity separate from matched performance parity. Do not modify product code, send messages, enable locked use, or change persistent access policy as part of this audit. This ledger is separate from the existing browser-heavy repair ledger and PiP optimization ledger because the new outcome is desktop application operation and parity.

## Assessment on 2026-10-28

**Current verdict:** desktop automation has a substantial, tested implementation, but this Mac's saved policy disables agent-driven operation. The current checkout could not reach native readiness during this audit, so operational readiness and good native performance are not established. It cannot yet claim full macOS Codex parity: foreground keyboard/text/drag delivery and the unavailable Locked Use native integration are concrete capability differences.

An off switch is a configuration state, not a product defect. The saved settings are evidence about the next boot configuration, not an observation of a running process. This audit never enabled automation, changed access policy, sent content to a provider, or issued OS input.

### Verified execution path

1. `plugins/computer-use/src/index.ts:327` publishes app state, app list, element queries/expansion, zoom, wait, OCR and revision-bound actions; registration is at line 644.
2. `lib/claude/build-options.ts:3684` checks character opt-in, mobile policy and IM authority; its tool manifest excludes the computer-use plugin when this fails. Enabled-plugin lifecycle and character policy remain required even when the platform has automation capabilities.
3. `lib/plugin/api/automation-api.ts` binds plugin permissions and turn/session provenance and forwards to `lib/automation/client.ts:135`.
4. `src-tauri/src/lib.rs:1713` registers the canonical IPC commands. `crates/cognia-automation/src/automation/commands.rs:575` and `:820` enforce invocation, gate, consent/audit and route local or remote execution.
5. `crates/cognia-automation/src/automation/worker.rs:248` serializes backend access; `:645` captures state and `:854` executes revision-bound actions. State/action contracts include lineage, revision, turn binding and coordinate transforms.
6. `lib/external-bridge/handlers/computer-use.ts` forwards the same app-session shapes; workflow nodes use the canonical client. These routes have deterministic tests, not current native/provider acceptance.

### Capability comparison

It describes Windows as foreground-only. The page publishes no comparable native latency/resource benchmark. Public product behavior is not evidence of the private Codex backend architecture.

### Performance findings: source behavior, not a benchmark

Existing useful optimizations include model frames capped at 1280x800 by default, unchanged-frame suppression, cached revision queries, native stream reuse for the same window, and a 250 ms focus-metadata cache. Image suppression runs after capture/redaction/scaling, so it bounds model payload rather than eliminating native capture work.

The following require targeted experiments before optimization claims:

1. **Collection budget differs from returned projection.** `worker.rs:677` passes depth into the AX traversal, then applies `options.maxNodes` at `:805`. `platform/shared/tree_shape.rs:38` allows up to 25,000 collected nodes, 8 MiB and a 10-second traversal budget, while `session.rs:23` defaults to a 1,000-node model projection. Requesting fewer returned nodes does not itself reduce the AX collection budget.
2. **Repeated tree collection is serialized.** One worker handles all apps. `settle_application_tree` at `worker.rs:1197` reads until stability, normally at least twice with a 50 ms pause, and can extend its settling deadline to 5 seconds. The plugin's instruction asks the agent to read state before and after each action, adding capture/traversal work around the worker's own post-action read. These are code paths and budgets, not observed p95 values or hard end-to-end upper bounds.
3. **Capture ownership is backend-wide.** `platform/ax/mod.rs:79` stores one capture stream, and `platform/ax/screen_capture.rs:145` replaces it when the app/window key changes. Native configuration requests 30 fps with queueDepth=3. No task-end/idle/kill release of this app-state capture slot was found; Drop stops it at replacement or backend shutdown. Stream lifetime and multi-app restart costs need a real CPU/GPU/RSS experiment. This is a resource-lifecycle concern, not a measured leak or measured 30 fps workload.
4. **Long-text optimization is route-specific.** `commands.rs:1042` applies pasteThresholdChars only to desktop_type. The canonical model-facing perform_action(TypeText) path at `worker.rs:1149` calls backend.type_text directly. The setting therefore does not govern this canonical path; actual native throughput is unmeasured and Enigo already accepts whole strings outside virtual-display mode.

### Background delivery needs app/window authority, not a deleted foreground check

The current trait has send_keys(chord), type_text(text, opts), and drag(from, to, opts), with no process/window identity in the keyboard/drag calls. worker.rs validates the app before dispatch, then ordinary synthetic delivery uses those global operations. Removing ensure_foreground would allow the current focused application to receive another app's intended text or keys.

Add an app-scoped backend input seam that receives a host-resolved target from PreparedAction: application identity, current process identity, captured window/surface, selected element where available, current revision/turn and an input lifetime/cancellation token. The model supplies its existing handle/pixel target and requested action, not arbitrary PID/window IDs. Revalidate ownership immediately before delivery; a reused PID, closed window, changed surface or stale revision must not be silently retargeted. Target policy checks must use metadata proved to belong to that app/window; perform_session_action currently also samples globally focused window/URL facts and needs an ownership review before background delivery.

Keep target resolution strategy (semantic/pixel/auto) distinct from delivery policy (background required or foreground permitted). A proposed optional delivery policy and capability report must preserve current old-caller semantics, be mirrored in schema/plugin contracts, and never make an old host interpret an unknown background request as foreground input. The exact public shape should be finalized after P1 establishes what the backend can promise.

Prefer AX press/value/selection/menu actions when they express the requested action. SetValue replaces a field; TypeText inserts at the caret. They are different operations and must not be substituted in a way that deletes existing text or changes editor event semantics. Background key delivery must also prove the intended same-app window is the recipient; a process-level shortcut can otherwise act on a different key window.

Apple exposes [CGEvent.postToPid](<https://developer.apple.com/documentation/coregraphics/cgevent/posttopid(_:)>). The installed core-graphics 0.25.0 dependency already binds it as post_to_pid, guarded by the elcapitan feature; the current cargo feature graph enables default/link/highsierra, not elcapitan. A prototype can explicitly enable that existing feature. Enigo 0.6.1 has no target-PID setting, so changing an Enigo Settings value is not an existing route to background delivery. This establishes an extension point, not universal app compatibility.

Do not rely on undocumented event fields or private focus handshakes as an unstated production assumption. If public per-process posting plus verified AX state cannot establish the exact window/action, record unsupported delivery and evaluate an explicitly approved foreground action or a separately isolated desktop. A VM changes the task environment and does not operate the user's existing signed-in app session by itself.

For drag, post the entire button-down/move/button-up gesture to the validated target, maintain the screenshot-to-window coordinate transform, isolate modifier/button state and release on timeout, cancellation, permission loss and target death. Do not warp the physical pointer as a background implementation. Start with same-window dragging; crossing apps/windows requires its own proven contract.

### Screen-off mode is not background input or Locked Use

ADR-0242's virtual-display beta moves and activates the target application and requires an active unlocked console session. It protects its owned display geometry and checks the driven application still has keyboard focus. Reusing it does not prove that the human can keep using another app without interference, and it cannot unlock a Mac. Background requests must not enter its activation/migration path implicitly; an active screen-off lease needs an explicit compatibility/refusal rule.

### Locked Use requires a native trust and recovery boundary

Reuse the controller's signed lease, 30-second maximum, device/account/task/turn binding, app allow-list, cancellation and relock latch. Its current installation-receipt boolean, NativeSenderIdentity strings and AuthenticatedToolTurn values are policy inputs. The missing native code must derive these from real installation/code identity and current authenticated host state; accepting equivalent fields from renderer/model/MCP input would not establish trust.

| Missing production edge               | Required responsibility                                                                                                                                                                                                                                                                                                                       |
| ------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Host turn/lease issuer                | Derive active device/account/task/turn and both grants from authenticated Host authority; sign only an active eligible turn, bind target apps, cancel immediately on task end/revocation/disconnect. Ordinary remote-control authority alone does not enable Locked Use.                                                                      |
| Native helper and authenticated XPC   | Derive peer identity from OS audit/code identity, validate the expected signed installation and protocol in both directions, bound every request and keep private signing material outside renderer/model access.                                                                                                                             |
| Session guardian                      | In the user's GUI session, establish coverage of every display before temporary unlock, monitor coverage/topology and physical input, and trigger relock on loss or crash. Privileged authorization code must not host the GUI.                                                                                                               |
| Authorization Plug-in                 | Participate only in the explicitly scoped existing-session screen-unlock mechanism. Exact supported mechanism/OS behavior must be validated in a disposable environment; new-user login, FileVault preboot unlock and user switching are outside this feature's proposed scope.                                                               |
| Durable approvals and replay boundary | Store explicitly granted app/device approvals under Host ownership. The existing in-memory allow-list and nonce set are not durable installation/restart evidence. Add a proven service-instance/boot-epoch or equivalent replay boundary and version it; do not allow a restarted helper to accept a previously issued unlock lease blindly. |
| Installer, upgrade and uninstall      | Verify nested signatures/installation receipts, obtain the required system approval, update only owned mechanisms, preserve unrelated authorization entries, support interrupted-install recovery and restore normal manual unlock on disable/uninstall/failure.                                                                              |

Apple's [Authorization Plug-in guide](https://developer.apple.com/documentation/security/extending-authorization-services-with-plug-ins) separates privileged and GUI hosts and describes bundle/policy registration. [SMAppService registration](<https://developer.apple.com/documentation/servicemanagement/smappservice/register()>) manages helper registration subject to approval; it is not by itself the Authorization Plug-in installer. The guide's description of authorization APIs does not prove a supported automatic-unlock integration for every macOS version.

Only after these edges are accepted should capability availability move from the current dormant declaration to a truthful build/installation/health verdict and the device UI become actionable. Keep the type, UI, tests, IPC registration/ACL and actual enforcement point in the same completed change. Do not simply change LOCKED_USE_AVAILABLE to true.
