Build a first-party optional delivery plugin with a headless execution layer and a client UI layer. One installation selects one execution Host, including the local desktop runtime. Keep execution, authorization, durable queues, interrupts and trusted publication in their existing host owners; the plugin owns delivery policy, stage definitions and presentation. Reuse the existing Bot step journal and execution/delegation tree. Repair existing safety defects before enabling the new path. Ship only after the same acceptance contracts pass on desktop and an always-on Host, and existing work survives migration without duplicate dispatch or publication.

The user has selected plugin packaging and desktop/Host support. The recommendations below are proposed implementation decisions, not approval to implement or acceptance of unresolved risks.

## 3. One execution Host owns each delivery and its external effects

The plugin has one shared domain implementation and separate runtime/UI entry graphs. These are proposed source boundaries; manifest field names are frozen in P0 against the actual SDK.

| Boundary                  | Owner                                              | Responsibilities                                                                                                     | Consumers                                          |
| ------------------------- | -------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------- |
| Runtime infrastructure    | Existing kernel/runtime modules                    | Leases, durable step journal, admission, run tree, live controls, interrupts, authority and outbound brokers         | Delivery plugin and other features                 |
| Issue and project records | Existing Issues/workspace owners                   | Canonical records, definitions, transactional guards, run associations and activity                                  | Plugin, existing boards, tools, sync and workflows |
| Delivery policy and state | Delivery plugin                                    | Versioned templates, stage progress, policy choices, evidence requirements, feedback routing and acceptance profiles | Plugin UI and host handlers                        |
| Execution engines         | Existing AgentTask, Squad and agent/CLI owners     | Execute an attempt, expose capabilities, report typed outcomes and respond to controls                               | Public runtime APIs                                |
| Trusted publication       | Existing Git/integration/outbound owners           | Validate exact source/evidence, resolve credentials on the Host, reconcile provider effects                          | Plugin publication requests                        |
| Plugin UI                 | Delivery plugin UI entry                           | Setup, queue, detail timeline, attention inbox, policies and history                                                 | Desktop and paired browser/mobile                  |
| Vendor integrations       | Existing providers or declared plugin dependencies | Tracker/forge/CI/message transport and granted connections                                                           | Delivery handlers through public APIs              |

Proposed source ownership is `plugins/agentic-delivery/`, with pure domain code, host handlers and UI code separated. New plugin files are justified because an independently packaged author cannot import the current private Coordinator and Issue-run implementation. Existing generic services are extended in place. They are not copied into the plugin. Rust helpers remain in their lowest owning crate, including `crates/cognia-git`, and are reached through host capabilities.

One flow instance binds `accountId`, `workspaceId`, `issueProjectId?`, `issueId`, installation identity and execution Host identity. Configuration is scoped to the installation; a project override is explicit. No operation discovers its target from the currently selected UI workspace.

For this release, the execution Host is also the canonical data Host for the adopted delivery scope: its Issue/IssueProject, run tree, interrupts, receipts and plugin checkpoints are authoritative there. Paired clients read and submit commands to that Host; their cached/mirrored rows are read-only. Creating work on an always-on Host must not depend on a desktop's Dexie remaining reachable. An existing desktop-local Issue cannot simply be dispatched remotely under the same flow: first use the explicit adoption/transfer protocol, or keep execution local. Cross-Host compute delegation with a different live data authority is deferred as a separate capability.

| Mode                      | Execution owner                                                | UI behavior                                                       | Shutdown/reconnect                                                                                                                  |
| ------------------------- | -------------------------------------------------------------- | ----------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------- |
| Desktop local             | Desktop runtime, with one elected/registered owner per process | Local plugin UI uses the same public contracts                    | Closing a page does not end work while the runtime remains alive. Application exit stops execution; restart reconciles durable work |
| Always-on Host            | Selected remote Host and its Node/plugin runtime               | Desktop is a client; paired browser/mobile can inspect and answer | Desktop exit does not stop Host work. Host restart reconciles work before new dispatch                                              |
| Paired browser/mobile     | Selected desktop or always-on Host                             | Configure, observe, approve and submit intents                    | Offline commands remain visibly pending; no local fallback execution                                                                |
| Standalone browser/mobile | No full delivery execution owner                               | Explain missing Host and offer connection/setup                   | Preserve the existing lightweight standalone capabilities; do not advertise full delivery execution                                 |

Handover stops admission on the source, reaches a safe checkpoint or cancels and acknowledges children, reconciles external effects, then transfers checkpoint and workspace references with a new ownership epoch. The destination verifies capabilities, credentials and authority before admission. A source Host that cannot be fenced or contacted prevents handover. A plugin switch or connectivity change never silently transfers ownership.

The transfer is a journaled prepare → fence → import → activate → finalize protocol, not a transaction spanning two Hosts. Prepare enumerates the complete closure of scoped Issue/project/status definitions, run lineage, decisions, effect receipts, policy/template versions, plugin data and source event cursor. Shared records still serving active work outside the transfer scope force a larger workspace transfer or a typed refusal. Fence durably makes the source closure read-only before the destination can activate. Import validates a versioned manifest, IDs, digests and referential integrity and keeps the destination inert. Activation requires the source fencing receipt and advances the destination epoch; source finalization leaves read-only redirects and receipts. Neither side can unfreeze itself after a timeout without a recorded peer-abort/ownership resolution. Crash tests cover every boundary, including source recovery after destination activation.

Prepare is provisional. The fence operation atomically binds the final sealed closure manifest/digest, record revisions and committed event cursor to its fencing receipt under the source write barrier. Any accepted decision, status change or effect receipt since prepare must be re-exported or replayed into that sealed snapshot before activation. Destination activation refuses an import whose digest/revisions/cursor do not match the fence. After sealing, stale source mutations are refused; new ingress is durably queued/redirected as idempotent intents for the destination, without changing sealed source domain records. AC-18 includes a human decision and an external-effect confirmation accepted between prepare and fence, then verifies that both survive transfer exactly once.

Host-local worktree paths are never transferred as usable paths. Transfer a validated commit plus retained patch/artifact bytes, or a verified workspace bundle including required untracked files, then provision a new destination workspace and compare digests. Secrets and unsafe/unexportable local material block transfer until resolved. Credential grants, engine handles and live sessions do not migrate; establish new destination grants and create a new child attempt. P2 adds the necessary public data/transfer and workspace reconstruction capabilities rather than relying on the current local-Dexie Issue API.

## 4. Business status, stage progress and execution status have different authorities

| Axis                         | Authority and proposed representation                                                  | Customisation                                                                                                  |
| ---------------------------- | -------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------- |
| Issue business status        | Issues service resolves a stable status definition and maintains its semantic category | Project/workspace-scoped labels, order, colour and allowed transitions                                         |
| IssueProject business status | IssueProject service resolves its own definition and compatibility value               | Separate definitions; an explicit automation rule determines whether a project state blocks new work           |
| Delivery stage               | Plugin checkpoint identifies template version, stage ID, revision and stage evidence   | Declarative stages and transitions in versioned templates                                                      |
| Execution state              | Existing `ExecutionRun` and engine owners                                              | Reuse queued/running/waiting/paused/recovery_required/completed/failed/cancelled; expose typed waiting reasons |
| Automation control           | Persistent mandate/control record associated with the existing delegation root         | Active, paused, stopped or human-owned control semantics, independent of an attempt finishing                  |

The existing IssueRun enum remains a compatibility dispatch projection during migration. Waiting, paused and recovery detail comes from its linked execution record. No new execution enum is introduced by the plugin, and terminal engine runs are never resurrected.

Long-lived ownership uses an existing `delegation` execution root associated with the Issue. Trigger handling uses Bot runs/steps; actual engine attempts are linked into the same execution tree with one parent per node. Delivery metadata stores stage progress and references, not a second copy of `ExecutionRun.status`. P2 must prove that Bot-to-engine child linkage and run controls can be expressed publicly. A Bot handler itself remains non-steerable; steering targets its active child engine when that child supports it.

That reuse requires an explicit change to the current delegation completion rule: [`maybeSettleDelegation`](../../lib/execution/delegation-bridge.ts) can currently complete a root once its current children complete. WP2 adds a generic host-owned durable completion obligation to the existing execution owner. Create the obligation atomically with the root, before the first child; completing a short Bot/engine attempt cannot satisfy it. Only a version-checked receipt establishing the selected profile and reporter delivery/waiver closes the obligation. Missing plugin code or a crash between stages keeps it open and visible, never implicitly successful. Failed child attempts enter the existing retry/recovery path; a new attempt preserves the logical obligation and history.

The fixed topology is delegation root → Bot orchestration attempt → engine child attempt. Public launch/binding APIs derive the parent, acting identity and budget ceiling from the owning root; caller-supplied parent IDs alone grant nothing. Root stop cascades to descendants and waits for acknowledged stop or a visible unresolved-stop state. Stage completion, next-stage obligation and event/outbox advancement use one revision guard, so a restart between children cannot prematurely close the root. Existing non-plugin delegations retain their current completion policy unless explicitly opted into a durable obligation.

### 4.1 Custom statuses preserve old records and older readers

Propose stable definitions with an ID, scope, immutable key, localised display label, colour, order, semantic category and legacy projection. Issue definitions retain the existing four categories: `unstarted`, `started`, `completed`, `canceled`. IssueProject definitions preserve its existing six-value compatibility vocabulary. Labels never serve as IDs.

Add an optional stable definition reference to the wire/storage contract while retaining legacy `status` and Issue `statusCategory` during the compatibility window. One service resolves and writes them together. Existing six Issue values are seeded as default definitions. Old commands writing a legacy value resolve to the configured default definition for that value; ambiguous/unmapped inputs receive a typed refusal. New clients always send definition IDs. Sync providers map stable definitions/categories explicitly, and surface unrepresentable distinctions rather than inventing a remote value.

The core Issue owner owns the shared definition registry because existing boards, sync and tools use it without the delivery plugin. The plugin owns configurable delivery transition policy. Both are enforced at the service boundary. Uninstalling the plugin leaves status labels and historical Issue records readable.

Retiring a definition requires an explicit replacement for affected live records or leaves the definition read-only for historical use. Template and status changes are versioned. In-flight flows keep their pinned template; a deliberate upgrade creates a migration event and invalidates decisions whose inputs changed.

### 4.2 Transitions are executable rules with recorded refusals

Rules specify source/target, actor role, required fields, dependency conditions, evidence and approval requirements, automation eligibility and failure/rejection destinations. Use a bounded declarative condition vocabulary; no arbitrary script evaluation. Validate unreachable stages, missing exits, cycles without attempt limits and terminal stages without required evidence at template publication.

Every writer uses the same guard: UI, plugin, Agent, sync, workflow and bulk actions. A refusal returns a stable reason and actionable details. Manual exceptions require a separately authorized override and a reason in the audit trail. Reopening a completed or cancelled Issue is explicit and creates a new delivery cycle; late events from the previous cycle remain historical.

The plugin authors the policy; the host owns a versioned, validated declarative policy snapshot and its generic guard evaluation. The guard can verify durable evidence/decision receipts without running plugin code. When a referenced predicate/provider is unavailable, guarded advancement is refused while stop, inspection and export remain available. Disabling the plugin therefore cannot reopen an unguarded path to Done. This capability belongs to the shared transition/authorization owner, not a kernel branch naming this plugin.

## 5. A single flow covers intake, execution, revision and reporter delivery

Every step records its trigger/input revision, owning stage, operation receipt and evidence reference. Preconditions are checked before the first step that needs them: installation enabled, configured Host, workspace/repository binding, selected template, granted connections, available engine, budget and authorized actor.

| Step  | Actor and event                                               | Required behavior and visible result                                                                                                                               | Owner                                      | Acceptance          |
| ----- | ------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------ | ------------------- |
| HP-01 | Person, tracker event or support/incident source submits work | Create/link the scoped Issue and origin thread; deduplicate the source event; show the accepted reference                                                          | Issues + plugin intake                     | AC-03, AC-16        |
| HP-02 | Plugin checks readiness                                       | Validate context, acceptance criteria, dependencies, bindings, permissions, capacity and completion profile; missing information becomes an assigned clarification | Plugin + admission/interrupt services      | AC-06, AC-07, AC-15 |
| HP-03 | Agent proposes a plan                                         | Save plan revision, policy version, budget and evidence requirements; request a human decision when policy requires it                                             | Plugin + existing delegation/plan services | AC-07, AC-12        |
| HP-04 | Host accepts execution                                        | Claim once, bind delegation/IssueRun/engine/session/workspace references, then report running; cancellation during acceptance fences the returned attempt          | Issue-run + execution owners               | AC-04, AC-09        |
| HP-05 | Engine performs work                                          | Preserve the brief and human/PR feedback; checkpoint work and typed completion reason; cap attempts, cost and duration                                             | Engine + plugin handler                    | AC-10, AC-14        |
| HP-06 | Deterministic verifier checks candidate                       | Run required checks against trusted policy and exact source revision; persist readable results; failure returns to bounded revision or human recovery              | Verification/execution owners              | AC-12               |
| HP-07 | Host publishes a candidate/PR                                 | Recheck authority and evidence, then use trusted publication; reconcile an unknown result before retrying                                                          | Git/integration/outbound owners            | AC-11, AC-13        |
| HP-08 | CI/reviewer/person returns feedback                           | Append once to the same Issue and delivery, route to its owning thread, invalidate affected decisions and revise the same PR when applicable                       | Plugin + event/outbox services             | AC-04, AC-14        |
| HP-09 | Reviewer accepts or requests changes                          | Decide on immutable candidate/version; request changes returns to a named stage with feedback; acceptance reconciles linked task review/dependency semantics       | Review/Issue services                      | AC-08, AC-12        |
| HP-10 | Authorized actor merges/releases according to profile         | Record merge and, when required, release/rollout evidence for the exact candidate; missing release evidence remains visibly waiting                                | Plugin + granted integration               | AC-13, AC-17        |
| HP-11 | Plugin sends the outcome to the origin                        | Persist destination, content/version and delivery receipt; retry delivery safely; show pending feedback separately from accepted work                              | Outbound owner + plugin                    | AC-17               |

Completion profiles are explicit and pinned: `artifact-accepted`, `pr-reviewed`, `merged`, `released`. Each defines its terminal evidence. A coding product-delivery template proposes `released`; a PR-assistance template can end at `pr-reviewed`. Setup states the distinction. A required release integration can be replaced only by an authorized, version-bound manual release receipt. A successful Agent turn or a merged PR alone does not satisfy a released profile.

Business acceptance and reporter delivery have separate receipts. The Issue may display its accepted completion status once its selected profile is satisfied, with a visible pending-notification badge. The overall delivery cycle is successful only after the stored origin acknowledges delivery, or an authorized person records an explicit notification waiver. A transport failure never rolls back a valid acceptance or gets presented as successful reporter delivery.

## 6. HITL decisions survive clients, revisions and runtime restarts

Reuse durable execution interrupts and Bot waitpoints. Preserve the existing stronger Squad and Workflow semantics. A shared attention projection may aggregate them; it must retain the owning decision service and avoid a parallel approval table.

| Decision                  | Binding and options                                                                       | Re-entry behavior                                                                             |
| ------------------------- | ----------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------- |
| Clarification             | Issue/cycle, question revision, assigned person; answer, defer or stop                    | Revalidate HP-02 with the answer                                                              |
| Plan review               | Plan digest, policy version and authorized reviewers; approve, request revision or reject | Approved plan reaches HP-04; revision returns to HP-03; rejection ends or explicitly re-plans |
| Tool/publication approval | Exact action, target, payload/artifact digest, identity ceiling and expiry                | Execute only the bound action after a current authority check                                 |
| Deliverable acceptance    | Candidate digest, check evidence and reviewer; accept, request changes or reject          | Changes create a new candidate revision; stale acceptance cannot complete it                  |
| Human takeover            | Named owner, reason, worktree/artifact references and handback conditions                 | Agent admission pauses; explicit handback revalidates edits, authority and next stage         |
| Recovery                  | Failed step, known effects, restart safety and permitted actions                          | Resume a safe checkpoint, create a new attempt, reconcile, or terminate                       |

Persist the interrupt before exposing a card or callback. A decision submitted before an in-memory waiter attaches is still accepted exactly once. Duplicate clients observe the winning decision; stale/foreign decisions receive a typed refusal. Expiry never means approval, success or automatic resolution. Timeout behavior is explicit: remain blocked, escalate, or fail the stage according to policy. Human takeover may become overdue but never silently returns to an Agent.

HITL changes must be available in the desktop plugin UI and paired client attention view. Existing IM channels receive equivalent scoped actions through the same decision service. IM delivery failure leaves the durable attention item open. No online client is required to keep a waitpoint safe. Plugin unload/restart must not lose an interrupt or authorize an old candidate.

## 7. Public contracts expose capabilities without granting private host access

The following are proposed logical API additions. P0 freezes their exact catalog names and schemas; P2 implements and packs them before plugin extraction. Prefer extending an existing owning namespace over introducing a delivery-specific kernel API.

| Public contract                                   | Existing basis                                                  | Required addition                                                                                                            | Unique owner              |
| ------------------------------------------------- | --------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------- | ------------------------- |
| Scoped Issue/IssueProject actions and definitions | `ctx.issues`, shared Issue service, `ctx.project`               | Definition/version CRUD, transition preview/apply, project grouping and explicit scope checks                                | Issues owner              |
| Issue execution and lineage                       | `startIssueRun`, adapters, execution tree                       | Start/read/cancel and capability-checked steer; durable Issue ↔ delegation ↔ attempt ↔ session/thread links                  | Execution API owner       |
| Root completion and scope transfer                | Existing execution completion and selected-Host data boundaries | Durable completion obligations, derived parent/authority, fenced closure export/import and verified workspace reconstruction | Execution/data owner      |
| Durable event intake/replay                       | Issue committed events, Bot ingress/journal                     | Cursor-based catch-up, event IDs and resumable subscriptions for bridged clients                                             | Event/runtime owner       |
| Plan, review and takeover                         | Existing delegation, Squad review and interrupts                | Version-bound create/read/decide/handoff/handback operations; shared attention projection                                    | HITL owner                |
| Verification evidence                             | Existing Goal and Squad verification evidence                   | Run/read required deterministic checks bound to policy, source and environment revisions                                     | Verification owner        |
| Candidate publication and reconciliation          | Existing trusted Git publisher and integration broker           | Prepare/publish/read-back using scoped connection and operation receipt; host-neutral capability negotiation                 | Git/integration owner     |
| Policy checkpoints and plugin data                | Bot steps, plugin namespaced DB                                 | Transactional/CAS metadata writes, schema migration and read-only history when plugin unavailable                            | Plugin runtime/data owner |

Mutating requests carry a schema version, operation/idempotency key, account/workspace/resource identity, expected revision and execution ownership epoch. The host derives actor/grant identity from the authenticated invocation; a caller-provided actor never elevates authority. Responses distinguish accepted, refused, conflict, pending, recovery-required and external-outcome-unknown. Timestamps crossing the wire use epoch milliseconds; payloads are bounded JSON values, not closures, Date objects or AbortSignals.

Errors include unsupported capability, host unavailable, scope mismatch, stale revision/epoch, run already active, policy refusal, missing/expired approval, dependency unavailable, budget exhausted, interrupted execution and unknown provider outcome. Map existing error codes where available; new codes are registered once in the shared contract and localised by clients.

Required capability negotiation covers engine start/stop/steer, worktree operations, verification, publication, durable waits and event catch-up. Setup reports a missing prerequisite before arming the installation. A manifest flag alone is insufficient. The plugin's host graph imports no React, UI store or DOM-only API; UI dependencies load exclusively through its UI entry. Keep the static export compatible and use the existing Host transport, not Next.js server routes.

The SDK catalog, schemas, generated bindings and packed authoring kit change together. Declare minimum app/SDK/contract versions and test the packed plugin without repository aliases. Coordinate with ADR-0250's contract cutover: use the supported public contract at implementation time, migrate once if the cutover ships, and never introduce a second competing host/UI protocol. If public closure cannot be achieved, the extraction milestone is blocked until its named owner supplies that capability; shipping a private-import plugin is not an alternative.

## 8. Data ownership keeps history readable and state changes atomic

| Data                                      | Source of truth                                          | Proposed change                                                                                                  |
| ----------------------------------------- | -------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------- |
| Issue/IssueProject and status definitions | Existing core data owner                                 | Add stable definition references, definition/version storage and guarded transitions                             |
| Engine/root run state and controls        | Existing execution records                               | Add/repair lineage and control semantics through owning services; retain canonical statuses                      |
| Durable trigger/step/wait state           | Existing Bot queue/journal and interrupt owners          | Reuse leases, receipts, cancellation and wait resolution                                                         |
| Delivery metadata                         | Plugin-namespaced transactional tables                   | Template/version, stage revision, Issue/root references, evidence references, origin route and migration markers |
| External effect receipt                   | Existing integration/outbound journal, extended in place | Intent, provider target, operation key, prepared/submitted/confirmed/unknown result and read-back facts          |
| Artifacts and retained workspaces         | Existing artifact/task-workspace owner                   | Exact revisions, policy-bound evidence and retention leases through recovery                                     |

No plugin-local localStorage or unjournaled timer is authoritative. Keep metadata bounded and index actual queries: workspace/project and stage, Issue/cycle uniqueness, root run, waiting owner, next due work, and external operation key. Use the existing queue indexes rather than adding a second scheduler.

Host-owned commands atomically guard and update the Issue plus run association and append committed events/outbox intents. A plugin cannot perform arbitrary writes to core tables. When plugin metadata and core state cannot share a transaction, use expected revisions and idempotent receipts: the core commit is authoritative, event consumption advances the plugin checkpoint, and restart reconciles missing checkpoint progress. Never claim distributed atomicity between separate stores or between a database and GitHub.

Schema allocation follows `dexie-migration` at implementation time; no version number is reserved by this plan. Migrations are monotonic, restartable and bounded in batches. Backup/export includes template version, definitions, lineage, pending decisions, receipt references and plugin metadata schema version. Import restores history inertly until Host bindings and authority are re-established. Cross-account or foreign-workspace references are rejected.

## 9. Exceptions have a visible owner and a safe recovery path

| Branch | From        | Condition                                                                      | Required outcome and recovery                                                                                                          |
| ------ | ----------- | ------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------- |
| BR-01  | HP-01/02    | Duplicate event, incomplete context or unbound repository                      | Deduplicate or park for assigned clarification; never dispatch speculatively                                                           |
| BR-02  | HP-02/04    | Project paused/completed/cancelled or automation stopped                       | Refuse new derived work; resuming requires explicit valid control/eligibility                                                          |
| BR-03  | HP-04       | Cancel or delete while engine acceptance is pending                            | Persist stop/tombstone first; cancel the late returned child; retain tracker until acknowledged                                        |
| BR-04  | HP-04/05    | Repeated poll errors, missing engine, lost heartbeat or Host crash             | Record typed attention state, reconcile liveness/effects and require safe continuation; no permanent false Running                     |
| BR-05  | HP-05       | Max-turn, budget, invalid output or runtime error                              | Record incomplete/failed attempt; do not publish; bounded retry or human recovery                                                      |
| BR-06  | HP-05/06    | Workspace cleanup races failed push or restart                                 | Retain recoverable workspace/checkpoint until export, completion or explicit expiry; validate before reuse                             |

Repair limits are lifetime counters scoped to delivery cycle and PR, not process-local cooldowns. Propose two automatic CI/conflict repair attempts and three review repair attempts, configurable downward or upward only through an authorized versioned policy change. These are proposed defaults, not measured current guarantees. Keep the existing feedback cooldown/hourly cap as additional limits. Provider transport retries are separately bounded and never consume or reset business repair accounting.

Admission composes Host resource capacity, workspace/project limits, per-stage limits, dependencies, automation control and cost/time reservations. A person's stop/takeover bypasses automated admission. Expose the binding constraint in the queue. P0 records actual engine heartbeat/poll semantics and fixes numerical stall, wait and retry defaults per template before enablement. A healthy long-running process is not failed merely because it has produced no chat message.

## 10. Authority and evidence are rechecked at every effect boundary

Reuse granted connections and current acting-identity/run-authority owners. Persist a versioned mandate with scope, allowed effects, budget, reviewer requirements, origin/return route and expiry/revocation behavior. Check current authority at dispatch, resume, steering and publication; a prior approval cannot elevate the current ceiling.

PR comments, Issue text, incident reports and repository files are untrusted inputs. They cannot change trusted verification rules, grant new tools, authorize another workspace, or redirect a stored reporter route. Resolve trusted policy from the selected trusted revision and record its digest. Agent-authored changes to policy require a separate authorized policy change before they can govern publication.

Every outbound model, embedding and cloud-text call continues through the existing PII gate and outbound broker. Credentials stay with the selected Host; no raw token enters plugin configuration, checkpoint, prompt, browser payload or logs. Scope file access to the managed workspace, reject traversal/symlink escape, and keep Agent-written `.git` state outside trusted publication. Native operations are generic Host capabilities with narrow command registration/ACL, never privileged plugin Rust code.

External publication is an explicit authorized stage. Automated PR creation, merge and release require their own grants; enabling the plugin grants none of them implicitly. An incident import records source provenance and access constraints. Redacted evidence is still required to be authentic and sufficient; demo SRE fixtures cannot be labelled live evidence.

## 11. Plugin lifecycle and migration are part of the feature

### 11.1 Lifecycle behavior

| Operation     | Required behavior                                                                                                                                             |
| ------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Install       | Validate signature/version and required capabilities; create an unarmed installation; select Host, scope, template, grants and completion profile             |
| Enable        | Reconcile checkpoints and unknown effects first; arm triggers only after readiness succeeds                                                                   |
| Disable       | Stop new intake/dispatch, checkpoint work, retain interrupts and history; policy explicitly chooses acknowledged stop or drain of already authorized children |
| Upgrade       | Stop admission, pin/drain old-version work or apply an explicit checkpoint migration, then swap; unsupported checkpoints remain in recovery                   |
| Uninstall     | Block while effects/children are unacknowledged; offer authorized stop/drain and export/archive; keep core Issue/run/artifact history readable                |
| Purge         | Separate explicit data deletion with resource impact and retention policy; never imply an external PR/release was deleted                                     |
| Host handover | Use the fenced protocol from section 3; credentials and publication grants are re-established at the destination                                              |

Core run controls and the attention view must remain usable when plugin code is disabled or unavailable. Before uninstall can remove plugin-owned tables, archive the necessary stage/evidence/decision metadata through a host-owned versioned export envelope. Generic retention honors pending work/recovery leases. Core status definitions are preserved. Reinstall can restore an archive without rearming execution.

This requires extending the existing Host-owned provider-drain/quiesce boundary in [`PluginManager`](../../lib/plugin/core/manager.ts) to cover active delivery handlers, children, decision and effect obligations. Current `onDisable`/`onUninstall` hooks are log-only notifications and cannot provide the gate; disable unloads code/revokes grants, and uninstall removes provider connections. A normal prepare-disable/upgrade/uninstall must checkpoint/archive or acknowledge bounded drain **before** those actions. A timeout reports an unresolved lifecycle operation and offers emergency stop; it never reports successful drain.

The first release does not keep two handler versions resident. Upgrade quiesces the old handler before unload; persisted pinned versions are checkpoint metadata, not a promise that old code can keep executing. New code resumes only checkpoints it explicitly supports/migrates; otherwise retain a rollback package and show recovery-required. Bounded drain may finish an already running safe step while old code and its still-valid authority are present; it cannot wait indefinitely on a human approval.

Emergency disable always revokes plugin authority promptly and uses Host-owned child-stop/control paths. It never lets a plugin veto revocation. The Host preserves unresolved children, external effects and decision records in its archive/attention projection for later reconciliation without plugin code. Normal uninstall/purge waits for those obligations; a forced removal preserves the archive/tombstone and cannot claim resource cleanup succeeded. Extend this pre-teardown gate once for all owning lifecycles rather than adding business-specific hook exceptions.

### 11.2 Ordered migration and rollback

1. **Expand:** seed status definitions and optional references; add lineage and receipts; leave existing reads/writes working. Validate backup and restore first.
2. **Backfill:** fill deterministic links/status references in bounded batches, with a resumable cursor and provenance. Ambiguous Issue ↔ thread or PR links require review; no title-based guess. Historical approvals remain historical facts, not new authorization.
3. **Shadow:** the plugin reads events and computes proposals without dispatch, writes or publication. Compare state/attention/lineage with existing owners.
4. **Adopt:** introduce one persisted automation-owner fence for each adopted Issue/cycle. Legacy automation stops admitting that work before plugin execution is enabled. Existing active attempts drain or are explicitly attached at a safe checkpoint.
5. **Canary:** enable selected workspaces on each host type with explicit permission. Run real acceptance and rollback drills; inspect events and receipts.
6. **Cut over:** enable validated scopes, keep compatibility projections for supported old clients and finish backfill. Remove legacy delivery watchers/actions only after the consumer inventory reaches zero.
7. **Retire compatibility:** a separate release after the supported-version window and restore drill. No destructive removal in the first plugin release.

Rollback disables plugin admission and publication, retains its checkpoints/receipts, reconciles accepted external writes and returns control only through the ownership fence. Reuse a legacy executor only if it understands the current state and does not bypass new guards. Otherwise keep history readable and work paused pending a forward fix. Do not downgrade a database schema or rewrite custom statuses into lossy old values. Old clients that cannot safely edit the new state receive a read-only/upgrade-required result.
