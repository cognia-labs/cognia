# DSH plugin compatibility in Cognia — 2026-11-02

Inspection began on 2026-11-01 and completed on 2026-11-02 (Asia/Shanghai). Cache paths retain the inspection-start date.

Request: “帮我评估一下这些插件在 Cognia 当前 DSH 接入里的兼容性，看看哪些能直接用，哪些还需要补支持。都列举一下”

## Result and scope

**None of the named original DSH packages can be installed unchanged into Cognia's current managed DSH runtime.** This is an intentional host boundary, not a finding that every upstream plugin is broken.

This assessment covers all 24 community projects named in the preceding two answers. DeepSeek Design contains three independently installable packages, so there are 26 community package entries. It also covers the six official capability groups previously named and adds Custom plugin indexes explicitly. Browser Use has three provider manifests: together this is **35 inspected package declarations**, presented below as 26 community package rows and seven official groups.

The baseline is Cognia's managed **DSH 0.2.1-rc.2, conformance suite 6**, with SDK readonly, SDK workspace and ACP profiles. Current source was read from the shared worktree, including the prior DSH repair. The recorded head is `dd6e08bb1a3f91638d612810280bca156a32a33e`; uncommitted file contents, rather than HEAD alone, are the authority. SHA-256 hashes of 16 relevant local sources are in `.cache/dsh-plugin-compatibility-20261101/source-snapshot.json`.

Only this report, an assessment pointer in the existing evidence ledger, and task-local cache evidence are written by this assessment. No plugin is installed, no product source is changed, no credentials are read, and no provider, browser, IM or external application action is run.

## What “usable” means

- **Original package directly usable**: installing/selecting the original plugin makes its declared behavior available in the existing Cognia DSH chat and permission/UI model, without changing the managed composition. Count: **0**.
- **Existing Cognia alternative**: Cognia has selected tool/instruction/UI facilities that can serve part of the same need. They are not the named DSH plugin.
- **Tool-only bridge**: the existing MCP port can carry a separately installed and authorized MCP server's tools. A CLI needs a governed tool adapter/configuration. This does not provide Cordis services, automatic lifecycle hooks or a DSH frontend.
- **Native integration needed**: an approved, pinned plugin bundle and its services must be added to a newly certified composition; some plugins also need substantial Cognia UI and protocol work.
- **Declared compatibility**: a version-range check only. It does not establish dependency completeness, API behavior, active services, sandbox access, UI integration or end-to-end success.

Existing Cognia alternatives require the corresponding Cognia plugin/tool to be available, enabled and selected for the conversation. The assessment confirms source wiring and focused contract checks, not that every user's device already has these plugins installed and accepted.

Its [README](https://github.com/yjh051108/dsh-routing-suite/blob/main/README.md) still targets `>=0.1.0-rc.6 <0.2.0`; this disagreement requires component/preset testing. ## Practical reuse today

No unchanged original plugin is green. The following existing routes can be used or configured without implementing a generic native DSH plugin platform:

1. Enable/select Cognia Browser, Computer Use or Web tools and let the existing Cognia broker project those tools into DSH. This substitutes Cognia functionality, not BrowserSkill or the official DSH providers.
2. Enable/select Cognia Office, Presentations or Visualize tools for the supported workbook/deck/visualization operations and Cognia result cards. It does not provide the full Univer or DSH GenUI feature set.
3. Supply selected skill instructions through Cognia's completed instruction pipeline. This is prompt instruction reuse, not DSH Skills Manager or native skill discovery.
4. Configure an authorized, independently prepared standard MCP server for a new session. Playwright/Chrome DevTools tools can use this route; external server installation, connectivity and permissions still need validation.
5. OpenViking's tool subset can use its documented stdio proxy after preparation and explicit connection/actor settings. Its [README](https://github.com/volcengine/OpenViking/blob/main/examples/dsh-memory-plugin/README.md#how-the-tool-surface-is-mounted) explains why pointing the DSH client directly at `/mcp` can hang `tools/list`; automatic recall/capture is separate.
6. Browser-supported Cognia dictation produces text for the normal DSH send path. [The voice control](../../components/chat/composer/voice-controls.tsx) does not supply a general local SenseVoice backend; support depends on the browser/platform.

None of those alternatives was exercised against a real plugin service, browser, Office artifact, IM bot or authenticated provider during this audit.

## Suggested support order

1. **Use existing Cognia tools and MCP first.** Validate the desired subset against a real DSH session; prepare narrow configurations for OpenViking tools and standalone browser MCP where needed. ModLens/ModSearch/Blender CLI capabilities need explicit adapters, not just a label in a settings page.
2. **Add a small pinned native allowlist if backend hooks are required.** Start with one measured use case, such as dsh-ops on the minimal profile, native ModLens, or a specific compaction/recall integration. Extend the installer/channel and verify readonly/workspace/ACP separately. Keep code protected and state writable.
3. **Build typed Cognia projections for useful interfaces.** Context metrics, generated UI and Office artifacts should use Cognia's UI/tool-result/artifact contracts. Running an isolated full DSH Web app would be a separate product surface, not proof of compatibility inside the current chat.
4. **Treat orchestration and ingress as larger work.** AgentTeams, Worktree, Ralph, Mimir/ClearAI and IM connectors need explicit session/child ownership, cancellation, model budget, persistence/recovery and authorization tests. Current same-boot maintenance quarantine is not generic descendant reaping.
5. **Defer known conflicting inputs.** Repair the three Design package ranges/APIs, resolve Routing Suite's component/version disagreement, and determine a compatible CUA artifact before promising those native packages.
