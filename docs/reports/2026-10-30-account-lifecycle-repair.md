This implements the confirmed P1/P2 findings F1, F2, F3, F5, F6 and F8 from the [adversarial review](2026-10-30-account-adversarial-review.md). Follow-up adversarial cases found during repair are included: failed storage writes must not publish identity metadata; a rejected login must not discard the current Person's successfully rotated refresh; social identity and Feishu principal operations must stay in the captured database and roll back on a profile switch; native host mirroring must target the initiating unlocked profile, generation and committed authentication revision. Organization selection, claim and invitation settlement carry the captured profile lifetime through their continuations.

The host publication guard uses a dedicated auth fence shared with conditional credential batches. It releases the secret-store read lock before synchronous host work. This closes the native revision race while preserving the existing receipt path's connection→secret lock order. Both stale bind and stale unbind are covered in the composed default flow, and the native concurrency test exercises receipt secret I/O while host publication waits for a connection.

## Data compatibility

No account database/table/index/version migration, vault re-encryption, account recreation, or profile deletion is introduced. `signedOutAt` is an optional non-indexed field in the existing registry row; old bindings remain active as before. Logout retains the owner, canonical aliases and local content. The small new `cognia-logto-session-locks` IndexedDB database contains empty lock stores, not accounts or tokens. Existing secret key names remain valid; the new auth revision is opaque, non-secret metadata. Existing native command names and capability entries are reused, and new native arguments are optional.

The new `session-lock.ts` separates cross-window Web Locks/IndexedDB coordination from the existing OIDC state machine. The new auth and idle integration suites are separate from the existing unit suites because they compose the real storage/identity modules and the real account store respectively, with isolated external boundaries.

The native guarantee concerns the canonical encrypted secret store. Pre-existing legacy OS-keyring cleanup is best-effort and its read suppression is process-local; repeated legacy deletion failures across a restart have not been accepted by this task.
