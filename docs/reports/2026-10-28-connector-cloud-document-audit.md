## Confirmed defects and concrete integration gaps

These are the pre-repair findings and suggested priorities from the research stage. F1-F6 now have local repairs and regression evidence; see the dated repair section below for the current status and remaining acceptance limits.

### F1 — Same-adapter Feishu reauthorization does not invalidate old document selections (P1)

`lark/index.ts:66-77` returns only adapter id and label, with neither `authorizationEpoch` nor `subscribeAccounts`. `accountMatchesBinding` compares id + epoch, so changing connected user A → B under the same adapter leaves an old binding valid. The OAuth handler updates tokens and `connectedUser` under that adapter; it does not change the document account id. Search/staging rechecks account membership, but cannot distinguish these authorizations.

**Probe:** current provider `listAccounts`, `bindRemoteDocRef` and `accountMatchesBinding` loaded with a synthetic DB row: A and B have different `openId` and label but the old binding still matches. This proves the missing document-binding identity fence; it does not execute the production OAuth owner or prove a live cross-account disclosure or bypass of provider ACLs. Existing different-adapter rejection and session-generation guards still work.

**Reuse / acceptance:** add an authoritative non-secret authorization generation and change notification to the existing Lark credential owner; carry it through the existing binding and staging contract. Test A → B under one id, disconnect/reconnect, in-flight refresh, bot fallback, two windows and ordinary same-user refresh. Do not add a second Lark login.

### F2 — Wiki-hosted Sheets and Bitable bypass the existing grid readers (P2)

The Lark provider routes every `kind: wiki` to `fetchLarkDocAsRawSource`. That fetcher resolves the node then explicitly rejects any `obj_type` except `docx` / `doc` (`lark-doc-fetcher.ts:194-205`). Direct `/sheets/` and `/base/` links already use functioning reader implementations.

**Probe:** both `obj_type: sheet` and `bitable` produce `DocsProviderError("unsupportedType")` after the link is recognized. The existing fetcher test already pins the sheet rejection; it is an intentional narrow contract in Twin, not evidence that the broader cloud picker is complete. Feishu's [Bitable API documentation](https://open.feishu.cn/document/server-docs/docs/bitable-v1/app-table-record/create) explicitly describes resolving Wiki-hosted Bitable through `obj_type` / `obj_token`.

**Reuse / acceptance:** resolve Wiki resource type in the cloud provider's orchestration and dispatch to the existing grid readers. Keep the Twin fetcher's document-only return contract unless deliberately extending it. Cover docx, doc, sheet, bitable, unknown type, missing token and permission errors; preserve the original Wiki citation and resolved title.

### F3 — Feishu reads ignore the provider cancellation signal (P2)

Search and fetch accept `DocsProviderCallOptions.signal` but do not read or pass it. Separate inspection of the production shared authenticated harness confirms it also has no signal option. In the provider-boundary probe, an already-aborted fetch still enters a **replacement authenticated harness** and returns fixture content. That probe does not execute production auth, retries or native I/O. UI hook cleanup prevents a superseded result from staging in the tested account/session cases; this finding is wasted work / latency / quota, not proof that every cancelled response is attached.

**Reuse / acceptance:** extend the current harness/transport contract, check cancellation before acquiring identity and between multi-tab/table calls, and reuse the existing abort primitives where their contract fits. Test zero calls for pre-abort, cancellation between tabs and safe handling of shared token refresh. Google already blocks pre-dispatch abort and releases its caller; its dispatched native `connectors_http_request` still runs until timeout. Do not describe Google's old ignored-signal bug as unfixed.

### F4 — An empty grid can become a successful attachment containing only a heading (P3)

Both spreadsheet readers render `## <tab title>` even when the values array is absent/empty. Their provider checks use `text.trim()`, so the heading satisfies the nonempty check. The shared normalizer also accepts it. The existing provider-level empty-grid unit test returns an empty string from a mock and therefore does not exercise this reader-to-provider boundary.

**Probe:** an empty visible tab renders `"## Empty tab\n"` for both providers, without a truncation flag. This is locally deterministic; whether an intentionally blank grid should be attachable is a product decision.

**Reuse / acceptance:** define empty-content behavior once at the existing reader/content boundary, using actual cells rather than rendered headings. Test blank tabs, whitespace-only cells, zero, false, headers-only tables, hidden-only workbooks and partially empty multi-tab workbooks. Avoid treating a legitimate zero/false cell as empty.

### F5 — Existing Feishu settings do not provide document-specific authorization readiness (P2)

The settings OAuth button calls `beginLarkOAuth({adapterId, redirectUri})` without `extraScopes`. Its default is `offline_access im:message im:message.send_as_user`, while document search needs a user identity with the relevant document scope. `DocsProvidersCard` and `listAccounts` count enabled adapter rows, not document scopes or usable credentials. An enabled bot or an IM-only user grant is therefore not evidence of search readiness.

This is a source-confirmed onboarding gap, not a claim that every connected tenant currently fails: previously granted app/user scopes, bot access and manually initiated `extraScopes` can differ.

**Reuse / acceptance:** reuse `beginLarkOAuth.extraScopes`, stored `connectedScopes`, the existing scope audit and connection deep link for explicit feature-specific incremental authorization and readiness. Distinguish direct-link bot reading from user search. Do not silently request write scopes for read-only attachments.

### F6 — Output text caps do not bound the current readers' response-body transfer (P2)

`MAX_DOC_CHARS` clamps strings after retrieval. Google HTTP uses `connectorsHttpRequest`; the native owner ultimately collects `resp.text()` in `crates/cognia-net/src/http_client.rs:251-254`. No per-document byte limit is carried by this reader path. Bitable field payload size also varies even with a record-count cap. The strict byte-limited P0 proxy is a different command and is not evidence that these existing text readers are bounded by it.

This is a source-level resource-budget gap; no large-body live or memory-exhaustion test was run. Google's [Drive export contract](https://developers.google.com/workspace/drive/api/reference/rest/v3/files/export) separately imposes a 10 MB export limit; that does not replace a local transfer budget for every metadata/values/Feishu call.

**Reuse / acceptance:** add bounded response collection to the existing owning HTTP layer or deliberately use its existing bounded byte primitive with an explicit provider policy. Test declared/streamed overflow and cancellation without changing unrelated IM response behavior.

## Capability extensions and fidelity limits

### E1 — Google Slides is feasible within the existing provider; the exclusion rationale is stale

`google/index.ts:83-85` says Slides has no useful text read; `url.ts` and search MIME filters exclude it. Google's current [export format table](https://developers.google.com/workspace/drive/api/guides/ref-export-formats) lists presentation plain-text export, and [presentations.get](https://developers.google.com/workspace/slides/api/reference/rest/v1/presentations/get) exposes the presentation structure. Its accepted scopes include `drive.readonly`, already requested here.

The smallest extension is a presentation resource in the existing Google provider, search MIME filter and URL parser, reusing Drive export for text. Use structured Slides reads only if slide/table/notes ordering is required. `RemoteDocKind` already includes `resource`; evaluate `sourceType` before inventing another provider or widening the public kind union. The current canonical URL helper assumes every non-sheet kind is a document, so it must be extended too. API availability is verified from documentation; actual export fidelity, enabled APIs and provider acceptance need a test deck. No claim is made about Feishu Slides API availability.

### E2 — Spreadsheet attachment content is a bounded display snapshot

Google `batchGet` does not request `valueRenderOption`, whose official default is formatted values. Thus it does not provide a formula-preserving or locale-independent workbook representation. See [batchGet](https://developers.google.com/workspace/sheets/api/reference/rest/v4/spreadsheets.values/batchGet). Feishu grids likewise render API-returned values rather than a structured workbook; Bitable descriptors are JSON-encoded, not fetched attachments.

There is no picker-level selection of tab/range/table/view and no pagination continuation. Google search uses `name contains`, asks for one page, and omits pagination/incomplete-search metadata; it is not full-text workspace search. Deep links such as Sheets `gid` / range and Bitable table/view query parameters do not narrow the fetched snapshot. These are extension limits, not a reason to replace existing readers or remove their protective caps.

### E3 — Semantic completeness is weaker than the shared contract permits

The shared type supports semantic `partial` reasons and the normalizer/UI already warn on them. Current Lark/Google readers mostly supply legacy `truncated`; a small Lark raw-text response normalizes to `complete`. That demonstrates absence of a semantic-loss signal, not proof that a particular provider response dropped a particular block. Rich documents, embedded tables/media and multi-tab Google Docs need fixtures and real-provider comparison before any full-fidelity claim. Reuse `RemoteDocContent.completeness` and the current UI instead of creating another quality-warning system.

Google `config.ts:23-38` also describes a structured Docs fallback and three scopes as necessary. Current fallback is a second Drive export, not a call to `docs.googleapis.com`. Both [Drive export](https://developers.google.com/workspace/drive/api/reference/rest/v3/files/export) and [Sheets batchGet](https://developers.google.com/workspace/sheets/api/reference/rest/v4/spreadsheets.values/batchGet) accept `drive.readonly`; the additional Docs/Sheets scopes are not required by these current endpoints. Reconcile comments and intended structured-read scope before changing consent; removing those extra scope strings would not make the remaining broad Drive grant file-selective.

### E4 — Multi-account, cross-shell and additional-provider work remains incremental

Google exposes one `default` account. Lark supports multiple adapter instances but its URL parser accepts international Lark domains while authenticated reads use fixed `open.feishu.cn`; international-account support is not established by URL recognition. Region-aware auth/API routing would need to extend the shared Lark owner, not create a second document stack.

The host reach resolver explicitly reports that companions lack a route to the document reader. A future relay should reuse existing selected-host transport and credential ownership, with account binding, cancellation, capability negotiation and PII boundaries verified. A messaging attachment route does not itself implement cloud-document retrieval. Google write tools, broad cloud-file parsing and Notion/Microsoft providers remain separate future scope.
