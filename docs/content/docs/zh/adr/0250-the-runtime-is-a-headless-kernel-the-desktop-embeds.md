# ADR 0250 — 运行时是桌面内嵌的无头内核

**状态：** 提议中
**日期：** 2026-11-01
**相关：** [ADR-0059](./0059-cloud-deployment-headless-brain)（无头 brain 与注册表规则）、[ADR-0224](./0224-an-always-on-host-is-a-peer-the-user-brings)（常驻 Host）、[ADR-0090](./0090-unified-agent-execution-and-gateway-compatibility)（统一执行）、[ADR-0137](./0137-delegation-runtime)（delegation）、[ADR-0239](./0239-an-outbound-action-is-authorized-by-the-request)（外发授权）、[ADR-0247](./0247-long-lived-work-carries-a-mandate-and-follows-its-threads)、[ADR-0248](./0248-a-person-is-never-queued-behind-automated-work)、[ADR-0249](./0249-a-background-jobs-completion-reaches-the-agent)。证据：`docs/research/architecture-convergence-audit-2026-11-01.md`。计划：`docs/plans/2026-11-01-convergence-phase-0.md`。

## 背景

2026-11-01 的架构审计，把一段时间以来的直观感受量化了出来：桌面是一个顺带承担产品运行的 React 应用；常驻 Host 是把同一套前端代码无头化运行，旁边再补一张注册表。主要数字如下。

**运行时长在 UI 里。**

- 105 个 provider 初始化器中，75 个拥有运行时行为，其中只有 29 个在无头侧有对应。
- 其余 46 个没有对应：14 个有文档说明，**32 个没有任何记录**。
- 聊天回合编排写在一个 7299 行的 React hook 里（`hooks/chat/use-claude-chat-controller.ts`），无头侧没有对应，CLI 只好自己重写了 steer 和后台结果处理。
- 294 个 `lib/` 文件命令式地读写 Zustand UI store。
- 有好几种行为以"会话下次打开时"为前提：后台结果要等那时才送达；自动归档靠读聊天 store 来豁免，而 brain 上这个 store 是空的。

**两个宿主在漂移。**

- `check-host-parity` 登记了 183 项差异，65 个子系统被归为"尚未迁移"，其中包括 `lib/agent`、`lib/ai`、`lib/chat`、`lib/claude`。这个门禁当前因 27 个未分类的子系统而失败。
- `check-headless-registry` 通过了，却漏掉了不少缺口，因为它只按命名（`install*`、`start*`、`register*`）识别运行时副作用。

**每个功能都在重造同一套机制。**

- Dexie 有 383 张表。
- 约 23 种运行或任务记录，"成功"有四种写法。
- 约 17 个持久化队列，至少五条退避曲线；旁边有一套共享的重试策略，但很少有队列在用。
- 约 22 个互不感知的并发限流器。
- 约 15 套去重机制，其中几套是非唯一索引上的"先查后写"。

**关口只是约定。**

- 没有门禁枚举外发规划器的调用方。
- 投递网关的静态测试只认一种 import 写法，而且只扫五个目录。
- PII 门禁检查的是 import，而不是调用。
- `observeActingAuthority` 按约定只做审计。
- "唯一写入者"规则大多只写在注释里。

**一个已确认的缺陷说明了代价。** router-fusion 的 outbox 对失败的效果无限重试，既不退避也没有上限；积压的毒行一旦超过 500 条，所有更新的效果都会被饿死。

这些问题都不是零件质量差造成的。很多零件做得很细致，门禁也都在。根子在于组装方式，以及功能增长快于收敛。

解决问题所需的注册表其实已经存在。`lib/headless/types.ts` 写明了设计意图："provider 在桌面上变成薄包装，`bootstrapHeadlessRuntimes()` 在 Node 里启动同一份代码"。但只有 brain 从它启动，桌面从来没有。所以注册表只是一个移植的目的地，不是事实来源。

## 决策

### 1. 一个内核，所有宿主都启动它

- **内核**指 Cognia 所有长期运行的行为：调度器、投递运行器、恢复、连接器、Bot、同步、聊天回合编排、steer、后台结果、wakeup、监视器。
- **它放在 `lib/` 里**，以 `HeadlessRuntime` 条目注册到 `lib/headless/registry.ts`。注册表路径不变，在 `"brain"`、`"person-brain"` 之外新增一个宿主 `"desktop"`。
- **桌面从注册表启动。** 桌面通过一个 provider 启动内核：用 Tauri bridge 调用 `bootstrapHeadlessRuntimes({ host: "desktop", bridge })`。
- **初始化器只保留什么。** 拥有运行时的 provider 初始化器被注册表条目替代。初始化器只保留真正绑定渲染进程的工作，例如窗口显示、webview 租约、PWA 角标。每一项都要在排除文件里写明物理上的原因。
- **宿主差异用能力表达，不用分支。** 运行时通过 bridge 或能力对象询问宿主能做什么，不通过 `isTauri()` 或读 UI 状态来决定。确实无法在某个宿主上运行的运行时，在自己的条目里声明；一致性门禁读取这个声明。
- **移动端和配对客户端是宿主内核的客户端**，不是独立的宿主。

### 2. 内核规则

- **不依赖 React。** 内核代码不从 `@/components/`、`@/hooks/` 导入任何东西，也不导入 React。
- **不根据 UI store 做决策。** 内核需要的状态放在内核自己的状态、Dexie 或宿主存储里，UI store 订阅它。内核代码导入 `@/stores/` 只允许出现在"UI 观察内核"这个方向，不能反过来，并用棘轮压到零。
- **不存在"下次打开时"。** 必须发生的行为，在触发条件出现时就发生。有没有人在看，只影响怎么展示。
- **只有一个聊天引擎。** 聊天回合编排（发送、steer、审批、停止、后台结果送达）是一个内核模块 `lib/runtime/chat-engine/`。桌面 hook、brain 和 TUI 都驱动它，现有的重复实现直接删除，不保留。

### 3. 四个共享原语

1. **持久化队列。** 一个模块，提供：
   - 租约与认领；
   - 到期时间；
   - 重试，复用现有的 `decideNextAttempt` 策略（`packages/plugin-contract/src/lib/queue/retry-policy.ts`）；
   - 死信状态；
   - **唯一**的幂等键；
   - 每个队列可配的并发数；
   - 一个检查视图。

   所有持久化队列都迁到它上面。
2. **限流器。** 一个区分来源的限流器（ADR-0248）：许可数、为人预留的许可、两档队列，停止永不排队。每个并发上限都变成它的一个实例，各自设上限值。
3. **运行台账。** `executionRuns` 是唯一的运行记录。各引擎自己的表只保存引擎细节，并指向对应的运行。状态词汇以台账为准，成功状态是 `completed`，其他写法只在边界处做投影。
4. **承诺。** 长期工作是一个会被提升为 Issue 的 delegation（ADR-0247），所有入口的工作都落在这里。

新功能需要队列、限流、运行或承诺时，一律使用这四个原语。另起一套实现会被门禁拦下（§5）。

### 4. 门禁能枚举的关口

以下几类动作，每一类都只能经由一个模块：

- 外发审查规划（ADR-0239）；
- 连接器投递；
- 网络出口；
- 调用模型前的 PII 脱敏；
- 恢复执行时的权限检查。

对应的门禁要遍历源码、列出每个调用点，而不是只检查某个 import 存不存在。只有门禁证明覆盖完整之后，shadow 模式才按类别切到 enforce（ADR-0239、ADR-0247 §7）。

### 5. 棘轮

`scripts/gates/check-convergence.mjs` 记录基线，任何计数上升就失败。每个阶段降低自己负责的计数，并用 `:baseline` 锁定。

| 指标 | 基线（2026-11-01） |
| --- | --- |
| 拥有运行时、却既无注册表条目也无排除说明的初始化器 | 32 |
| `check-host-parity` 登记的差异 | 183 |
| 命令式读取 `@/stores/` 的内核（`lib/`）文件 | 294 |
| 导入 `@/hooks/` 或 `@/components/` 的 `lib/` 文件 | 64 |
| 没用持久化队列原语的持久化队列 | 约 17 |
| 没用限流器的并发上限 | 约 22 |
| 没关联到 `executionRuns` 的类运行表 | 阶段 0 测量 |

无头注册表门禁不再按命名匹配。初始化器在 effect 里调用的任何 `@/lib/**` 函数，必须满足三者之一：能从 brain 的模块图到达；通过注册表在桌面启动；带物理原因被排除。

### 6. 一块代码怎么迁（绞杀者模式，永不重写）

1. **特征化**：写一个在两个宿主上都能驱动该行为的测试（桌面 provider 和 Node brain），固定它当前的行为，已知缺陷也照实固定并加标注。
2. **迁移**：把行为做成注册表条目或原语实例，旧路径改为调用新实现。
3. **删除**：在同一阶段删掉旧路径。第二份实现最多存活到产生它的那个阶段结束，不会有两份实现同时长期在线。
4. **调低基线**并锁定。

每个阶段在独立的 worktree 分支上进行。机械性迁移，比如把某个队列迁到原语上、把某个上限换成限流器实例，分批交给 Codex 执行。架构、内核抽取和审查由 Claude 负责。每个阶段都在 `docs/evidence/` 下留一份证据台账。

### 7. 产能

在阶段 4 结束之前，拿出固定比例的产能（约一半）用于收敛。新功能继续开发，但要基于新原语和注册表。阶段 0 的门禁会让旧写法直接失败，所以新工作不会再往正在偿还的债务上加码。

### 8. 阶段与退出条件

| 阶段 | 范围 | 退出条件 |
| --- | --- | --- |
| 0. 止血 | 收敛门禁与基线；不按命名匹配的无头注册表门禁；让宿主一致性门禁恢复通过；修复 router-fusion outbox；核实审计中两项高风险问题；本 ADR | `dev` 上所有门禁通过；所有基线都已记录；两项高风险问题都有测试给出答案 |
| 1. 原语 | 持久化队列与限流器模块；迁移所有队列和上限 | 队列与限流器两项计数降到 0；ADR-0248 通过限流器实现 |
| 2. 内核脱离 UI | 桌面从注册表启动；抽出聊天引擎；所有运行时初始化器要么迁移，要么带原因排除 | 未说明缺口为 0；内核里的 `getState()` 为 0；`lib` 对 `hooks`/`components` 的依赖为 0；宿主一致性差异只剩"物理上不可能"这一类 |
| 3. 工作主干 | 类运行表都指向 `executionRuns`；统一状态词汇；ADR-0247 的承诺 | 每个运行都在台账里；内核中"成功"只有一种写法 |
| 4. 关口，然后 enforce | 为每个关口加上枚举调用方的门禁；按类别开启 enforce | 门禁证明覆盖完整；通过的类别默认开启 enforce |

阶段 2 工作量最大，也是本 ADR 存在的理由。阶段 0 和 1 排在前面，原因有两个：它们成本低，并且能阻止新债产生；内核本身就要用这些原语来搭建。

## 后果

- 桌面与常驻 Host 的功能一致性从结构上得到保证：两边运行同一个已注册的内核。ADR-0059 写下的那条规则，从一条桌面可以豁免的规定，变成了桌面本身的启动方式。
- 接下来几个月，约一半的产能用于收敛，新功能会相应变慢。棘轮让进度可以度量；任何阶段都能停在某个退出点，不会留下两份同时在线的实现。
- 一些过去只因"窗口开着"才成立的桌面行为会改变：它们会在触发时发生，而不是等有人来看。每一处这样的变化，都会在所属阶段的证据台账里留下经过特征测试、带标注的差异记录。
- 本地数据不做迁移（见 CLAUDE.md），所以调整表结构的成本较低。但账号同步副本和宿主存储是否同样适用，要在每个阶段动结构之前单独核实。
