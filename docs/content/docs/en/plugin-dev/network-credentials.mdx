# Network credentials

Every `ctx.network` request passes the host's PII gate before it leaves the
device. The gate cannot tell a token from user text by looking at it: real
tokens (`ghp_…`, `xoxb-…`, `Bearer eyJ…`) look like secrets to the detector,
and an email address typed into an `Authorization` header looks like a token
field to a plugin. So credentials go through the host instead of through the
plugin's request data.

## Reference a stored secret

Store the credential once with `ctx.secrets.store(key, value)`, then pass a
reference wherever the request needs it. The host reads the secret from **this
plugin's own** secret namespace and fills it in after the PII check and the
`networkAccess` destination check, right before the request is sent.

```ts
import { secretRef } from "@cognia/plugin-sdk"

await ctx.secrets.store("github-token", token)

const response = await ctx.network.get("https://api.github.com/user", {
  headers: { Authorization: secretRef("github-token", { prefix: "Bearer " }) },
})
```

Always build a reference with `secretRef()`. It returns
`{ $secretRef, prefix? }` and marks the object with a host-recognised brand that
JSON cannot carry. An object you write by hand, or one that arrives in a webhook
payload or model output, is ordinary data even if it has a `$secretRef` key: it
is inspected like any other field and never resolved. That keeps a plugin that
forwards untrusted JSON from sending its own secrets.

`$secretRef` is a non-empty key in your secret namespace; `prefix` is optional
text placed before the value (for example `Bearer ` or `token `). The prefix is
plugin-written text, so it follows the literal-credential policy below.

## Where a reference is accepted

References resolve only in credential positions:

| Position | Accepted names                                                                                                          |
| -------- | ----------------------------------------------------------------------------------------------------------------------- |
| Header   | `authorization`, `proxy-authorization`, `x-api-key`, `api-key`, `apikey`, `api_key`, `access-token`, `access_token` |
| Query    | the same names, passed in the `query` option (appended after the URL is checked)                                        |
| Body     | a field with one of those names in an object body, at any depth (not in a body you pass as a JSON string)               |

```ts
await ctx.network.get("https://api.example.com/v1/items", {
  query: { api_key: secretRef("example-key") },
})

await ctx.network.post("https://api.example.com/v1/session", {
  access_token: secretRef("example-token"),
  note: "refresh",
})
```

The request is refused before anything is sent when a reference sits in any
other position (including inside an array), is malformed, names a secret that
does not exist or is empty, or the plugin lacks `secrets:read`. When
`secrets:read` needs per-use consent, the prompt names the request's method and
destination. Header names and body keys are matched case-insensitively. Download
and upload headers accept references too.

The resolved value never appears in audit records, logs or rate-limit keys, and
the request is audited even when the secret cannot be read. If a server echoes
the value back in the response (headers, body, or a binary body) or in an
error, the host replaces it with `[REDACTED]`, including its URL-, JSON- and
base64-encoded forms, before your plugin sees it. Errors keep their name and
code; only their text is cleaned. Two limits: a secret shorter than 8 characters
is not echo-filtered (filtering such short strings would corrupt unrelated
text), and a file saved by `ctx.network.download` is written as received.

## Literal credentials during the transition

A plugin that still writes the credential text itself (for example
`headers: { Authorization: "Bearer " + token }`) keeps working. The manifest
field `networkAccess.literalCredentials` decides what the gate does with such
literal values:

| Value                 | Behavior                                                                                                                                                                 |
| --------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `"observe"` (default) | The literal is sent unchanged, as before. Each send records an audit entry naming the field (never the value), and you get one developer warning per field per session. |
| `"inspect"`           | The literal goes through the normal PII policy, so `Bearer alice@example.com` is redacted (or blocked under `piiPolicy: "block"`). A reference's `prefix` is checked the same way; the secret itself is filled in unchanged. |

```json
{
  "permissions": ["network:fetch", "secrets:read"],
  "networkAccess": {
    "allowedDomains": ["api.github.com"],
    "literalCredentials": "inspect"
  }
}
```

The host default is `observe` for now and becomes `inspect` in the release after
this one. Move credentials to `secretRef` and opt in to `inspect` early, so the
flip changes nothing for your plugin.

## What this does not change

- `ctx.auth.createPkceFlow` builds its own token request; the host keeps its
  protocol fields intact without any reference.
- `ctx.integrations.authenticatedRequest` already injects the account's
  credentials on the host side.
- Form-encoded request bodies you write yourself are still inspected as one
  string.
- Runtimes: JavaScript plugins running in the Node plugin host get the same
  behaviour; the host carries the brand across its process boundary with its
  own wire marker. Python, WASM and iframe plugins do not reach `ctx.network`,
  so there is no Python helper.
