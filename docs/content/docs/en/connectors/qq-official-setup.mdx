# QQ Official Bot Setup Guide

Cognia connects to the **QQ Open Platform** with an official bot's **App ID** and **AppSecret** (called **Client Secret** in Cognia). This connector is separate from personal-account access through [OneBot / NapCat](./qq-via-onebot-faq).

Group/C2C supports native Markdown, visible quote replies and native button keyboards. Button interactions return through the same verified transport and callback authorization pipeline. Incoming quotes, nested messages/chat records and ARK cards are normalized for the transcript; quote indexes are kept separately from passive-send authorization.

Group/C2C file sends accept public URLs and the original bytes of user-selected local attachments. The updated native host uses direct binary upload up to 5,000,000 bytes and chunked upload above that, with a 200,000,000-byte native source cap, then sends the file through the same passive-reply rules.

## 1. Prepare the QQ application

1. Open [QQ Open Platform](https://q.qq.com), create a bot, and record its App ID and AppSecret under **Development settings**. The old static Token is deprecated.
2. Configure the sandbox participants and the conversation permissions available to your application. Complete the platform's production review before testing production access.
3. If your application requires an **IP whitelist**, add the connector host's public outbound IP. A public callback tunnel supplies inbound HTTPS; it does not necessarily change the host's outbound IP. Recheck the whitelist after network/proxy changes.
4. Choose the events you need in the QQ console:

| Conversation                       | Event                     | Requirement                                                           |
| ---------------------------------- | ------------------------- | --------------------------------------------------------------------- |
| QQ group mentions                  | `GROUP_AT_MESSAGE_CREATE` | Group messaging enabled for the application.                          |
| All QQ group messages              | `GROUP_MESSAGE_CREATE`    | Enable QQ's receive-all-messages feature and subscribe to this event. |
| QQ private chat                    | `C2C_MESSAGE_CREATE`      | C2C messaging enabled.                                                |
| Group/C2C button presses            | `INTERACTION_CREATE`      | Enable interaction events; gateway adds `INTERACTION` (`1 << 26`). |
| Channel mentions                   | `AT_MESSAGE_CREATE`       | Public-guild messaging permission.                                    |
| All private-guild channel messages | `MESSAGE_CREATE`          | Private-guild `GUILD_MESSAGES` permission.                            |
| Channel direct messages            | `DIRECT_MESSAGE_CREATE`   | Channel direct-message permission.                                    |

Platform permissions and Cognia's response rules are separate. Receiving an ordinary group message does not automatically authorize an AI response. The default mention-only policy still requires addressing the bot; choose the conversation's always-respond policy only if that is the behavior you want.

## 2. Add the connector

1. Open **Settings → Platform Connections → Adapters**, click **Add connector**, and choose **QQ Official Bot**.
2. Enter a display name, App ID and Client Secret.
3. Keep **HTTPS webhook**, the default for new connectors, and save.
4. Reopen the adapter, copy its callback URL, and configure that exact URL and event subscriptions in the QQ console. The connector host needs reachable public HTTPS; a loopback address cannot receive QQ callbacks. QQ documents callback ports **80, 443, 8080 and 8443**.
5. Complete QQ's callback verification. Cognia verifies signed requests and answers the validation challenge on the native host.

For a private-guild bot with the appropriate permission, enable **Receive all channel messages**. In gateway mode this adds the `GUILD_MESSAGES` intent; in Webhook mode you must also subscribe to `MESSAGE_CREATE` in the console. Leave this off for public-guild bots without that permission. This switch does not enable QQ group full-message access; configure `GROUP_MESSAGE_CREATE` on QQ separately.

Credentials are stored in the OS keyring. Cognia exchanges them at `https://api.bot.qq.com/app/getAppAccessToken`, refreshes cached tokens near expiry, and uses `Authorization: QQBot <access_token>` for REST calls.

**Test credentials** in Webhook mode checks token issuance only. A running adapter or a successful credential test does not establish callback reachability, subscriptions or actual message delivery.

### Gateway compatibility mode

Select **Gateway WebSocket** only when the QQ application has gateway access. Existing gateway adapters keep their transport. The credential test additionally resolves `GET /gateway`; a returned URL is not an authenticated session.

Gateway mode uses HELLO / IDENTIFY / heartbeat / RESUME with reconnect backoff. These operations do not apply to Webhook callbacks. The current QQ docs still describe gateways, while Tencent's BotGo guidance recommends Webhook; availability depends on the application.

The gateway stays **Starting** until QQ returns `READY` or a valid `RESUMED`. Credential validation and gateway URL discovery do not establish online status. Native message listeners are installed before opening the socket; authentication has a deadline and disconnection changes health immediately. Quitting Cognia disconnects the service.

If QQ displays “soul offline” or “service not connected”, its backend service is not online; when using this integration, Cognia provides that service. Check the adapter's **Health** and actual incoming-message **Audit** entries. A saved credential alone is insufficient, and the hint does not by itself identify a sandbox-membership problem. See the [official Agent setup FAQ](https://bot.q.qq.com/wiki/agent-qqbot/).

### Verify an AI reply

Select an available provider/model under the adapter's **AI binding defaults**, or configure the application default it inherits. QQ credentials authorize QQ access; the selected AI provider also needs its own usable account or credential.

Send a private test message and check three separate results: an incoming-message audit entry, a delivered outbound message, and the expected AI answer in QQ. A welcome/help card can be delivered even when model-account resolution fails. If the audit records `route_handler_failed`, check the selected AI account and runtime diagnostics; reconnecting QQ alone does not repair a missing AI account.

### Welcome formatting and preview

Welcome and help use the shared A2UI builder. QQ group/C2C projects supported Card/Text content to native Markdown, including surfaces without buttons; configured buttons remain native keyboards. Titles, section labels and paragraphs are generated from semantic nodes, while literal text is escaped. QQ uses the documented heading levels and bold section labels. Guild channel/direct scenes and unsupported widgets retain their reported fallback.

Send `/help welcome` to preview the current welcome in the conversation. This reuses the common help entry and governed queue, does not invoke the model, and does not reset or consume first-contact welcome deduplication. With custom help triggers, append ` welcome` to that trigger instead. `/help` still shows the full help content. Existing conversations are not automatically greeted again after an update.

### Complex-case acceptance

Use a controlled test conversation. Complete onboarding before checking reply counts, because the initial welcome is a separate message. For each case retain incoming IDs, AI-run count, outbound status/attempts and the client's observed result. Keep failure injection in isolated tests; do not crash shared services or exhaust real platform quotas.

| Case | Observable result |
| --- | --- |
| Welcome preview | Rendered heading/paragraphs, no raw heading markers; no model call or new first-welcome record. |
| Concurrent first messages | One welcome job; each admitted task still runs. A failed welcome enqueue must not block the task or audit a false welcome success. |
| Two quick private messages | Two correlated replies, FIFO within the conversation; neither duplicate nor missing consumption. |
| Context and quote follow-up | The follow-up keeps its conversation, references the intended prior message and answers the new request. |
| Long Markdown and mixed media | Preserve order and text; split incompatible native payloads before sending and check the aggregate passive allowance. |
| Buttons and repeated callbacks | Only confirmed message receipts authorize actions; duplicate interaction runs once; a freshly issued card remains clickable. |
| Interleaved recipients | Each recipient keeps its own stream server ID, indexes, content and reply allowance even if logical keys match. |
| Stream cancellation/reconnect | No late text after cancellation; acknowledged continuation keeps one server ID and finishes with `input_state=10`. |
| Lost final ACK or partial multipart delivery | Queue stays `delivery_unknown` across runner restart; no automatic second POST; confirmed part/stream evidence remains available. |
| Binary upload, codec and permission failures | Failed preparation does not consume a message slot; retries reuse encoded bytes; refused operations do not gain authority. |

The focused local QQ suite is `pnpm im:test:qq`; help composition and the common queue/bus have adjacent Jest suites. Their native HTTP and protocol fault fixtures do not prove Tencent/client acceptance. The separate real QQ observer described in [Local Live Testing](./local-live-testing) proves its two-turn text contract, not stream completion or receipt recovery. Confirm real native streaming, file/voice playback and group grants separately.

## 3. Verify the actual flow

1. Send a controlled private message or mention the bot in an authorized group/channel, and confirm the message appears in Cognia.
2. Confirm one expected reply arrives in QQ. Ordinary unmentioned group/channel messages can be stored without triggering a reply under mention-only rules.
3. For receive-all access, send an unmentioned message and verify that it arrives. A mention test alone does not verify this permission. If full-message mention detection has no confirmed identity, use the adapter's identity probe; subsequent events use the updated result. Do not infer bot identity from an unrelated member mention.
4. If delivery fails, inspect **Platform Connections → Audit Log**, console subscriptions, permissions, callback reachability and the outbound-IP whitelist.
5. To verify native quoting, reply to a received group/C2C message, then quote a bot response in QQ and confirm the parent/preview appears in Cognia. Repeat after restarting the connector with a fresh passive context. A quote needs an index observed by this installation; an old message alone does not renew the send window.
6. Verify file delivery with a small binary attachment and a local file larger than 5,000,000 bytes. Confirm that QQ receives the original bytes and filename, including when the host uses a proxy. An upload result alone is not message delivery; Cognia waits for the final send's definitive message ID.

QQ business errors can accompany HTTP success statuses. Cognia checks `err_code` (with legacy `code` compatibility) and retains trace identifiers for diagnosis. Pending platform audits, duplicate rejections and responses without a definitive message ID require reconciliation and are not automatically resent. Such jobs are not proof of successful delivery; inspect the platform outcome before manually retrying.

Channel messages with a valid `data.message_audit.audit_id` use the shared asynchronous receipt path. The runner persists `pendingReceipt` through a host-owned send callback, holds the job in `delivery_unknown`, and displays **Awaiting provider result**. Exact adapter/conversation/receipt evidence from `MESSAGE_AUDIT_PASS` or `MESSAGE_AUDIT_REJECT` settles the existing queue row; PASS requires a real message ID, REJECT does not. Early callbacks survive until registration, duplicates are idempotent, conflicting evidence requires operator reconciliation, and a waiting head blocks newer jobs in that conversation. Delivery waiters continue waiting while the receipt is unresolved; plugin feedback and paired-client status projections retain the marker. Confirmed delivery updates the normal delivered-message ledger, SLA and audit projection. A provider-reviewed rejection cannot replay the old intent: compose and authorize a new message.

Enable **Receive message audit results** only after QQ grants `MESSAGE_AUDIT`. Gateway mode adds its intent only when enabled; Webhook requires the corresponding console subscription. Both use the same parser and queue settlement. This mapping is currently limited to channel audit contracts. Missing IDs, group/C2C uncertainty and multipart partial delivery remain manual reconciliation. The shared evidence store caps at 10,000 records and reclaims completed receipts; unresolved evidence is retained and capacity exhaustion fails closed. Unresolved send intents are not evicted merely because a quota window expires.

## Message capabilities and limits

- **Text, media and files:** passive text replies in all four scenes; group/C2C supports images, video, voice and files (`file_type=4`), while channel/direct retains public-URL images only. A file is sent as native media, rather than a text link.
- **Binary and chunked uploads:** group/C2C accepts base64 data URLs and inline `dataBase64` on file/image segments. The group/C2C composer accepts arbitrary file types and forwards their original bytes without document extraction, image resizing or video sampling. Arbitrary path strings and `file:` URLs are rejected at the final serializer because connector-send permission is not a filesystem grant. These require the updated native connector host; no public tunnel is needed for a local attachment. Up to **5,000,000 bytes** uses JSON `file_data` base64. Larger sources use `upload_prepare`, raw PUTs to the supplied storage URLs, `upload_part_finish` and `/files` merge. The uploader calculates whole-file MD5/SHA1, the exact first-10,002,432-byte MD5, and each part's MD5. It validates the complete part plan before any PUT and applies shared pacing below the documented 10 QPS limit.
- **Upload limits and failures:** the native uploader reads one bounded snapshot, capped at **200,000,000 bytes**. The composer preserves original bytes and retains its shared limit of **10 MiB per file and six files per message**; its attachments can still use chunked upload above the direct-upload threshold. Known file sizes are checked before upload, and actual native bytes are checked on the host. Native images/voice above 20,000,000 bytes and video above 30,000,000 bytes upload as files, following QQ's soft-limit behavior. URL uploads remain server-side downloads and still depend on QQ's format, quota and permission checks. Chunk uploads are sequential with a 300-second total deadline; persistent cross-restart upload resume is not implemented. Upload failure prevents the message send. A long upload may exhaust the passive window, which is checked again before sending.
- **Upload authorization:** all upload stages use `srv_send_msg=false` where applicable; chunks never consume passive reply slots. The final media message consumes one slot per part. QQ API credentials stay off presigned storage requests, which require public HTTPS, reject redirects and follow the host's checked proxy path. No upload is converted into a proactive send.
- **Passive budgets:** a group message allows up to **5 replies within 5 minutes**; C2C allows up to **4 replies within 60 minutes**. Multipart sends share that budget. Cognia conservatively counts C2C typing notifications as replies and reserves the final slot for the answer. Channel/direct replies retain the 5-minute window. Expired context is rejected rather than converted into a proactive send.
- **Native Markdown:** group/C2C assistant replies and explicit Markdown segments use `msg_type=2` with `markdown.content`; no template registration is needed. Headings, emphasis, lists, links and inline images are passed to QQ's Markdown renderer. Plain-text messages remain text. When a request mixes literal text with Markdown, the literal text is escaped; the Markdown source is preserved. Channel/channel-direct Markdown retains a reported text fallback because channel permission is invitation-only and is not enabled by this adapter.
- **Markdown with media:** standalone attachments are sent separately from native Markdown, in segment order. Every resulting part consumes the same passive reply budget; over-budget messages are rejected before any upload or send. Native Markdown rejection is reported rather than silently resent as text. Inline image links in Markdown use QQ's own resource handling and do not require a separate attachment part.
- **Native quote replies:** explicit group/C2C replies use the received message's `message_scene.ext.msg_idx`, or a bot response's `ext_info.ref_idx`, in `message_reference.message_id`. The current real inbound `msg_id` still supplies passive authorization, so quoting another message cannot bypass expiry or reply limits. Native text, Markdown and media parts retain the same selected quote. Scoped mappings persist across connector restarts, including every confirmed part of multipart sends; the cache is bounded, and missing/conflicting/pruned indexes make an explicit native quote fail before sending. Legacy reply segments without a known index retain their reported text alternative. Channel/direct behavior is unchanged.
- **Structured incoming content:** `message_scene.ext` preserves padded indexes and strips `auth_token`; `msg_elements` supports bounded recursive messages and chat records. Native quotes keep a read-only preview and resolve known parents to stored messages; unknown parents remain previews without an invented jump or bot identity. ARK cards show allowlisted titles, descriptions, sources/tags, addresses, safe links and previews. Unknown card fields and credential-bearing/non-public URLs are omitted. Card portraits do not become sender identities. Quoted/chat-record media and card previews are display context, not new model attachments; current message attachments retain the normal media policy.
- **Native buttons:** group/C2C A2UI `Button` components become custom `keyboard.content.rows` buttons. Callback buttons use action type 1, HTTP(S) link buttons use type 0, and a Button's optional `qqCommand` string uses type 2 to insert a command. Rows, columns, cards and text retain a readable body; unsupported inputs retain a reported text alternative. Guild scenes keep the text alternative. There is no message editing or automatic removal of a completed card's buttons.
- **Interaction callbacks:** enable `INTERACTION_CREATE` in the QQ console. Cognia checks a per-delivery token against its persisted, confirmed outbound receipt, adapter, scene, conversation, expiry and any provided button/origin ID. Group callbacks require `group_member_openid`; C2C uses `user_openid`. Group/C2C callbacks often omit the origin message ID, so it is never invented. Author-owned workflow/tool/skill approval bindings retain their original kind, actor restrictions and consume-once rules. Chat allow/blocklists still apply; a deliberate button press does not require an @ mention.
- **Acknowledgement and replies:** the native host's Webhook transport ACK and `PUT /interactions/{id}` are separate. Cognia reports callback admission without waiting for the model/workflow to finish; an ACK is not proof that the action completed. Redeliveries share one press ID, while a fresh click gets a new ID; binding lookup uses the separate stored action key. Transient routing failures remain retryable without a second ACK attempt. Replies and approval confirmations preserve that click's captured `event_id`, never substitute it for `msg_id`, and retain passive expiry, quote and aggregate part-budget checks.
- **C2C native streaming:** eligible automatic replies update one QQ message through `stream_messages`, using full Markdown snapshots (`input_mode=replace`), increasing indexes, the first response's server-issued `stream_msg_id`, and a final `input_state=10`. Updates are coalesced at 500 ms and share one logical passive reply slot. The primary AI turn and an authorized button callback can stream; drafts, human mode, unattended scheduled digests and replies routed through another connector stay final-only. Every snapshot passes the PII gate; twin replies use a fixed leading disclosure. A native C2C stream replaces the separate progress card for that turn.
- **Stream bounds and recovery:** Cognia conservatively uses a **five-minute stream window**, following the official Node SDK guidance, while ordinary C2C sends retain the 60-minute rule above. Snapshots are bounded to **48 KiB UTF-8**. QQ's `remain_msg_len` is retained as response metadata, not a writable-character quota: zero or a small value does not stop subsequent snapshots or trigger a second ordinary message. A delivered prefix cannot be rewritten. Rewritten, mixed-media, card or explicitly quoted finals close any known preview and send the complete final through the ordinary path, with a reported alternative and its additional passive slot. Cancelled captures close only their already accepted safe text; late snapshots are ignored. Stopping the adapter stops queued flushes and preserves checkpoints. A known acknowledged stream can finish after restart within its window; an interrupted send, missing definitive ID or ambiguous final requires reconciliation rather than automatic replay. Checkpoints are capped at 1,000. Resolved passive checkpoints use 24-hour retention; unresolved sending/uncertain evidence is retained. Recall checkpoints and receipts remain through the captured user message’s 30-day recall horizon, preventing old keys from reopening after 24-hour cleanup. Recovery remains bounded; capacity exhaustion requires reconciliation. Default reply streams never set `is_wakeup`.
- **Native C2C reengagement streams:** explicit `sendOptions.mode: "reengagement"` uses the same stream manager, with `is_wakeup=true` and the existing captured-user, opt-out, 30-day and quota checks. Pure text/Markdown queued recalls use the native endpoint even without previews. All frames share one provider ID and one logical recall reservation, including the final `input_state=10`; continuations keep the original quota across time boundaries and consume no passive reply slots. Quota validity and consent are checked again at the provider boundary after pacing/token acquisition. Duplicate/pending/unknown acknowledgements remain reconciliation-only. Once a recall preview is accepted, a rewritten, quoted or mixed final can only close the known safe prefix and report incomplete delivery; it never opens a second recall. Cancellation and finalization use durable conditional writes across manager instances.
- **Other limitations:** group streaming, generic outbound ARK and miniapp jumps remain unavailable. Current group/C2C send tables do not establish an outbound ARK body; legacy guides conflict. Provider controls remain system events and do not automatically become model messages.
- **Recall and scene-specific features:** native recall endpoints are available subject to QQ's restrictions; typing is C2C-only and reactions are channel-only.

### Keyboard bounds and native cards

Cognia uses at most five rows of five buttons. QQ labels are limited to ten characters; generated A2UI labels are shortened while the full readable mirror is retained. Explicit native payloads with invalid labels, duplicate IDs, unsafe links or unsupported fields fail before sending. Links accept HTTP(S) without URL credentials. Command `enter=true` and `anchor=1` are C2C-only; image-picker anchors also depend on the QQ mobile client. Deprecated `click_limit`, guild-only role restrictions, and mini-program jumps are not exposed. Shared `Button.confirmation` maps to QQ callback-button `action.modal`, and `exclusiveGroup` maps to `group_id`. Modal content is limited to 40 characters, cannot include links, and button labels are limited to four characters. Other adapters must declare this policy explicitly; QQ client support remains required.

For an explicit platform card, use a `MessageSegment` with `type: "card"`, `card.kind: "qq-keyboard"`, and `card.payload` containing `content` or `markdown: { content }` plus `keyboard`. `content` and Markdown are exclusive. The keyboard accepts a template `id` or custom `content.rows`, never both. Explicit custom callback `action.data` must name an existing live callback binding in the same conversation; Cognia replaces it with a per-delivery token. Template/external callbacks without a managed receipt are rejected. Unknown opaque card kinds remain unsupported.

Callback receipts persist across connector restarts, expire after at most 30 days and cannot outlive a shorter author binding. Already-consumed approval bindings cannot grant again. Callback envelopes delayed more than five minutes are rejected locally. A keyboard message is its own ordered part; mixing Markdown, keyboards and media may exceed the conversation's shared 5/4-reply budget and is rejected before upload/send.

For acceptance, send a button card in both group and C2C, press a generic button twice, retry a one-shot approval, and verify that only the permitted user can approve. Repeat through the configured HTTPS callback, confirm the reply stays in the same conversation, and check failure/denial feedback separately from final action completion. These steps require the application's live QQ grants and a compatible QQ client.

## Shared connector entry points

### Common system interactions

Adapters advertise `events.interaction` and `events.delivery-status`. Platform-neutral `NormalizedInboundEvent.interaction` and `deliveryStatus` travel through the existing bus, `ctx.connectors.onInbound`, audit log and `trigger.connector.system`; the workflow editor and runtime share one event-kind catalogue. QQ menu type12 emits `systemKind: 'interaction'` with `featureId`; it is acknowledged only after policy admission and atomic event/audit capture. Type13 LIKE/UNLIKE and selection/removal reuse the common reaction path. Types14/15/16 expose session-reset, story enter/exit and model-change observations. Types18/19/20 expose authorization observations; a scope without a documented grant/revoke result never grants proactive consent. Typed metadata cannot execute a command, delete Cognia history or switch its model. Configured workflows/plugins act through their normal permission and PII gates. Only native buttons and menus receive interaction ACKs; other controls receive none. Workflow fan-out retains its existing best-effort boundary; receipt evidence and queue settlement are durable.

### Management and voice

These features use shared connector contracts. An adapter advertises named operations through `listManagementOperations`; unsupported operations fail before a network request. Plugins use `ctx.connectors.queryManagement(adapterId, request)` with `connectors:read`, or `manage` with `connectors:manage`. These APIs accept validated operation parameters, never raw platform URLs or headers. The opt-in assistant tools are `im.query_resource` and `im.manage_resource`; mutations require a confirmation card or the existing desktop approval dialog. Cards show the connector, operation and changes; only the permitted actor can choose Confirm or Cancel, once, and execution rechecks the original session's permissions.

| Operations | Shared inputs and QQ behavior |
| --- | --- |
| `links.create` | `{ purpose: 'add-contact', state?: string }` generates a bot invitation URL. Shared capability `links.create`; QQ maps `state` to `callback_data`, at most 32 Unicode characters, without trimming or truncation. State passes the outbound PII gate. Only the documented public HTTPS `qun.qq.com/qunpro/robot/qunshare` receipt is accepted; no response tokens are exposed. Creation uses the existing manage permission/confirmation and does not send or publish the link. |
| `assets.upload/list/delete` | Upload a public URL or explicit base64 image, query pagination, or delete an owned image ID. PNG/JPEG/GIF/WebP, 10,000,000 bytes; the native host checks format/MIME, hashes and prepare → PUT → complete. Reusable references belong to one adapter; local inventory survives restart, checks expiry on Markdown/cards/streams, and renews only after acknowledged use. QQ limits each bot to 100 images and expires unused images after 90 days. Signed preview URLs are not persisted. |
| `menus.get/set` | C2C global menu, with shared prompt/slash/link/submenu/toggle items. Publishing replaces the menu. QQ allows ten top-level items and five children per submenu; names use weighted platform lengths. |
| `commands.list/get/create/update/delete/targets` | List requires `scope` (`private`, `group`, `channel`, `direct`); use returned IDs for updates and target changes. Panels contain command names/descriptions or HTTPS links. Specific C2C/group targets are updated separately with `action: add/remove` and up to 20 target IDs per call. |
| `members.list/get/remove`, `blacklist.list/update` | Canonical chat/member IDs. Removal is explicit and may request a rejoin block; partial blacklist failures are returned. Member/bot-state APIs require QQ's invited application permission; administrator status alone is insufficient. |
| `moderation.get/set`, `joinRequests.list/decide` | Public group administrator APIs do not depend on invited member-read access. Member mute expires within 30 days. Decisions require the exact chat/member/request ID. QQ enforces protected member roles. Auto-approved join events are lifecycle notices, not new pending requests. |
| `joinPolicies.list/create/update/delete/allowlist/execute` | Policies use group OpenIDs, explicit enable/expiry/groups and account-number strings for allowlists. QQ allows 20 policies, 100 groups per policy and 10,000 allowlist entries per call. `execute` returns `accepted` for an asynchronous platform job; this is not proof of completed approvals. |

```ts
const operations = ctx.connectors.listManagementOperations(adapterId)
const panels = await ctx.connectors.queryManagement(adapterId, {
  operation: 'commands.list', input: { scope: 'group', limit: 20 },
})
const invitation = await ctx.connectors.manage(adapterId, {
  operation: 'links.create', input: { purpose: 'add-contact', state: 'campaign_123' },
})
// invitation.link.url is returned; sharing it is a separate authorized action.
```

For a user arriving through that link, `ctx.connectors.onInbound` and `trigger.connector.system` receive a `kind: 'system'`, `systemKind: 'lifecycle'` event. Its common `referral` field contains `state` from QQ's `scene_param` and `source` as the string form of QQ's scene number. QQ-specific `channelData.friendAdd` retains the scene number and bounded short code. Lifecycle audit records also retain the referral. These fields are untrusted attribution, never identity, proactive consent or reply authorization; they do not create a chat message or automatically start an AI turn. Cross-application `union_openid` and unrelated provider fields are not retained. Malformed attribution is omitted without dropping the valid lifecycle event.

Management requests are serialized and conservatively paced per bot below the relevant menu/panel/group limits. Stopping the adapter invalidates queued work. Permission errors report the missing platform approval/group role; a declared capability does not grant those permissions. There is no dedicated management settings page in this increment; the common plugin APIs and opt-in tools are the supported entry points.

`im.send_voice` uses a known captured conversation and the existing TTS settings, provider credentials, character-voice resolution, pronunciation dictionary, cache and retry path. It generates one encoded audio file without local playback; new cloud synthesis is metered, cache hits are not. Complete source text and actual post-dictionary spoken text pass the connector PII gate even for local synthesis. The resulting voice segment retains its real MIME type and transcript and enters the governed outbound queue. It does not enable automatic voice replies or cloud transcription.

QQ groups accept MP3/WAV/SILK. C2C documents SILK only: `im.send_voice` now uses the shared local audio converter to turn buffered TTS output into real Tencent SILK before queuing the captured C2C destination. Even a matching provider MIME is decoded and validated before export. Delivery retries reuse the queued encoded bytes and do not call TTS again. Incoming `voice_wav_url` is used when public and safe, while retaining the original voice URL; `asr_refer_text` supplies a bounded platform transcript through the existing media/model policy. Missing ASR remains an attachment rather than an automatic cloud STT request.

The platform-neutral `transcodeAudio` entry accepts in-memory WAV (PCM/float), MP3, AAC/ADTS, M4A/MP4 AAC, native FLAC, Ogg Opus, Tencent SILK, or explicitly described PCM16 (8–48 kHz, mono/stereo). It outputs mono 24 kHz WAV or Tencent SILK in a disposable local WASM Worker; no audio file is sent to a conversion service. Limits are 20 MB input/output, 300 seconds, 64 MB cumulative decoded float samples, one active conversion and a 30-second deadline. SILK output pads the final 20 ms frame with silence. Cancellation stops synthesis/conversion and rolls back a not-yet-committed queue write; after durable queue handoff the existing delivery lifecycle owns the job. Vorbis, WebM, ADPCM WAV and browser speech playback-only providers are not supported for this export path; select a buffered provider/format such as MP3, AAC or WAV. Worker/WebAssembly support and packaged codec assets are required.

AAC-LC and HE-AAC audio is decoded locally, including mono/stereo ADTS and self-contained M4A with fast-start, trailing movie metadata or fragmented media. `audio/aac`, `audio/mp4` and M4A aliases use this same entry, so a configured AAC TTS response can reach C2C without changing provider settings. M4A priming and a single media edit (optionally preceded by silence) are respected; encrypted files, external references, multiple tracks/descriptions, changing layouts, multi-block ADTS, multi-segment/rate-changing edits and inconsistent sample timing are rejected. MP4 metadata/table/packet limits apply before demuxing; raw decoded samples and the presented timeline each obey the existing resource caps. No AAC encoding is added: shared outputs remain WAV/SILK.

### Explicit delivery and image policies

For incremental explicit delivery, use the existing `ctx.connectors.streamReply(adapterId, { conversationKey, conversationRef, streamKey, sendOptions: { mode: "reengagement" }, text })`. `text` is the cumulative Markdown snapshot. The host resolves its stored destination, plans every frame through the same immediate-delivery authorization and PII gates, and isolates stream keys by plugin. Missing authorization never uses the unplanned shadow waiver. Queue the final through `enqueueSend` with the same `sendOptions.mode` and `metadata.streamKey`; public callers keep their original key, while the host applies the same namespace to both calls. Ordinary automatic reply, held/draft and unattended-capture behavior is unchanged.

`OutboundRequest.sendOptions.mode` is `reply` by default. `proactive` and C2C-only `reengagement` are explicit intents, also exposed as `im.broadcast.deliveryMode`; they always require governed outbound authorization, including when ordinary reply planning uses compatibility mode. Expired replies never change mode automatically. C2C proactive sends require a recorded user opt-in; an explicit opt-out also blocks reengagement. Group proactive sends require platform permission. Reengagement requires a captured user message and uses one allowance in each interval (0–1, 1–3, 3–7 and 7–30 days). Cognia conservatively reserves 30 sends/minute per bot, 20/minute and 1,000/day per recipient, and persists intent before sending; unknown acknowledgements require reconciliation and are not automatically replayed. Multi-part sends consume each wire message. Local limits supplement QQ's own quotas and do not guarantee platform admission.

Friend-add, receive/reject and group lifecycle events preserve verified outer event IDs and provider timestamps. Eligible event replies use a separate five-minute event authority; they do not fabricate a message ID or automatically start an AI turn. Group join/member events subscribe to `GROUP_MEMBER` (`1 << 24`) in gateway mode; Webhook subscriptions must also be configured in the console.

`sendOptions.imagePolicy: 'require-complete'` sets native `markdown.force_verify_image_resource=true` for group/C2C Markdown, including keyboard cards. Text-only requests and unsupported scenes reject this requirement. A stream final needing this policy uses the ordinary verified-image path. A shared mention segment with `audience: 'all'` emits the native group broadcast marker; raw marker injection is rejected, administrator role is required and the daily allowance is one broadcast-bearing part per group (Beijing time).

## Avatars

Channel and channel-direct messages preserve `author.avatar`. Existing channel rows can resolve member information through the bound guild and use the guild icon. Group/C2C open IDs are not numeric QQ account IDs and are never used to construct numeric avatar URLs. Those scenes retain placeholders when no authoritative portrait is available. An ARK card's avatar is message content rather than the sender's identity.
