# Desktop Pet

<Status variant="beta">Beta · ADR-0058 · Dexie (no schema bump)</Status>

<TLDR>
  The pet is not a widget inside the app window — it lives in its own transparent, always-on-top Tauri
  windows, and `PetWindowRole` (`lib/pet/window-role.ts:18`) determines which of five roles
  the bundle uses at startup. Rust creates those windows `visible(false)` and never shows them on the create path:
  on Windows a `transparent(true)` window shown before its WebView commits a first paint renders as an
  opaque black rectangle. The renderer calls the shared reveal (`lib/pet/reveal.ts`) after mount, waiting
  **two rAFs** — layout, then post-commit — so the transparent frame is on screen before the window
  appears. The pet simulation includes: needs decay, care condition, coins and a shop, XP and
  levelling, achievements, and a locomotion FSM with ballistics.
</TLDR>

## Five window roles, one bundle

```ts
type PetWindowRole = "main" | "overlay" | "popup" | "island" | "web"
```

The same static export boots into every role; `getPetWindowRole()` (`lib/pet/window-role.ts:70`) resolves
which one from the Tauri webview label — `PET_WINDOW_LABEL` (`"pet"`), `PET_POPUP_WINDOW_LABEL`
(`"pet-popup"`), `ISLAND_WINDOW_LABEL` (`"island"`). `isSecondaryOverlayRole()` and `isMainAppWindow()`
are the guards that keep main-window-only work — bootstrapping, migrations, singletons — from running
three extra times in the overlay windows.

## The reveal contract exists because of a real bug

Transparent overlay windows are created hidden and revealed by the renderer, not by Rust. Showing a
`transparent(true)` window before its WebView has committed a first paint produces an opaque black
rectangle on Windows until something forces a recomposite — the "invisible / black until I click it"
bug. `lib/pet/reveal.ts` waits two animation frames (layout, then post-commit) before calling
`revealPetWindow()` / `revealIslandWindow()`, mirroring the main window's `WindowShowInitializer`
contract. The renderer's reveal goes through Rust on every platform (a panel generation check lets a close
that lands between the open and the first frame win over the reveal), then nudges the size by one pixel to force a recomposite. An existing window is never
re-shown before its first paint. The overlay and popup routes are marked `data-pet-overlay` by the boot
script, so their background is transparent before React hydrates.

## Window plumbing

The overlay and popup are created non-focusing (`.focused(false)`; `WS_EX_NOACTIVATE` / `WS_EX_TOOLWINDOW`
on Windows; a non-activating NSPanel on macOS), so the pet never takes focus from the app the user is
in, and neither window appears in Alt-Tab. An OS close routes through the same close path as the UI.

| Concern | Owner |
| --- | --- |
| Which monitor a window is on | `work_area_for` probes the window centre against `available_monitors` physical rects (`pet_window/mod.rs`) |
| Monitor or scale changes | `ScaleFactorChanged` and a cross-monitor `Moved` emit `pet://work-area-changed` |
| Live size changes | `pet_window_set_size`, anchored at the bottom centre and clamped to the work area |
| Popup placement | `resolve_popup_placement` (`pet_window/popup.rs`), from the pet's physical rect on its own monitor; re-placed on every content resize |
| CSS → physical pointer deltas | `resolveCssToPhysicalScale` / `petBoxScreenRect` (`lib/pet/overlay-geometry.ts`) |
| Pet settings writes from any window | `updatePetSettings` (`lib/pet/settings-sync.ts`): a Web Lock, a fresh read, then a broadcast that every pet window follows |

While the desktop pet is out, the in-app widget is hidden. `PetMainRuntime` keeps the pet's voice and
appearance running in the main window either way (ADR-0058 D12).

## Perchable surfaces degrade by platform

The pet can climb onto and walk along the top edges of other visible top-level windows, Shimeji-style.
`src-tauri/src/pet_window/surfaces.rs` splits that into three layers so the logic stays testable without a
live desktop: the `PetSurface` / `PetSurfaces` serde DTO, the pure `filter_and_sort_surfaces` predicate
over plain `WindowCandidate` records, and thin platform enumeration. Windows uses `EnumWindows`; macOS
uses Core Graphics window metadata and excludes Cognia's own process. Linux returns an empty list because
Wayland deliberately does not expose stable cross-application window geometry, so the overlay explicitly
degrades to normal floor-wander behavior.

<Callout type="warn">
  `PetSurface` is a **named struct, not a tuple**. A bare tuple serializes as a JSON array and the
  TypeScript wrapper then silently reads `undefined` — there is a regression note about exactly this in
  `pet_window/mod.rs`.
</Callout>

account instead of re-rolling on every boot.

## Three governed renderers

`types/pet/skin.ts` defines the common contract for built-in SVG, Live2D Cubism 3–5, and Sprite v2:
typed asset selection, capabilities, render mode, gaze target, and structured diagnostics. Unknown or
deleted selections normalize to SVG with a diagnostic; they never produce an empty render or a silent
permanent fallback.

`lib/pet/skin-runtime.ts` is the single expensive-resource owner in each WebView JavaScript realm. It
arbitrates one live renderer using `configuration > interactive > console > thumbnail` priority, keeps
neutral snapshots for losing previews, caches Sprite object URLs per asset, counts renderer/WebGL/ticker/
timer/URL/load/context-loss/fallback resources, and revokes them on invalidation or teardown. Hidden,
suspended, reduced-motion, and click-through-paused surfaces stop update callbacks. Live2D runs at 60 fps
normally, 30 fps in low-power mode, and 12 fps while quiescent.

`lib/pet/live2d/` owns Cubism discovery, manifest parsing, import validation, plugin registration,
parameter/emotion/gaze mapping, lip-sync, and URL replacement. Compatibility is classified as `ready`,
`degraded`, or `invalid`: required settings, moc, and textures block activation when unusable, while
missing optional motions, expressions, sounds, physics, or pose are removed and reported. Path traversal,
normalized duplicates, case-insensitive ambiguity, corrupt images, Cubism 2, and size limits are rejected
before persistence. The official Hiyori and Haru corpus is revision- and SHA-256-pinned in
`test-fixtures/pet/live2d-public-corpus.json`; binaries are fetched into `.cache`, not committed.

`lib/pet/sprite-v2/import.ts` validates the fixed atlas contract. Its final two rows provide 16 clockwise
gaze directions in 22.5° buckets with a dead zone, hysteresis, and stale-input return to idle. SVG moves
its existing face artwork; Live2D maps standard head/eye/body/mouth parameters. Gaze yields to suspension,
held pose, one-shots, locomotion, and semantic state. The in-app widget and previews follow the page-local
pointer; the overlay uses Tauri's least-privilege cursor command, sampled at no more than 10 Hz and never
persisted or transmitted.

Character bindings may inherit the global selection or choose SVG, a Live2D model, or a Sprite pack.
Legacy `live2dModelId` rows are interpreted lazily as typed Live2D selections, and deleting an asset clears
both global and character references transactionally before SVG takes over.

## Reaching the pet

The pet runs only in the desktop app's main window (ADR-0058 D9); on the web and mobile the rail, ⌘K and
Settings never offer it, `/pet` explains itself, and `/pet feed` says where the pet lives. On the desktop
every summon path, the global hotkey, the tray toggle, ⌘K "Toggle desktop pet", the Settings overlay
switch and the agent's `pet_show`, runs `openDesktopPetWindow()` (`lib/pet/commands.ts`), which opens at
the saved geometry and switches a disabled pet on. The six nurture commands are bindable in Settings →
Shortcuts and stay registered while the pet is off, answering with a "pet is off" notification rather than
nothing. A fresh Attention Radar report arrives as a `radarReport` event whose bubble offers "Open
Insights" (D10).

## Console and customization workspace

`/pet` renders on the shared `FeaturePageShell` + `FeaturePageHeader`, like `/memory` and
`/conversations` (ADR-0058 D15). The header draws the pet in its identity tile, carries the editable
name with a level · stage · coins line, and offers "Appearance & settings" and the desktop toggle. Its
second row is the navigation: Home, Chat, Shop, Collection (dex, achievements), Activity (journal,
insights), and a Plugins tab while a plugin registers one.

Home opens on "Most needed now": the lowest need and the care that restores it most
(`lib/pet/care/suggest-care.ts`, ranked from the controller's effect table), as the page's primary button.
Below it come the care actions with the `pet.panel.actions` plugin slot, the backpack with coins and the
way to the shop, a quick-talk field with the way to the full conversation, and the pet's stats. The pet
itself sits on the console's one accent surface beside them.

Appearance & settings is a sub-page (`/pet?view=appearance`) with a breadcrumb back. It holds
`PetCustomizationWorkspace`, the only owner that reads `DEFAULT_PET_SETTINGS` and persists merged settings
through `updatePetSettings()`, and the per-character looks, with a section index on a wide pane.
Settings → Pet and the "pet is off" notification point to it. Every `/pet` link is built with
`petConsoleHref` from `lib/pet/console-tabs.ts`, which also keeps the earlier ids (`nurture`, `customize`,
`binding`) landing on the place they now mean.

The desktop popup is a mini Home: stat card, needs, "Most needed now", care actions and quick talk, then
click-through, put away, open the pet page, and appearance & settings. Every "put away" (console header,
title bar, popup, tray, hotkey) persists `desktopPet.enabled = false` through `hideDesktopPetWindow`.
None of this changes `PetSettings`, `PetProfile`, asset records, Dexie versions, progression, economy,
interactions, or Tauri window protocols.
