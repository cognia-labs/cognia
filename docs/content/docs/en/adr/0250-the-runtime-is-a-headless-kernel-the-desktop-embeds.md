## Context

The architecture audit (revised after a second, adversarial pass) found two root causes and several problems that cut across them.

**The runtime lives in the UI.**
- 105 provider initializers. 75 own a runtime behaviour. 29 have a headless counterpart.
- Up to 32 of the rest are recorded nowhere. 32 is an upper bound: some are documented after all.
- Chat turn orchestration is a 7,299-line React hook with no headless counterpart, so the CLI reimplemented parts of it.
- Kernel code is coupled to Zustand stores. Counting static imports, 355 `lib/` files import `@/stores/`. Counting dynamic imports, 475 do and 409 call them imperatively. Not all of those stores hold UI state.
- Some behaviours wait for "when the session is next opened".
- `check-host-parity` has a baseline of 183 findings, but the tree now has 200: 26 new, 9 closed.
- The registry that ADR-0059 introduced (`lib/headless/registry.ts`) is booted only by the brain. The desktop never uses it.

**There is no shared work kernel.**
- 393 Dexie tables.
- About 23 run-like records.
- About 17 durable queues on at least five backoff curves.
- About 22 caps that know nothing of each other.
- About 15 dedup mechanisms.

**Chokepoints are conventions.**
- No gate enumerates the outbound planners' callers.
- The delivery gateway's static test sees one import spelling.
- The PII gate checks imports, not calls.
- Resume authority checks are audit-only.
- 122 gates exist, but a PR can raise a ratchet baseline in the same change, because CI does not compare against the base commit.

**What the second pass added:**
- **Data authority switches with connectivity.** `DataPlane::pick` (`crates/cognia-companion/src/data_plane.rs:77`) prefers a connected brain, then the desktop renderer, then a writable SQLite fallback. Writes made during a brain outage have no reconciliation.
- **Plugins are a public boundary.** The contract has 938 methods across 91 namespaces, and only 120 of them declare headless support. `context.ts` builds runtime and UI APIs in one object.
- **Contracts have several semantic sources.** Rust signatures, dispatch, the manifest, Zod and the response schemas each define them. Generated output can be byte-identical while behaviour differs; `check-rpc-semantic-parity` currently fails at 114 opaque response schemas against a ceiling of 110. Business rules have already diverged: the workflow cron editor accepts `L` and `#`, the Rust daemon rejects them, and the failure is swallowed by `safeInvoke`.
- **Execution has about 17 paths:** two sidecar engines, 14 external protocol adapters and the completion rail. Their process, session, approval, cancellation and recovery ownership is implicit. Some caps protect real native resources, such as the Python host's semaphore; they are not business admission.
- **Standalone mode executes.** An unpaired phone and a browser with no Companion run chat turns in the WebView with the user's own keys (`lib/ai/chat/standalone-engine.ts`, 400 lines).
- **The dual-host safety net is thin.** 200 e2e specs exist, 24 of them for Tauri. Only 2 run against a real Web↔headless stack, and the Compose tier that runs them is not on the pull-request path.

## Decision

### 1. One kernel and one data authority per host

The **kernel** is every long-running behaviour: schedulers, delivery runners, recovery, connectors, bots, sync, chat turn orchestration, steering, background results, wakeups and watchers.

- It is registered as `HeadlessRuntime` entries in `lib/headless/registry.ts`.
- A host runs exactly one kernel.
- That kernel is the only writer of the host's application data.

### 2. Where the desktop runs its kernel

**Decision: the kernel runs in the WebView (2b).** The desktop keeps its single-process shape and meets four requirements explicitly:
- **One owner per process.** The kernel is started once per desktop process, by the main window or an elected leader. It has a start, a cancel, and an awaited teardown, all safe under StrictMode replay. Secondary windows are clients of that owner, never second kernels.
- **Account lifecycle.** The kernel joins the account and runtime-target lifecycle through `registerRuntimeTargetCleanup`. A lock or an account switch waits for the kernel's teardown before the database selection changes.
- **A host adapter matrix.** Each registry entry states how it is assembled on each host; the matrix lives in `docs/research/` (phase 0a A5). A brain entry cannot be reused on the desktop by swapping the bridge, because the event publisher, the connector server lifecycle and the plugin adapters differ. Parity between the desktop and a Host is held by the one registry, this matrix, and the dual-host lane (§12).
- **A storage budget for heavy accounts.** Today's WebView path is slow at scale. On a 200,000-message dataset, the first sidebar list arrives 5.6–6.8 s after a cold open, and the session-list p95 is 630–785 ms. Phase 2 carries its own budget for that path.

**Rejected for now: the desktop runs a local brain (2a).** Spike S1 measured 2a against ranges fixed before any measurement. The evidence ledger is `docs/evidence/2026-11-01-convergence-s1.md` on branch `spike/local-brain-s1`.
- **Storage passed.** The brain store was faster than the WebView on every operation. On the heavy dataset, the session-list p95 was about 50 ms, against about 700 ms for the WebView.
- **Startup and memory failed by a wide margin, for structural reasons.**
  - Added cold start was about +3.0 s on a real-sized account and about +37 s on the heavy one. The ranges were +0.8 s and +2.5 s.
  - Idle memory was 883 MB and 3.8 GB. The ranges were 400 MB and 800 MB.
  - The causes are fixed costs. An empty brain already needs 2.5 s and 669 MB to load its module graph, and the store restores every row into memory on boot.
  - Meeting the ranges needs an on-disk brain store and a much smaller module graph. Phase 2 cannot credibly deliver either.
- **More work besides.** 2a would also need:
  - the desktop's renderer fallback in `DataPlane::pick` removed;
  - four new brain-to-Tauri adapters: `browser_local_rpc`, `proxy_http_request`, `ocr_http_fetch` and `perf_start_sampling`;
  - several host stores re-homed.

**Reversal trigger.** Revisit 2a when both of these hold:
- A disk-backed brain store, with a reduced module graph, measures inside the S1 startup and memory ranges on both datasets.
- Non-JSON values round-trip through brain durability.

### 3. Clients and the standalone path

- **Paired devices** (mobile and browser with a Companion target) are clients of a host's kernel.
- **The standalone path is not part of the kernel.** An unpaired phone and a browser with no Companion target keep a lightweight BYOK path (`lib/ai/chat/standalone-engine.ts`).
  - Its capability list is stated (chat, search, documents) and pinned by a test.
  - It reuses the kernel's pure libraries: provider resolution, prompt composition, event mapping.
  - The kernel does not have to run in a browser for it.

### 4. One authority; clients queue intents

- **No silent fallback writes.** A host never writes application data to a fallback authority when its kernel is unavailable. The `Direct` branch of `DataPlane::pick` becomes read-only or reports the host unavailable.
- **A remote Host's brain is supervised.** `cognia-server` restarts it, and clients show a disconnected state while it is down.
- **Clients queue intents.** A client that cannot reach its host keeps what the person did as intents, not data, following the `mobileOutboundQueue` pattern. It replays them with idempotency keys when the host returns, and the host accepts or refuses each one. There is no second copy of the data to reconcile.

### 5. Kernel rules

- **No React.** Kernel code imports no React and nothing from `@/components/` or `@/hooks/`.
- **State has one owner.** State the kernel decides on is owned by the kernel, in its stores or database. A Zustand store holding domain state the kernel needs moves into the kernel, and UI stores subscribe to the kernel. Imperative reads of UI stores from kernel code are ratcheted to zero.
- **No "when it next opens".** A behaviour that must happen does so when its trigger happens.
- **One chat engine.** Chat turn orchestration is one kernel module, `lib/runtime/chat-engine/`. The desktop and TUI clients drive it through the host; duplicates are deleted.

### 6. Shared primitives

1. **Durable queue.**
   - Provides lease and claim, a due time with a scheduled wake, retry through `decideNextAttempt`, a dead-letter state, a unique idempotency key and an inspection view.
   - Queues in separate databases (for example `fusionOutbox`) migrate too.
   - Existing rows are upgraded, never hidden by a new index.
2. **Admission limiter, for business admission only.**
   - Origin-aware (ADR-0248), with a reserved person permit, two bands, and stops never queued.
   - Native resource backpressure stays where it protects a real resource, such as the Python host semaphore, sandbox pool slots and node install slots. It is listed in an inventory with its owner, and it is not migrated.
3. **Run ledger.** `executionRuns` is the only record of a run. Engine tables point at it by a real reference, not a field that happens to be named `runId`. Inside the kernel, success is spelled `completed`.
4. **Commitment** (ADR-0247). A thread followed by a commitment as owner has exactly one executor: the commitment.

### 7. Execution ownership

Each execution path declares one owner for each of its process, session, tool approval, cancellation, recovery and drain:
- the two sidecar engines;
- each external protocol adapter;
- the completion rail.

The declaration is an engine/host port contract, checked by a test per path. Merging paths is out of scope; making ownership explicit is not.

### 8. Contracts and shared business rules

- **One authority per contract kind.** Each kind of contract names its authoritative source: command signatures, requests, responses, events, errors, cancellation.
- **Cross-language fixtures.** Behavioural parity is checked with fixtures built from real serialization on both sides, not only by comparing generated bytes.
- **Shared business rules have shared test vectors.** This covers rules that exist in both TypeScript and Rust: cron, time zones, status vocabularies, serialization.
- **Failures are not swallowed.** A required registration or persistence call that fails is surfaced as a health state, never returned as `null`. The workflow cron divergence is the first case fixed.

### 9. Plugins: a new contract in one cutover

- **What breaks.** The plugin author API is replaced, not extended:
  - **Scope:** TypeScript, Python and WASM move to one new contract with a host layer (runs in the kernel) and a UI layer (runs in a client).
  - **Old contracts** are frozen and archived the way WASM `cognia:plugin@0.1.0` was.
  - **Untouched:** the VS Code extension compatibility layer, which follows VS Code's own API.
- **Whom it affects.** Only first-party plugins are migrated; there are no external authors to support.
- **When.** The cutover happens with phase 2, when the kernel moves.
- **Host-side UI calls.** A plugin running on the host that asks for UI work, such as a dialog or a selection change, is routed to an online client. With no client online, the call fails with a named error.
- **One schema with modules.** A plugin's host layer and UI layer are the two data-only manifests a module declares (§14). The plugin contract extends that schema with what only a plugin needs: packaging, signature, permissions and versioning. It does not define a second shape.
- **The host API follows its owners.** The 52 feature namespaces of today's plugin host API move to the modules that own them, each contributed through the module's `pluginApi` field, in the same cutover. The plugin host itself (dispatch, permission gate, bridges, lifecycle) stays in the kernel.
- **A module becomes a plugin only when it can.** After the cutover, a module moves out as a plugin (§14, M4) only when all three hold:
  - every host dependency it has is within the surface the plugin contract exposes;
  - no other module imports it;
  - its tables are settled. Plugin tables are namespaced `${pluginId}:${tableName}` (`lib/plugin/dexie/namespace.ts`), so turning a core table into a plugin table renames it, which is a data migration. Each such module gets its own decision: drop the old data, migrate it explicitly, or keep the core table and grant the plugin access.
  - A module that needs Rust windows or host commands of its own stays a module, because a plugin cannot carry that code.
- **The contract itself** is its own ADR, written during phases 0a and 1 from the plugin API matrix (§13).

### 10. Chokepoints a gate can enumerate

These are each reached through one module, and a gate lists every call site:
- outbound review planning;
- connector delivery;
- network egress;
- PII redaction before a model call;
- resume authority checks, live per ADR-0243 §2 and ADR-0247 §7.

Shadow modes switch to enforce per category only after their gate shows full coverage. Enforcement decisions are persisted with the work they authorize, so a mode switch never has to guess what was decided earlier.

### 11. Ratchets that cannot be quietly raised

- **Reproducible inventories.** Baselines are inventories with members (file, symbol, table and owner), produced by a committed counter at a recorded commit. They are not heuristic counts.
- **Baselines cannot grow quietly.** `scripts/gates/check-convergence.mjs` fails when a count rises. A baseline check compares every ratchet file against the merge base and fails on growth, unless the PR carries an exception record with an owner and a repayment phase.
- **The headless-registry gate** keeps its "called inside the reachable set" rule and widens only which symbols it considers.

| Metric | Baseline (to be fixed by phase 0a's counter) |
| --- | --- |
| Runtime-owning initializers with no registry entry and no exclusion | ≤ 32 (member list in 0a) |
| `check-host-parity` findings | 200 (A 96, C 104) |
| `lib/` files using `@/stores/` imperatively | 294 static / 409 with dynamic imports |
| `lib/` files importing `@/hooks/` or `@/components/` | 64 static / 74 with dynamic imports |
| Durable queues not on the primitive | inventory in 0a (~17) |
| Business caps not on the limiter | inventory in 0a (~22 total caps, native ones listed separately) |
| Run-like tables without a real `executionRuns` reference | inventory in 0a |

### 12. How a piece moves

1. **Characterize** it on both hosts, using the dual-host harness from phase 0a. Changes to the kernel or to contracts run a blocking brain integration lane on pull requests.
2. **Move** it, and **delete** the old path in the same phase.
3. **Lower the baseline.**

Each phase has its own worktree branch and evidence ledger. Codex does the mechanical migrations in batches; Claude does architecture, extraction and review. About half of capacity goes to convergence until phase 4 exits. Features continue on the new primitives, and phase 0 gates block the old way.

### 14. Feature modules and generated registries

§5 says what the kernel must not import. This section says how everything outside the kernel is cut, so that adding a feature stops meaning editing shared files.

**Why.** The feature-module analysis measured this at 2026-11-04:
- **The coupling is a mesh, not a few hubs.** 150 of the 176 `lib/` subsystems sit in one strongly connected component. Removing the 15 subsystems that shrink it most still leaves 86. Splitting god files does not fix this; a direction rule with a gate does.
- **Features edit shared files.** 37% of the feat commits in the last 60 days touched at least one central registry, 32% without the companion catalog. Adding one settings section edits five places.
- **Three sinks act as a bus.** The settings store has 530 direct importers and `SettingsState` has 151 members. 88 of the 210 data modules in `lib/db` have a single user. The plugin host API reaches 82 subsystems.
- **The plugin boundary held.** No first-party plugin imports `@/`. What is missing is a module boundary inside the app.

**Five classes.** Each subsystem is in exactly one:
- **Foundation:** plumbing with no business meaning: UI primitives, utilities, the database instance, platform and transport bridges, logging, errors.
- **Kernel:** §1's kernel and what every feature depends on: sessions and messages, the send pipeline, model gateway and credentials, agent execution, the run ledger, identity and accounts, workspaces, sync, storage, queue and scheduling primitives, authorization, the plugin host, settings infrastructure. The kernel is a closed list. The per-subsystem record is in the analysis (§11 there), and adding a member amends this ADR.
- **Shell:** aggregation and navigation that nothing depends on: the settings UI, initializers, `app/me`, the desktop and mobile shells, global search, slash commands, headless assembly.
- **Module:** every other feature, compiled in and running in the same process. A subsystem the kernel list does not name is a module.
- **Plugin candidate:** a module that implements a capability port or is an optional app. It stays a module until §9's extraction rule lets it out.

Dependencies point one way. Foundation depends on nothing above it; the kernel depends on no module, plugin candidate or shell; a module depends on no shell.

**Two data-only manifests per module.**
- **Host layer:** `lib/<id>/module.ts`, through `defineHostModule`. **UI layer:** `components/<id>/module.ui.ts`, through `defineUiModule`. They are the same two layers as §9's plugin contract.
- **Data only.** A manifest imports only its `define*` helper. Its top level holds literals and lazy entries `() => import("…")`, never a schema, defaults or a side effect. Every host imports the generated registries statically, and S1 already showed that the eager module graph is a budget (§2).
- **Identity and lifecycle:** `id`, `kind`, `stage` (`kernel`, `stable`, `beta`, `experimental`, `deprecated`), `owner` (a team in `.github/CODEOWNERS`), `acceptance.realSmoke` (`pending` or `passed:<date>`).
- **Boundary:** `owns` (paths beyond the default `{lib,components,hooks,stores,types,app}/<id>/**`), `dependsOn`, `api`, `provides` and `requires` (capability ports).
- **Host contributions:** `runtimes`, `settings.keys`, `tables`, `tools`, `capabilityContributions`, `taskExecutors`, `builtinSkills`, `pluginApi`, `workflowNodes`, `searchProviders`, `slashCommands`, `nav`, `prompts`, `flags`, `messages`.
- **UI contributions:** `slots` (named from `CANONICAL_EXTENSION_POINTS`), `settingsSections`, `effects`.

Where an existing rule already owns a field, the field follows that rule:
- **`runtimes`** declare a runtime's identity and criticality, plus one adapter per host: §2's adapter matrix, written as data. Each adapter is a module specifier. The brain adapter keeps `HeadlessRuntime.start`'s signature and names the brain profiles it starts on (`hosts`). `HeadlessHost` (`brain`, `person-brain`) is not widened to make the desktop look like a brain.
- **`effects`** hold side effects that need React context, the router, i18n or toasts. They are not runtimes. The `runtime-initializers` inventory decides which an initializer is.
- **`settings.keys`** declare which flat `AppSettings` keys a module owns. The wire does not change, and `packages/agent-config-types/src/settings-sync.ts` stays the sync source. A module reads its own keys through a view. ADR-0068's S5 store slicing cuts along this ownership.
- **`capabilityContributions`** produce `AgentCapabilityGrantV1` only, applied stage by stage by the existing resolver chain (ADR-0198). There is no ordering number and no patching of `SendOptions`. A contribution that needs a new stage amends ADR-0198 first.
- **`tables`** declare ownership only. The schema stays in `CURRENT_SCHEMA`, so adding a table still edits `lib/db/schema.ts` and the governance catalog. That is the accepted cost of one Dexie version.
- **`tools`** carry their permission rules: each tool's consent and effect are declared as data, and the kernel derives the ruleset from them (amended below, M3). **`taskExecutors`** declare an executor together with its task source.
- **Dormancy on three axes (Rule 7).** `stage`, the inert label the UI shows for a disabled module, and a test over the generated registry. An `experimental` module is off the navigation and starts no runtime. A disabled module starts no runtime, is hidden from navigation, shows "disabled" on its routes and keeps its tables.

**Generated registries, never committed.**
- `scripts/build/gen-module-registry.mjs` generates one registry per host: `lib/modules/generated/{brain,desktop,mobile}.ts` and `components/modules/generated/ui.ts`. They hold lazy entries only. Per host, so the brain never sees a desktop-only entry.
- The host layer is one host-neutral `lib/modules/generated/host.ts`. Every field in it applies on every host, and a settings section's reachability is decided at runtime by its `requires` and `profiles`, as for a built-in one. `runtimes.adapters`, the first field that differs by host, did not split it (M2): an adapter is a specifier, and the generator writes each host's lazy imports into that host's own runtime registry. `host.ts` and `ui.ts` import the manifests themselves, which are data plus lazy entries, and `lib/modules/registry.ts` and `components/modules/registry.ts` are what the shells read.
- They are gitignored and generated by `postinstall`, `predev`, `prebuild`, `prestorybook`, `scripts/test/jest.mjs`, `typecheck-root.mjs` and the CLI builds, which the brain's Docker build and CI run. A committed aggregate would conflict, as the committed companion catalog does today. In a shared working tree, regenerating it would also write other sessions' uncommitted manifests into the commit.
- Registries move in order. Settings sections, search providers and slash commands in M1. Slots, navigation, runtimes with effects, and table ownership in M2. Prompts, capability contributions and settings keys in M3. The plugin host API with §9.
- Once a registry is generated, a hand-written entry in it fails G5.
- **What M1 settled for its three registries.**
  - A slash command's descriptor is data in the manifest and its handler is a lazy `load`. It joins `BUILTIN_SLASH_COMMANDS` with scope `builtin`, so every surface that lists built-ins lists it.
  - A search provider loads lazily and registers beside the built-ins. The dialog re-runs its query when it arrives, and a headless search waits for it. A provider's `kind` stays in the search vocabulary (`lib/global-search/types.ts`). A module adding a new kind adds it there, as it would add a type.
  - A settings section's metadata (group, a Lucide icon name, `after`, `requires`, `profiles`, layout, keywords) is data, and its strings are full keys in the module's own namespace. A section id is typed from its manifest; the plugin contract's `SettingsSectionId` lists only the sections plugins may open.
  - Dormancy: an `experimental` module contributes nothing to these three surfaces, and a deep link to its section says the section is off.
- **What the `eval` pilot settled for the ownership table.**
  - A module whose code sits under another subsystem's directory claims it with `owns` in its manifest, and its table row and path overrides go in the same change (G1 refuses both at once). For `eval`, the row and the `lib/ai/eval/` and `lib/plugin/eval/` overrides became claims; every file kept its owner and G2 gained no edge.
  - The manifest can live at `lib/<id>/module.ts` before any code moves there. Moving code is a separate change with its own reason.

**How modules talk.**
- **Public API files.** A module imports another module only through the concrete files listed in its `api`, plus `types/<id>/**`. There are no barrels, as `check-root-loading-boundaries` already requires. The target must be in `dependsOn`, and the `dependsOn` graph has no cycle.
- **Capability ports.** The kernel defines a port, a module or plugin `provides` an implementation and a consumer `requires` it. Ports so far: `ocr`, `speech`, `web-reader`, `web-search`, `docs-provider`, `forge`, `remote-desktop`, sandbox backends, IM adapters, and subscription, balance and model-catalog. A port follows the shape of ADR-0246's granted connections.
- **Typed events.** For an inverted dependency, the kernel's event bus carries events the publisher declares in `types/<id>/events.ts`.
- **Contribution points.** The shell and the kernel collect from modules only through manifest fields.

**Ownership before moves.** Every non-test source file has exactly one owner: a module, a kernel member, the foundation or the shell. A transitional ownership table covers what no manifest claims yet, and its row count is a ratchet. Files move only when their module is next changed, so the shared tree never takes a mass rename.

**Vendors in three layers.** A vendor is never one unit. It is split by what each piece is:

| Layer | Holds | Form | May depend on |
| --- | --- | --- | --- |
| 1. Protocol library | API client, signing and verification, paging, error mapping, data types. No business logic, no credentials, no state | A package with no `@/` imports, such as `packages/feishu-protocol`. Rust parts stay in their crate | Foundation only |
| 2. Auth provider | Sign-in, account, refresh, rotation, sign-out, callback, such as `auth.feishu` | A base plugin (`feishu-auth`) or a built-in Rust provider (`auth.google`) | Its protocol library |
| 3. Business implementations | One per capability port: IM adapter, cloud documents, issue sync, calendar, backup, OCR | Owned by the module of its port, or a plugin | Credentials only through an ADR-0246 granted connection; imports only the protocol library; never another business implementation |

- The protocol library is a package rather than a library plugin because ADR-0246 has not defined how a library plugin serves business plugins (interface version, account scope). Holding no credentials and no state keeps it safe to share.
- **Feishu goes first (M1).** `packages/feishu-protocol` holds the deployments, scopes, PKCE, the OAuth and tenant-token requests, the response envelope, the error codes and paging, over a transport the caller passes. The auth layer is `lib/auth-providers/feishu/`, beside `auth.google`: the token cache, user-token refresh and retry wrappers, OAuth begin, pending record and callback, the Host connection provider and the authed API that cloud documents, issue sync and Twin read through. The connectors host bridge it calls (the connectors crate's Tauri bindings, its event listener, server ingress and credential-rotation events) depends only on the foundation, so the ownership table files it with `tauri`, and the connector OAuth state key and scope audit with `oauth`. Moving the layer added no G2 edge and repaid eight. The package is source-only, resolved through the `@cognia/feishu-protocol` path alias. It stays out of the pnpm workspace for now, because a new workspace member adds a lockfile importer and that invalidates the plugin authoring-kit pin. It joins at the next kit repin.
- **Frameworks are vendor-neutral.** The IM, cloud-document, issue-sync, backup and scheduling frameworks name no vendor and import no vendor implementation. Vendor-specific behaviour, such as Feishu's run-presentation driver, is a contribution the business implementation makes. G8 holds this. In the IM framework the contribution is `ConnectorVendorContribution` (`lib/connectors/vendor-contribution.ts`): what the framework needs without a live adapter at hand, such as static capabilities, the adapter factory, the identity probe, OAuth completion, the passive ping, avatars, startup services, command and approval cards, the final-answer cards, run cards and the principal registry. A live adapter's own hooks stay on `PlatformAdapter`. Each framework reads its implementations from one catalog beside them (`lib/connectors/adapters/_vendors.ts`, `lib/docs-providers/providers/_builtin.ts` and `_document-urls.ts`), which may import only each implementation's entry file. A contribution imports light constants eagerly and loads the rest inside its hooks. M1 did Feishu: its builders, web entry and clients, run cards and principal registry moved under `lib/connectors/adapters/lark/`, and its document URL parser into the Feishu docs provider. The seam is host-internal and not part of the plugin contract.
- **Shipping a vendor's set.** One-click "everything for vendor X" is a cogset (ADR-0209): a distribution bundle, not a code dependency.
- The same split applies to Google (protocol, `auth.google`, Drive backup and Docs), GitHub (protocol from `octokit-factory` and `auth-app`, the GitHub connection, `forge` implementations, `backup-github`, the runner) and each subscription vendor (protocol, sign-in, then subscription, balance and model-catalog implementations).

## Consequences

- **The desktop and a Host stay two hosts of one kernel.** They boot the same registry in different processes. Parity therefore depends on the adapter matrix and the dual-host lane, not on running the same binary. In exchange, the desktop avoids a second process, the startup cost and a data migration.
- **S1 exposed known costs in the always-on host's brain.** On a heavy account, it takes about 37 s to serve again after a crash and holds about 3.8 GB resident. Durability also lost non-JSON values, which phase 0b fixes. A disk-backed brain store is follow-up work for ADR-0224 hosts, and it is also the precondition for revisiting 2a.
- **Plugins break once,** in phase 2. First-party plugins are rewritten then; the old contracts stay readable as frozen history.
- **About half of capacity** goes to convergence for several months. Progress is measured against inventories that cannot be quietly raised.
- **Some behaviours change.** Behaviour that worked only because a window was open will now happen when its trigger happens. Writes during an outage now wait as intents instead of landing in a fallback store. Each change is recorded in its phase's evidence ledger.
