## Context

Slices ① and ② of the tracker (Dexie v170 / v171: projects, issues, events, counters, labels, GitHub mirror, `/issues` `/projects` `/workspace` routes) shipped with the **types, i18n keys and UI placeholders of slice ③ already present** — `canRun`, the four `run_*` / `artifact_linked` event kinds, the `agent-team` / `agent-task` source ids, the "N agents working" tile, the "My agents" view — but nothing produced them. This is the repository's recurrent "built but dormant" pattern, and an audit against the original intent (the Multica plan, ADR-0066/0086/0111/0113/0018, the shipped changesets and message bundles) listed the gaps precisely:

- "N agents working" was a hard-coded `0`; "My agents" had an empty `agentKeys` and could never match.
- Two declared federated sources had no adapter; `canRun` had no consumer; `lib/issues/run/` did not exist.
- `/workspace` linked to Settings instead of opening the one workspace editor (`WorkspaceManageDialog`), and showed neither trust state nor running agents.
- No ⌘K provider, no ADR (the type file cited one that did not exist), no assignee picker, `WorkItemRefV1.kind` had no `"issue"`.
- Slice ③ as a whole — notifications, IM cards, filing from chat — was unbuilt.
- Adjacent workspace/team gaps: `WorktreeCreate` / `WorktreeRemove` had four declarations and zero producers; Agent Teams created before v86 had no `projectId` and leaked across workspaces; a dormant `lib/terminal/collaboration` share model (see ADR-0133); a stale `project-store` docblock; an e2b workspace-backend shim whose `else` branch was unreachable and whose lookup used the wrong id prefix.

Non-goals, unchanged from slice ①/②: GitHub Projects v2 / milestones, bidirectional field sync, per-project **custom columns**, **saved views**, **mobile writes**, free-text tag refactor, an MCP bridge, an IM `/issue` slash command, a Managed Workspaces page (deliberate debt), external-agent assignees. Section 7 adds view *preferences* and column *collapse*, which are display state over the fixed six columns and the four built-in views — neither introduces a new column nor a new view.

## Decision

### 1. Terms and invariants

`Workspace = Project` (`types/plugin/_compat.ts`), which owns `WorkspaceRoot[]`, `IssueProject[]`, `Issue[]` and `AgentTeam[]`. An issue's **assignee** is an `IssueActor`: `human`, `agent` (= a `Character` id) or `team` (= an `AgentTeam` id); anything else is refused by the picker and the IM handler. The board's six columns are fixed. **Triage is an attribute, not a seventh column** (2026-09-29): `Issue.triage = "pending"` marks an issue whose status and assignee are a proposal nobody accepted yet. It changes no column and no category projection; what it changes is who may start a run — `trackerVerdict` refuses origins a door derived (`im`, `wakeup`) with `issue-in-triage` and lets a run a person names in the Run dialog (`interactive`) through (`isNamedRunOrigin`). Accepting clears it through the same bulk-action vocabulary as every other edit, and releases wakeup inputs held meanwhile. GitHub import mode can file new open, unassigned issues into triage (`GithubRepoSyncSettings.triageNewIssues`). Every programmatic face (`ctx.issues`, the workflow nodes, a paired phone's `issue_apply_action` / `issue_create`, the External Bridge) sets `triage` and the sub-issue `stage` through those same actions, with one exception: the External Bridge may send an issue into triage but is refused accepting one out, because an external agent granting the acceptance the gate waits for would defeat the gate. Human moves go through `lib/issues/state-machine.ts`. **The runtime owns `in_progress` while a run is in flight** — `moveIssue` reads the issue's active run inside its own transaction and refuses moves both into and out of that column (§8) — but with no run in flight a human may move an issue there like any other column. (An earlier revision of this ADR said "a human can never move an issue there", which the guard never implemented and which the guard's own docblock argues against: "an issue tracker should not argue with its user". The code is the decision; this wording now matches it.) A settled run parks the issue at `in_review`, never `done`; a cancelled run hands it back to the column it held before the run (`statusBefore`), recorded as `run_cancelled` (§8). The run bridge's settle (`settleIssueRunAndIssue`, over `applyRuntimeIssueStatus` / `handBackRuntimeIssueStatus` in `lib/db/issues.ts`) is the only writer of runtime transitions.

### 2. Execution bridge — `issueRuns` (Dexie **v174**) and `IssueRunAdapter`

`lib/db/issue-runs.ts` adds the `issueRuns` table (`&id, issueId, [issueId+status], projectId, [projectId+status], adapterId, kind, targetId, status, startedAt, updatedAt`) — the **issue side is the single source of truth** for "which runs belong to this issue"; execution engines are never widened with an `issueId` column, so a new engine binds without a schema bump (`AgentTeamTask.metadata.issueId` is a reverse convenience only). Claimed as v174 rather than v172 because two concurrent branches hold v172 (ADR-0130) and v173; Dexie tolerates the gap.

`lib/issues/run/registry.ts` defines `IssueRunAdapter { id, kind, canRun(issue, project) → verdict, start(issue, ctx) → IssueRun, cancel(runId) }` with `registerIssueRunAdapter` / `listIssueRunOptions` / `startIssueRun` (refuse-or-dispatch; **dispatch failures throw**, they are never swallowed). Three adapters ship: `agent-task` (`createAgentTask` → `startAgentTaskNow`, which resolves once the Scheduler accepted the task, not when it settles), `agent-team` (`createTask({ metadata: { issueId } })` + `startSquadRun`, the one Squad funnel of ADR-0140; artifacts from delivery nodes / child-run workspace paths), and `github-loop` (only when the project holds a `github-repo` resource; runs `executeIntegrationAction("runIssueLoop")` under the `awaiting_approval` gate; desktop only). `running.ts` exposes `listRunningIssueIds()` and `viewerAgentKeys()` (all Characters + AgentTeams as `agent:<id>` / `team:<id>`), so "My agents" includes *every* agent/team assignee in a single-user app. No adapter is settled by its engine calling back. `installIssueRunBridge` (`lib/issues/run/install.ts`) asks each adapter to `poll` whenever something a run points at changes — a Dexie `liveQuery` over the `agentTasks` and `integrationActionJobs` rows and the Squad run records, and a subscription on the AgentTeam store — plus a slow safety interval and one reconcile at boot. (Revised 2026-11, §8: earlier wording named a `liveQuery` on `agentTaskAttempts` and the completion sink `team-completion-linkage.ts`; the bridge reads neither.)

### 3. Federated sources

`lib/issues/sources/{agent-task-source,agent-team-source}.ts` implement the two declared `IssueSourceAdapter`s **read-only** (`READ_ONLY_ISSUE_CAPABILITIES`), mapping engine states through one table (`agent-status-map.ts`: `pending→backlog`, `blocked/claimed→todo`, `in_progress/paused→in_progress`, `review→in_review`, `completed→done`, `failed/cancelled→canceled`) and deep-linking back to the native page. Federated rows render on the board by default with a source badge and a toolbar source facet; a row that carries an `issueId` (metadata or `issueRuns.targetId`) is badged "from KEY-1".

### 4. UI

`issue-console.tsx` reads the live viewer (`viewerAgentKeys`) and running set; a new `assignee-picker.tsx` (Characters + AgentTeams + me + unassigned) is wired into create and detail; `run-issue-dialog.tsx` is the `canRun` consumer (mode = local AgentTask default / AgentTeam / GitHub loop) and the detail panel shows run history, artifacts and cancel. `/workspace` mounts `WorkspaceManageDialog` directly (one editor, two entry points), shows trust state per root (`lib/db/trusted-workspaces.ts`) and a live agents-working tile. ⌘K gains `lib/global-search/providers/issues.ts` (kind `issue`); `WorkItemRefV1.kind` gains `"issue"`.

### 5. Notifications and IM (slice ③)

`lib/issues/notify.ts` projects issue events onto the Notification Center (`NotificationSource` `issue`, command `issue.open`) for: assigned / reassigned, run succeeded / failed, arrival at `in_review` / `done` / `canceled`, and comments by someone other than the viewer. A `liveQuery` watcher with a fixed watermark plus a seen-set never skips events; when the issue originated from an IM conversation (`Issue.origin = { kind: "im", conversationKey, messageId? }`) or a conversation is bound to the project (`ConversationOverrideRow.issueProjectId`) the same event is pushed back over IM through the governed queue, gated by the conversation's proactive-push opt-in and `hasNoLeakingPii`.

IM cards (`lib/issues/im/card.ts`) are pure A2UI builders: exactly the **legal human moves** (which excludes `in_progress` only while a run holds the issue), a **Run** button when an engine can take the issue, and an **Open** link; a numbered mirror serves button-less channels. Buttons carry `bindingKind: "issue_action"` + payload via `bindingHintFields` (shared by the Discord / Telegram / Slack / WeCom / Lark mappers) so a click reaches `lib/issues/im/callback-handler.ts` (a `ConnectorBus` short-circuit before `tool_approve`) instead of a model turn. Move / run buttons stay re-clickable; only the create-confirmation card is consume-once. Filing from chat is the built-in skill `issue.create` (write level, `hitlSurface`): the confirmation card lists ≤ 5 projects, the conversation's remembered choice first, and **nothing is written until a project button is pressed**; `issue_list_projects` resolves names. Lark and Slack inbound now carry `replyTo` so quote-to-issue works there as it did on Telegram / Discord. A click answers to the **sender half of the conversation's trigger policy** before the handler runs (`senderTriggerRefusal` in `lib/connectors/policy-eval.ts`, resolved bot → character → conversation override as an inbound turn is): a sender a `user-blocklist` names, or one missing from a bot that only answers `user-allowlist`s, cannot move or run an issue by clicking either, and a click with no bot row to read is refused (2026-09-30). The permission ceiling (`buildImPermissionCeiling`) only narrows a run's tools; it is not this gate. New audit kinds: `issue.card_action`, `issue.card_action_denied`, `issue.im_pii_blocked`.

### 6. Adjacent workspace / team gaps closed in the same change

- **Worktree hooks fire** (ADR-0111 decision 9, wording revised there): the Registry emits through `WorktreeLifecycleSink` (Rust) and `lib/git/commands.ts` fires after `git_worktree_add/remove` (TS) — two producers because the Registry does not sit in front of the Agent Team allocator or the source-control panel. Observational only.
- **Pre-v86 AgentTeams** get `projectId = DEFAULT_PROJECT_ID` (persist v7 `backfillTeamProjectIds`, applied in `migrate` and in `activateAgentTeamAccountStorage`); `updateTeam` stamps it; the mode selector drops its `!t.projectId` escape hatch.
- **e2b**: `resolveWorkspaceBackendByKind` (exact id, then `:<kind>` suffix) replaces the `"e2b"` lookup that never matched the registered `cognia-e2b-sandbox:e2b`; the `setE2BBackend/getE2BBackend` shim and the unreachable plugin branch are removed. `project-store` docblock corrected.

### 7. Surface rebuild (2026-08-22)

A second audit — this time of what the UI could actually reach — found **twelve exports with no non-test caller anywhere in the app**: `updateIssue`, `addIssueLabel`, `removeIssueLabel`, `addIssueComment`, `moveIssueToProject`, `deleteIssue`, `linkIssueToGithub`, `countIssuesByStatus`, `updateIssueProject`, `deleteIssueProject`, `computeIssueProjectProgress`, `reorderLabels`. The read and run paths of §2–§5 were fully wired; the **edit** path existed only in the data layer. Three consequences were user-visible:

- A workspace got **one `IssueProject`, ever**. The only `createIssueProject` caller was the create-issue dialog's `projects.length === 0` branch, `/projects` had no create button, and `deleteIssueProject` had no caller — so the count could never fall back to zero.
- An issue could not be renamed, re-described, re-prioritised, labelled, moved between containers, deleted, or commented on locally after creation.
- **No label chip could render anywhere.** Local issues could never acquire a label; GitHub rows carry synthetic `github:<name>` ids with no row in the `labels` table, so every chip was filtered out while the filter menu fell through to `?? labelId` and displayed the raw string.

Decisions taken in the rebuild:

- **One action vocabulary, one gate.** `lib/issues/bulk-actions.ts:IssueBulkAction` expresses every edit whether it lands on one issue or twelve, and `canApplyBulkAction` gates each item on its own `capabilities` before any write. Outcomes are **counted** (`applied` / `skipped` / `failed`), never assumed. `lib/issues/menu-model.ts` decides what a menu offers, what is disabled and what is ticked — the context menu, the bulk toolbar and the inspector all render it.
- **`title` and `description` are in the vocabulary but excluded from `menu-model`**, so they can never appear in a bulk menu.
- **GitHub labels are never materialised.** `lib/issues/github-label-display.ts` builds ephemeral display rows for `github:*` ids, merged into the catalogue for rendering and filtering only. Every *write* menu receives local labels alone — applying a synthetic id to a local issue would store a reference resolvable only while that GitHub row happened to be on the board.
- **Layout.** `/issues` gains a rail (views, containers, labels) in `FeaturePageShell`'s left pane and a filter bar carrying a removable chip per engaged facet; the header returns to one row. Everything had previously been crammed into `FeaturePageHeader`'s single `controls` slot, which renders inside `overflow-x-auto` with the scrollbar hidden — so on a narrow window the right-hand controls scrolled off the edge with nothing on screen to say so.
- **View preferences persist per view** (`stores/issues/issue-view-store.ts`). Overrides are partial and fall back to the `IssueViewDefinition`, because the four built-ins declare different defaults and a single global set would fight them. Column collapse is one field with three states per column: absent means "collapse iff empty", present is the user's explicit decision.
- **`/projects` is a master-detail console** — a table (name, key, status, lead, target date, progress, issue count), an inspector that writes all eight editable fields, create, and a delete that states the issue count because the cascade takes every issue, event and run with it. `key` stays immutable; every printed identifier embeds it.
- **Drag layering.** The dragged card rides a `<DragOverlay>` portaled to `document.body` at `zIndex 60`. In place it was clipped by the column's `overflow-y-auto` and the board's `overflow-x-auto`, and painted *under* later columns because `opacity < 1` opens a stacking context at `z-auto`. `components/agent/workspace/board/task-board.tsx` had the identical defect and is fixed the same way.
- **Keyboard.** The board's `KeyboardSensor` claims Space alone so Enter stays free to open a card, and horizontal movement is resolved against the columns in lifecycle order — dnd-kit's `sortableKeyboardCoordinates` assumes one sortable list and mis-targets on six side by side.
- **Two of the twelve were removed rather than wired.** `countIssuesByStatus`'s only plausible consumer was the rail's counts, and it reads only the local table, so it could never have agreed with the federated board beside it. `computeIssueProjectProgress` ran one query per container for a tally both real consumers get in a single pass over issues they already hold; `lib/issues/project-progress.ts` is the one implementation. The other ten now have a UI path, including `linkIssueToGithub` — without it the `github-loop` adapter refused every issue not created by the GitHub sync, because nothing in the app could set a `githubRef`.
- **Label catalogue management** is generalised out of Settings → Connections → Labels rather than copied. `colorMode` distinguishes the scopes: conversation labels store free hex, issue labels store oklch theme tokens, and a native colour input would silently rewrite one as the other.
- Mobile stays read-only, and now says so: rows open a read-only sheet instead of tinting a row nothing could open, and `/projects` gains a mobile body it never had.

### 8. 2026-11 state-flow revision

A third audit, this time of the **state flow** (what moves an issue between columns, who may do it, and when the rest of the app hears about it), found races and gaps that the type checker and adapter-mocking tests could not see: two runs could start on one issue; the run lock was a `runActive` argument callers had to remember to pass; a crash between settling a run and moving its issue left the issue stuck in `in_progress`; a cancel always dropped the issue in `todo`; events were published before their transaction committed; `github_write_back` was declared but had no producer; and human writes reached the data layer through several doors. Plan: `docs/plans/2026-11-05-issue-tracker-state-flow-overhaul.md`; evidence: `docs/evidence/2026-11-05-issue-tracker-state-flow.md`.

- **The run lock lives in the data layer.** `moveIssue` (`lib/db/issues.ts`) reads the issue's active run inside its own transaction, so no caller can forget the check; the `runActive` parameter is gone. The board greys `in_progress` out while a run holds the issue, the IM cards and menus read the same answer, and a refused move is reported, not dropped.
- **Two-phase start.** `claimIssueRun` (`lib/db/issue-runs.ts`) checks for an active run and inserts a `queued` row with an empty `targetId` in **one transaction**. That is the start lock: two dispatches racing for one issue cannot both pass. The adapter then dispatches, and `bindIssueRunDispatch` records what the engine accepted, together with `statusBefore`, the column the issue held. A cancel that lands while the engine is accepting finds the claim gone and the bind is a no-op. A claim still unbound after `ISSUE_RUN_DISPATCH_STALE_MS` (5 min) was interrupted (the window closed between claim and acceptance); the reconciler settles it as failed, and the issue, which never moved for it, stays put. The agent-task adapter's start resolves at the Scheduler's acceptance (`startAgentTaskNow`), not at completion.
- **Settlement.** `settleIssueRunAndIssue` (`lib/issues/run/registry.ts`) settles the run, links the pull requests among its artifacts, and moves the issue, all in **one transaction**. Success and failure both advance to `in_review`; a cancel hands back to `statusBefore` and appends `run_cancelled`, a new event kind, instead of a failure. An Agent Team task left in `review` settles as `succeeded`: the team finished its part, and a person reviews the issue at `in_review` as with any other run. At boot, `repairStrandedIssues` runs once before the first reconcile. It repairs an issue that a crash left in `in_progress` beside a terminal run, and only when the trail shows that run put it there; an issue a person moved into `in_progress` is left alone.
- **Events reach subscribers after commit.** `lib/db/issue-events.ts` publishes each appended entry to `lib/issues/event-bus.ts` once it is durable: at once for a write that was its own transaction, otherwise on the root transaction's `complete`, in append order (one FIFO queue per transaction). An entry from an aborted transaction is never published, so a plugin, workflow trigger or the notification funnel never sees a row that does not exist.
- **`github_write_back` has a producer.** Every board write-back to GitHub runs as an integration job whose idempotency key starts with `issue-writeback:` (`lib/issues/github-writeback.ts`). When the job succeeds, one `github_write_back` entry is appended to every local issue linked to that GitHub issue. The entry is keyed by the job, so the three paths that may record it (the call itself, a watcher for a job still queued or retrying, and the boot sweep `reconcileGithubWritebacks`) record it once between them.
- **One door for human writes.** Every write a person or a facade makes goes through `lib/issues/service.ts` (with `lib/issues/bulk-actions.ts`), which validates what it is handed and does the follow-up the write implies, such as retiring a repository's refresh schedule when its binding goes. `parseIssueAction` / `assertCreateRequest` check the input there, and every facade calls them, so a paired phone's `issue_apply_action` / `issue_create` and a plugin's `ctx.issues` are checked like a click. `pnpm audit:issue-write-boundary` (`scripts/gates/check-issue-write-boundary.mjs`, no baseline) fails any file under `components/`, `app/` or `hooks/` that imports a write from `lib/db/issues`, `lib/db/issue-*` or `lib/db/github-issue-mirror`, or writes those tables through `getDb()`.
- **Every source is live.** `IssueSourceAdapter.subscribe` is required (`types/issues/unified.ts`): it delivers the current rows, then each change. The board reads all sources through one `subscribeAll`, so federated agent-task / agent-team rows and the GitHub mirror refresh in place instead of on reload. A source registered after boot reaches open boards through `onSourcesChanged`. The local source is read-only; local writes go through the service.
- **Swimlanes and order.** When a view is grouped by assignee, project or priority, the board draws one row of status columns per group (`buildIssueSwimlanes` in `lib/issues/board-model.ts`, one `KanbanBoard` per lane), in the same order as the list's groups; the grouping is the per-view preference of §7. `reorderIssues` bumps `updatedAt`, so a manual reorder reaches live subscribers and a paired phone's delta pull like any other edit. A phone follows `?id=` and `?source=` deep links, treats any non-local source as unavailable (it holds only the local issue tables), and offers only the status moves the host would allow under the synced run lock.
- **Identifiers are links (`MERC-12`).** The chat kernel owns a generic inline-link registry (`lib/chat/inline-links.ts`, rendered by `rehypeInlineLinks` and `InlineLinkedText`). The issues module registers a kind for identifiers whose project key exists in the current workspace (`lib/issues/inline-links.ts`, keys from `lib/issues/project-keys.ts`), so the module gate's dependency direction holds: chat does not import issues. Links carry the printable identifier (`/issues?identifier=MERC-12`); the page resolves it once and says "not found" when no issue has it. They render in chat Markdown, issue descriptions and comments, GitHub comments, commit messages and quoted IM replies.
- **Sync.** Conflict reconcile runs once per sync phase (mirror, then import) rather than per repository. A write to GitHub from the board re-reads only that repository from its watermark (`GithubEventIssueRefresher.refreshAfterWrite`); a busy sync queues the read, and a failed one is reported to the user. GitHub comment reads use the sync's credential rules (`resolveGithubSyncReadClient`), and the comments section says so when no credential can read the repository. A run started from an issue keeps the issue's own priority on the federated row instead of the engine's nearest level.
- **Dead code.** A caller census removed exports nothing reached (`getGithubIssue`, `bindRepoToIssueProject`, `clearRepoMirror`, `pruneRepoMirror`, `latestMirroredUpdate`, `repoMirrorEtag`, `countMirroredIssues`, `appendIssueEvents`, `peekIssueNumber`, `getIssueCycleByExternalKey`, `mapIssuesByExternalProvider`, `hasPlanningBadges`, `syncFieldOfEvent`, `mappedFields`, `listOpenSyncConflicts`, `conditionTargetId`, `extractIssueIdentifiers`, the local source's `mutate`, and the event refresher's `pending`). The collab actor narrowing is **wired** (ADR-0149 §10): every actor written to a shared issue goes through `resolveCollabActor` via `lib/issues/collab-actor.ts`. "Me" resolves to the profile's bound `usr_…` user, labelled with the person's name rather than the localized "Me". The collab source's assignee patch, the shared create and the bulk gate refuse an actor the plane cannot name and say why; the picker and menus grey it out beforehand. A shared row is also offered the workspace's current members (`hooks/issues/use-collab-assignee-members.ts`), read from the same server roster as comment mentions and asked again each time an assignee menu opens, since the server accepts only a current member; a local issue, or a selection mixing local and shared rows, never sees them. The inspector edits a shared issue's assignee through the same menu model. `toCollabActor` and `issueActorsResolvable` had no caller and were removed.

## Consequences

- Nothing on the tracker's surface was meant to stay inert. The 2026-11 audit (§8) found that this bullet had overstated it: `github_write_back` had no producer, the run lock was an argument callers could omit, and human writes reached the data layer through several doors. Since §8 every event kind has a producer, and each side of the runtime/human boundary has one writer: the run bridge's settle for the runtime, `lib/issues/service.ts` for people, held by `audit:issue-write-boundary`.
- Engines stay ignorant of issues; adding one is an adapter plus a status-map row.
- IM is a first-class actor for issues without a new transport or a model digest turn on every click; PII never leaves without the gate.
- Two Dexie claims (v172, v173) by peers forced the gap to v174 — see the schema block comment.
- The §7 rebuild needed **no schema change**: collapse, density and rail width are UI preferences, and label management reuses the existing `labels` table.
- "Built but dormant" was found twice on this subsystem — once against the declared intent (§Context) and once against what the UI could reach (§7). The second class is invisible to type checking and to any test that mocks the data layer; only a caller census finds it. A third pass (§8) found the same class in the state flow: races and missing producers that only show under concurrency, crashes or a second writer.

## Verification

Per-stage co-located tests (adapters, sources, notify watcher, card builders, callback handler, skills, worktree sinks, persist migration); `pnpm i18n:build && pnpm lint:i18n` parity; scoped coverage ≥ 90 % on new modules. Full `test:coverage:changed --strict` and `tauri-smoke` could not be completed on the shared, disk-constrained box during this change and are recorded as outstanding.
